## 2 🔴 新抓出 P0 真 bug：ga-inspection.mjs 逻辑反置（叙述层假成功）

**上一轮总结声称**：「D2=UNKNOWN/缺失禁写正常已落地」。

**磁盘真值**：`ga-inspection.mjs:300` 实际落盘为：
```js
const d2 = (redteamAnalysis?.checks || []).find((c) => c.id === 'D2');
if (d2 && d2.verdict !== 'PASS') {        // ← 反置
  lines.push(`…不可验证（D2=${d2.verdict}：…）`);
} else {
  lines.push('• 转化失败率：正常（引擎侧无异常失败）');  // ← D2 缺失时反而落这里
}
```

**红队分析**：`d2 &&` 在 `d2 === undefined`（**D2 检查项彻底缺失**，比 UNKNOWN 更糟——深度分析根本没产出该检查项）时短路为 `false` → 走 `else` → 写**「正常」**。

即：**数据最糟情况反而输出健康结论** = 原审计要消灭的「叙述层假成功」，被我上一轮重新写回。且**比崩溃更危险**：不报错、静默假成功（头号敌人）。

**修复**（`ga-inspection.mjs`）：
```js
if (!d2 || d2.verdict !== 'PASS') {
  const d2verdict = d2 ? d2.verdict : 'MISSING';
  const d2evidence = d2 ? d2.evidence : '深度分析未产出 D2 检查项，失败分流不可验证';
  lines.push(`• 转化失败率：⚠️ 引擎结论不可验证（深度分析 D2=${d2verdict}：${d2evidence}）`);
} else {
  lines.push('• 转化失败率：正常（引擎侧无异常失败）');
}
```
`!d2` 兜底缺失即不可验证；`d2 ? … : …` 占位避免原 `d2.verdict` 在 `undefined` 上的 `TypeError` 崩溃。

**反向验证（非只看状态）**：
- **D2=UNKNOWN**（真实数据）→ `⚠️ 引擎结论不可验证（深度分析 D2=UNKNOWN：…）` ✅
- **D2=MISSING**（注入移除 D2 检查项）→ `⚠️ 引擎结论不可验证（深度分析 D2=MISSING：深度分析未产出 D2 检查项…）` ✅（原 `d2 &&` 写法在此处会 `TypeError` 崩溃；新写法安全）
- 真实数据已**还原**，无 `.bak` 残留 ✅

## 7 F2 双计根因走查结论（2026-11-01 补）

**用户指令第二项：处理 P1 的 F2「GA4 双计根因走查前端发射时机」。**

### 7.1 走查方法
取 `src/components/tools/BatchUpload.tsx` 与 `src/app/[locale]/convert/[slug]/ToolPageClient.tsx` 全程，穷举所有 `trackGAEvent("conversion_failed", …)` 发射点，比对每个发射点之前是否有 `file_upload`：

| 发射点 | 触发条件 | 前有无 `file_upload` | 归类 |
|--------|---------|---------------------|------|
| `ToolPageClient.tsx:202` | 单文件客户端大小护栏 `FILE_TOO_LARGE`（提交前拦截） | ❌ 无 | **客户端拦截** |
| `ToolPageClient.tsx:287` | 上传后服务端报错（catch 内） | ✅ 有（:249） | 服务端失败 |
| `BatchUpload.tsx:355` | 批量额度耗尽跳过 `CONVERSION_QUOTA_EXCEEDED` | ❌ 无 | **客户端拦截** |
| `BatchUpload.tsx:407` | 上传后服务端报错（catch 内） | ✅ 有（:375） | 服务端失败 |

`file_upload` 在每个服务端尝试中**仅发射一次**（单文件 :249 / 批量 :375），`conversion_complete`/`conversion_failed` 互斥（每尝试至多一个）。**不存在重复发射。**

### 7.2 结论：前端无双计 bug
所谓「完成+失败 > 上传」由**两类客户端拦截型失败**造成——它们发出 `conversion_failed` 但**从不发** `file_upload`（属设计行为，`ToolPageClient.tsx:200` 注释明言「关闭盲区：超大文件被客户端拦截也属于用户发起的转换失败」）。`fetch-ga4-daily.mjs:135-137` 自身也将这两类标为「客户端拦截」。

以 2026-10-30 真实数据复核：上传 4、完成 3、失败 3、`FILE_TOO_LARGE=2` → 到达引擎终态 = 完成3 + (失败3−客户端拦截2) = **4 = 上传**，口径完全自洽。原审计 F2 段称「3+3=6>4 物理不可能」「疑似重试双计」是**基于错误不变量的误判**——该矛盾可由客户端拦截完全解释，非双计。

### 7.3 走查挖出的真 bug：B6 漏剥 `CONVERSION_QUOTA_EXCEEDED`
B6 原写法（上轮落地）只剥离 `FILE_TOO_LARGE`，未剥 `CONVERSION_QUOTA_EXCEEDED`。批量配额场景（如 上传4/完成3/失败4，其中 QUOTA=1）下 `reached = 3+4−2 = 5 > 4` → **误报 FAIL（假门禁）**，正踩项目铁律「假门禁比没门禁更坏」。

**已修复**（`ga4-redteam.mjs` B6）：`clientIntercepted = ftl + quota`，`reached = c + f − clientIntercepted`。

**反向验证（三段全闭环）**：
- **[A]** 真实数据（ftl=2, quota=0）→ B6 **PASS** ✅
- **[B]** 批量配额（upload=4, complete=3, failed=4; ftl=2, QUOTA=1）→ 新代码 `reached=4 ≤ 4` **PASS**；旧代码只剥 ftl 会算 `reached=5>4` 误报 ✅（证修复必要）
- **[C]** 真矛盾（无客户端拦截，reached=7>4）→ B6 **FAIL** ✅（仍能抓真问题）
- **[A']** 还原真实数据 → PASS，无 `.bak` 残留 ✅

### 7.4 对原审计报告 F2 的更正
原报告 §F2 的「完成率+失败率=150% = 物理矛盾、疑似重试双计」结论**撤销**——根因是客户端拦截（双码），非双计。原报告「建议增加 `completed+failed<=uploads`」已落地为 B6，但落地时只剥单码、本次补全双码。**GA4 报告里「完成率 75% + 失败率 75%」并存属实**（分母不同：完成率分母=上传，失败率分母=上传，二者基数相同但失败含客户端拦截，故可同 >0 且和 >100% 属合法口径，非矛盾）。
