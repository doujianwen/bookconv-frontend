# 红队审计 · 直传失败三码拆分方案（2026-11-02）

> 审计对象：上一轮排查提出的修复方案——把单一错误码 `DIRECT_UPLOAD_FAILED`
> 拆分为「presign 503 / presign 其他错误 / R2 PUT 失败」三级，使 GA4
> `failedByErrorCode` 能定位直传失败发生在哪一关。
> 触发：实施动作前主动红队（2026-11-01 用户拍板纪律）。

## 0. 审计结论

**GO-WITH-CONDITIONS（有条件通过）。** 方案方向正确、 ROI 高，但**纯实施会引入 ≥2 处新假 FAIL/误报**，
且**方案本身无法解释 11-01 当天 8 次失败的根因**（它是预防性，不是诊断性）。

## 1. 假设挑战（R1）

- **方案是「预防性」而非「诊断性」。** 三码拆分只让**未来**的直传失败可定位阶段，
  对 11-01 当天的 8 次失败**没有任何回溯能力**——那天的数据已落库为单一
  `DIRECT_UPLOAD_FAILED`，永久丢失子原因。
- **红队须明示**：我们至今仍不知道 11-01 是「R2 env 瞬时丢失（presign 503）」
  还是「CORS 回归」还是「用户侧网络」。三种假设都未被排除。
- **建议配套（不阻塞本方案）**：在 `presign` 路由加一处服务端计数/日志——
  当 `isDirectUploadEnabled()===false` 或 `createPresignedPut` 抛错时打一行带时间戳的
  `console.error`/metric。这才是能捕获「某时段 presign 503 脉冲」的真实诊断信号，
  比 GA4 事后聚合快一个数量级。本次先记录，作为后续行动项。

## 3. 关键发现

### R-B（已存在 bug，方案必须顺带修，否则只是平移错误）
`direct-upload.ts:44-48` 在 presign 非 200 时抛 `new Error(payload?.error)`，**丢弃了
presign 返回体里的 `code`**。presign 对 >100MB 文件返回 `413 + code:"FILE_TOO_LARGE"`
（route.ts:133-140），但该 code 被丢弃 → 外层统一改写成 `DIRECT_UPLOAD_FAILED`。
**后果：>100MB 文件当前被误报成「直传失败」而非「文件过大」。** 三码拆分若不分
清 413，会把同一错误平移成 `DIRECT_UPLOAD_PRESIGN_ERROR`，仍错。
**修正：映射时必须保留 presign 自有 code（413→FILE_TOO_LARGE 直通）。**

### R-G（门禁同步铁律，复发点）
三码拆分后 `failedByErrorCode.DIRECT_UPLOAD_FAILED` 在新数据中恒为 0，
3 道门禁（G1/G2/G3）都仍在读旧字面量 → 新码既没被剥离也没被归类 →
B6 假 FAIL + 飞书误报引擎失败 + Part D 误判。**三处必须同步改为「3 新码之和/之集」。**

### R-H（降风险项，已验证）
`error_code` 已是 GA4 注册自定义维度（`fetch-ga4-daily.mjs` 与 `ga4-advanced-analysis.mjs`
都用 `customEvent:error_code` 拉取）。新增**码值**无需重新注册维度，
`failedByErrorCode` 会自动出现新桶。→ 维度层面零风险。

### R-E（429 被吸收，可能掩盖限流脉冲）
presign 限流返回 `429`（route.ts:96-101，无 code）。三码方案里 429 会落入
`DIRECT_UPLOAD_PRESIGN_ERROR`，与「presign 400/网络」混在一起。
**注意：11-01 的 8 次脉冲型失败若实为单用户/批量多次重试触发的限流，会被此方案掩盖。**
建议：至少保留辨识手段（见 §5 设计）；若后续怀疑限流，再拆 `PRESIGN_RATELIMITED`。

### R-A（字面量陷阱）
presign 返回 `"DIRECT_UPLOAD_UNAVAILABLE"`（route.ts:84/169）**不在 ErrorCode 联合**。
当前 `direct-upload.ts` 把它丢成 plain Error 反而「安全」。新方案若改为透传此字面量，
`isErrorCode` 会拒收 → GA4 塌缩 UNKNOWN。
**修正：direct-upload 应把 503 映射为既有 `DirectUploadUnavailableError` 类（已存在），
由 ToolPageClient 按类映射成 `PRESIGN_UNAVAILABLE`，绝不透传 `DIRECT_UPLOAD_UNAVAILABLE` 字面量。**

### R-I（环境残留，低危）
审计者在 R2 桶 `uploads/2026-11-02/<uuid>.epub` 留了 1 个 1 字节探针对象，
按 memory 记载 24h 临时 key 会被生命周期清理，无需人工干预。

## 4. 建议设计（可测 + 保留 FILE_TOO_LARGE）

**新增 3 码（加入 ErrorCode 联合 + ERROR_MESSAGES）：**
- `DIRECT_UPLOAD_PRESIGN_UNAVAILABLE` — presign 503（R2 env 丢 / createPresignedPut 抛错）
- `DIRECT_UPLOAD_PRESIGN_ERROR` — presign 非 200 且非 503/非 413（400/网络；429 暂并入）
- `DIRECT_UPLOAD_PUT_FAILED` — R2 PUT 阶段（CORS 预检失败/网络/5xx）
- **FILE_TOO_LARGE 保持不变**：presign 413 直通，不入上述三码。

**实现要点（消除 R-F 不可测）：**
1. `direct-upload.ts` 抛**带阶段的可判别错误类**：
   - 503 → 既有 `DirectUploadUnavailableError`（→ PRESIGN_UNAVAILABLE）
   - 非 200 且 413 → 抛带 `code:"FILE_TOO_LARGE"` 的错误（→ FILE_TOO_LARGE）
   - 非 200 其他/网络 → `DirectUploadPresignError`（→ PRESIGN_ERROR）
   - PUT 失败 → `DirectUploadPutError`（→ PUT_FAILED）
2. `ToolPageClient.tsx` 不再用 `unavailable` 布尔 + 写死字面量，改调**纯函数**
   `mapDirectUploadError(err): ErrorCode`（放 `src/lib/`，无 React 依赖，可单测）。
3. **门禁同步（G1/G2/G3 三处）**：用「3 新码之和/之集」替换旧字面量。
   耐久改进：把 `PRE_UPLOAD_FAILURE_CODES` / `INFRA_CODES` / `NON_ENGINE` 抽成
   `scripts/` 内**单一共享常量**被三脚本 import，从根上消除「漏改一处」类 bug。
