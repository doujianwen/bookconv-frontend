## 1. 告警 ①②③：三条灰卡为什么都「正确、无需处置」

三者同属「用户上传了损坏/截断的 EPUB」，且都已被既有防线**正确识别并给出可操作提示**
（重新下载 / 重新导出）。逐条取证：

### 1.1 告警 ①（epub→txt，1095 B）
- **1095 字节本身即异常**：一个含 `OEBPS/` 树、`mimetype`、`container.xml`、OPF 的合法 EPUB
  远大于 1KB（项目实测最小合法样本在数 KB 级）。1095B 只能是**截断/导坏**的残片。
- 错误串 `corrupt epub: ZIP member OEBPS/nav.xhtml (manifest reference missing) failed deep
  validation` 命中 `LOCAL_VALIDATION_SIGNATURES` 的 `corrupt epub:` 前缀（alerts.ts:191-198）
  ⇒ `inferLocalValidation` ⇒ `failed`（§3.5 真拦截）。映射 `CORRUPT_INPUT` ⇒ 灰卡，措辞
  「请重新下载或重新导出」正确。
- 路由事实（route.ts:82-85）：`epub→txt` 在 2026-11-08 被**显式排除**出后端委托
  （`canDelegate` 双例外之一，照 `epub→html` 既有写法），改走纯 JS `epubToTxt`。故该告警
  与后端健康度无关，纯本地校验结论。
- **处置：无。** 用户侧可预期错误；卡片已告知重下。频次若飙升才需看（节流窗口 10min 可观测）。

### 1.2 告警 ②（epub→mobi，1,049,781 B）
- 1 MB 文件**通过**了本地 §3.5（否则错误串会是 `corrupt epub:` / `Invalid zip file`，到不了
  引擎），但 Calibre import 阶段抛 `OEBError: Spine is empty`。
- 归因链（与 11-03 诊断 §2 同构）：`route.ts` 委托后端 → Calibre import 失败 → 后端 500
  `CONVERSION_FAILED` → `delegateToBackend` 记 `backend HTTP 500 — CONVERSION_FAILED: …`
  （P1-B 透传，11-03 已部署）→ 回退 CloudConvert → CC import 也拒（`Input task has failed` 类）
  → `convertAndStream` catch → `mapErrorCode` → 灰卡。
- **`Spine is empty` 是 Calibre 真实错误**：OPF 无 spine / 阅读顺序条目（常见于只有图片的 EPUB、
  或 OPF 被破坏）。两引擎独立同判 ⇒ 文件确实不可转。
- **卡片字段瑕疵（非新 bug，已登记）**：`localValidationInferred: failed`。按 alerts.ts 现行
  语义，`inferLocalValidation` 只看 convMsg 是否命中 §3.5 签名；本条 convMsg 来自 CC 回退后的
  错误串，若含 `corrupt epub:`/`invalid zip` 之类即标 failed。但 §3.5 其实**已通过**（文件到了
  引擎）。这正是 11-08 诊断 §2.4 已知的「CC import 拒收被误标 failed」残留语义，**非本次新引入**，
  跨日期统计时不可把 11-08 前后混用（见 alerts.ts:70-75 注释）。
- **处置：无。** 用户侧文件问题。

### 1.3 告警 ③（epub→pdf，639,007 B）
- `Invalid zip file (no central directory; 639007 bytes)` 是 **11-03 诊断**为可归因而**专门新增**
  的前缀安全日志串（`conversion.ts:262` 改 `Invalid zip file (no central directory; N bytes)`），
  子串 `Invalid zip file` 保留，`error-handler.ts` 映射键 / `CORRUPT_INPUT` 灰卡 / `retryable:false`
  全部不变（11-03 §3 已论证「前缀保留的子串安全变更」）。
- 后端侧 `ValueError: Premature end of file` = Calibre 的 `localunzip` 修复路径也失败（与 11-03
  §6.2 实测的「截 ≥1000 B 后 local header 被砍断、Calibre 修复失败」形态一致）。
- **处置：无。** 截断下载，灰卡正确，提示重下。

## 2. 告警 ④（红卡 · 后端熔断 503）：唯一需跟进项

### 2.1 触发机制（代码层，已逐行核对）
- 红卡来自 `conversion-backend-client.ts` 的 `notifyBackendDown()`（:354-361），**只在**
  `recordBackendFailure()` 返回 `transitionedToOpen=true` 时发出——即**某 Vercel 实例的断路器
  由 CLOSED 跃迁到 OPEN 的那一刻**（`conversion-circuit-breaker.ts:63-72`：连续 3 次失败且
  未开过 ⇒ `transitionedToOpen=true`，开 60s）。
- `Error: This operation was aborted` 的**唯一来源**是 `attemptOnce()` 的 90s 超时
  （`conversion-backend-client.ts:139-141` 的 `AbortController` + `controller.abort()`）。
  90s 超时是后端**最重的失败形态**（后端卡死/慢/重启/网络中断），且 `recordBackendFailure`
  对「网络错误/超时」路径（:209-221）默认 `countFailure=true`（计入熔断）。
- 即：告警 ④ 的含义 = 「**某实例连续 3 次后端调用失败（其中最后一次或某次是 90s 超时）⇒ 熔断
  开启 60s ⇒ 该实例 60s 内全站绕过后端、压给 CloudConvert**」。这是**瞬时降级**，不是持续故障——
  60s 后断路器进入 half-open，下一次请求即重新探活，成功后归零。

### 2.2 为什么 11-19/20 可能触发（与告警 ②③ 的时间相关，但**不可据灰卡断言**）
- 灰卡的 500 `CONVERSION_FAILED` 是**快速响应**（Calibre 数秒内拒），按 11-08 修复 `countFailure=false`
  **不计入熔断**——所以告警 ②③ 的 500 本身**不会**开熔断。
- 但 90s **超时**会。若某实例在那段窗口内连续 3 次「超时 + 其它健康失败」，即开闸。告警 ④
  自带 90s 超时串，说明**至少一次**是超时。
- **Unknown（须 SSH 坐实，不可臆断）**：那 3 次具体是哪些请求、后端当时是否真不可用（卡死/
  OOM/被重启/网络抖动）。11-19 当天已有大量 ops 活动（`docs/tasks/bookconv-ops-d1-20261119`），
  若后端做过重启/变更，时间窗可能重合——但这是**假设**，未经后端日志证实前不得当结论。

### 2.3 本地验证尝试与局限（诚实记录 · 对应 MEMORY §0「单机视角系统性误导」）
- 本机出口 = TUN 代理，**无法直连 HK 后端**。实测：
  - `curl https://43.129.176.38/health` → HTTP `000`（~1.56s 连接失败）；
  - `curl https://43.129.176.38/` → HTTP `000`（~0.32s）。
  - `000` 含义是**本地 egress 连不上该 IP**，既不能证明后端宕机、也不能证明在线（代理隧道
    对该目标不可达）。**⇒ 后端真实状态从本地判为 UNKNOWN，不作任何存活/宕机结论。**
- 按 MEMORY §2「连通/拦截类诊断必用外部 vantage 对照（单机视角系统性误导）」，本机 curl
  结果**不得**当作后端健康证据。唯一权威取证通道 = SSH 到 `ubuntu@43.129.176.38`（密钥
  `~/.ssh/geo_tuozhi.pem`）看 `conversion.log` 的 11-19/20 失败窗口 + `systemctl status
  bookconv-conversion`。SSH 为交互式/代理依赖，本次**不擅自执行**（外部动作、需用户确认）。

### 2.4 定级与建议（fail-safe，不扩大范围）
- **等级**：P1（重要残余）。理由：① 属**瞬时**熔断（60s 自愈），非持续故障；② 回退 CloudConvert

  宕机导致全站转换失败」的迹象（若持续宕机，会看到大量红卡 + 转换整体失败率飙升，本次仅 1 条）。
- **不构成 P0 / 不立即行动**的依据：单条红卡、瞬时语义、兜底链路健康。但**必须**留一条待办取证，
  防止「后端真挂了只是这条卡没刷屏」被漏判。
- **建议取证清单（需用户确认后再执行，全部只读）**：

       是否有连续 3 条同签失败 + 是否伴随 90s 级 `rt`/`urt`）

- **代码层无需改动**：熔断 + 回退 + 告警卡 + `delegationFallback` 透传机制在 11-08 已修到位；
  本条红卡是**机制正常工作的产物**（正确告警 + 正确降级），不是机制 bug。

## 3. 红队回执（L2 · 本诊断的自审）

**断言**：A1 灰卡①②③均为用户输入损坏、正确无需处置；A2 告警④是瞬时熔断、P1；A3 本地

**逐条攻击与裁定**：
- **A1 最可能错法**：把「卡片标灰」当成「文件确坏」——但卡片是**推断**（`localValidationInferred`
  明确写 *inferred, NOT measured §3.5*），灰卡也可能掩盖「后端把容量故障伪装成用户错误」。
  **反例核查**：告警②的 `delegationFallback` = `backend HTTP 500 — CONVERSION_FAILED: Spine is
  empty`，是**后端确定性拒收**（countFailure=false 路径），非 429/超时容量信号 ⇒ 排除「容量伪装」。
  告警①`epub→txt` 根本不走后端 ⇒ 与容量无关。**裁定：通过**（三条各自排除容量故障伪装）。
- **A2 最可能错法**：把「瞬时」当结论——可能其实是后端**持续**宕机、只是 60s 冷却 + 10min 节流
  让红卡没刷屏。**反例核查**：本地无后端日志佐证持续不可用（UNKNOWN），且若持续宕机，告警②③
  的回退 CC 会因 CC 也忙而**普遍**失败、用户侧会看到大量转换失败而非「个别坏文件」；本次 4 条里
  3 条是**不同输入文件**各自的损坏（1095B/1MB/639KB 三个 hash 不同），更像分散的用户侧坏文件，
  而非系统性后端故障。**裁定：暂通过，但保留 P1 取证待办**（A2 的「持续宕机」子假设未证伪，
  需 SSH 坐实，不得当已排除）。
- **A3 最可能错法**：把 000 误读成「后端挂了」或「后端好的」。**裁定：通过**——000 在本机 TUN
  代理下仅表示本地 egress 不可达该 IP，方向中性，已显式标 UNKNOWN，未据此下任何存活结论。
- **A4 最可能错法**：「无需改代码」可能漏掉 11-08 登记的已知债务（告警②`localValidationInferred`
  误标 failed）。**裁定：通过（范围限定）**——本诊断只做 triage 定级，不捆绑修复 11-08 已登记的
  残留语义；若用户要「根治卡片误标」，那是 11-08 §5 残余项，另开任务（且属「指标口径变更」，
  需走独立通道，不并入本次）。

**残余（UNKNOWN / 未证伪）**：
