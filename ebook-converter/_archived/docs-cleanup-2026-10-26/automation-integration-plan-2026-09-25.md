## 二、职责边界判定

### 2.1 核心问题不同（本质互补，非重叠）

| 维度 | geo-audit-content.mjs（监控侧） | bookconv-daily-analysis（双渠道侧） |
|------|-------------------------------|-----------------------------------|
| 被审计对象 | 内容文件 `src/data/content/*.ts` | 线上流量数据（GSC/Bing API/CSV） |
| 回答的问题 | 「这个页面**有没有** GEO 要素？」 | 「站点在搜索 / AI 里**表现如何**？」 |
| 时间属性 | 静态（发布前 / 改后） | 动态（发布后，随算法波动） |
| 失败含义 | 内容缺章节 / 词数不足 | 流量下跌 / 排名漂移 / 引用变化 |
| 输出消费者 | 开发者（CI 阻断发布） | 运营者（日报 / 战略决策） |
| 计算口径 | 0–7 GEO 评分，EN-only | VI v1.0、Bing AI Citations、GSC 曝光 |

**结论**：两者监测的是不同维度（内容结构 vs 外部信号），**不存在功能重叠**。它们像「出厂质检」与「上市后的销量 / 口碑监测」——质检不替代销量监测，销量监测也不需要重做质检。

### 2.2 真实存在的「计划内重复」⚠️

`docs/convert-page-geo-standards-v2-2026-09-24.md` **§5.3** 写道：

> 在每日分析流程中增加 convert 页面 GEO 合规率追踪：统计 PASS/WARN/FAIL 比例，监控 Top 10 高 Citation 页面的 GEO 评分变化。

这条会把 **GEO 合规率计算**塞进每日双渠道流程 —— 而该指标已由 `geo-audit-content.mjs` 作为**单一事实源（single source of truth）**在 CI 中计算。若双渠道流程自行重算，会出现：
- 两处口径可能漂移（阈值、EN-only 处理、计分词正则若不统一）；
- 维护双倍逻辑；
- 「狼来了」风险：双渠道流程若放宽阈值，会与 CI 门禁结论矛盾。

**处置**：§5.3 的「追踪 GEO 合规率」改为「**引用**审计产物，不重算」——每日报告只读 `geo-audit-content.mjs` 的 PASS/WARN/FAIL 汇总行作为静态背景，焦点仍放在流量 delta。

### 2.3 潜在的弱重叠（可合并）

| 项 | 现状 | 风险 | 建议 |
|----|------|------|------|
| GSC 数据拉取 | 每日双渠道流程 §0.1 拉 GSC；另有一次性「GSC 监测」自动化（9/10 已过） | 过期的 GSC 监测自动化若被误触发会重复拉取 | 删除已过期的 `automation-1787835506064`；GSC 拉取唯一归属每日双渠道流程 |
| GEO Validation Day 系列 | 7/14/30 天复测自动化，未定义具体执行脚本 | 若独立手算合规率 = 与 CI 门禁重复 | 明确这些自动化 =「运行 `geo-audit-content.mjs` + 读取最新双渠道日报的趋势段」，而非独立重算 |

## 三、整合方案

### 3.1 单一事实源（Single Source of Truth）划分

```
┌─────────────────────────────────────────────────────────────┐
│                  单一事实源（不重复计算）                       │
├──────────────────────────┬──────────────────────────────────┤
│  内容合规（GEO 要素）      │  流量 / 可见性                    │
│  Owner: geo-audit-content │  Owner: bookconv-daily-analysis  │
│  .mjs（CI + 手动）         │  （每日 22:00 自动化）            │
│                            │                                  │
│  输出: PASS/WARN/FAIL 矩阵 │  输出: 日报/深度/红队/最终报告     │
│  触发: push / 改内容后      │  触发: 每日 22:00 / 手动          │
└──────────────┬───────────┴───────────────┬──────────────────┘
               │ 引用（只读）                │ 引用（只读）
               ▼                            ▼
      GEO Validation Day 自动化     每日报告「内容合规」背景段
      （运行审计 + 读趋势）          （粘贴审计汇总行，不重算）
```

### 3.2 整合后的流程结构

```
[Push / 改内容]
      │
      ▼
┌──────────────────────────────┐
│ CI: lint + typecheck +        │  ← 门禁，阻断不合规发布
│   geo-audit-content.mjs        │
│   → PASS 才允许部署             │
└──────────────────────────────┘
      │ 部署上线
      ▼
┌──────────────────────────────┐
│ 每日 22:00 自动化 f4d73b34     │  ← 流量监控，不碰内容合规计算
│ bookconv-daily-analysis        │
│  ① 拉 GSC + Bing（唯一拉取方） │
│  ② 算 VI / Citations / 曝光     │
│  ③ 报告内「内容合规」段：       │
│     只读 geo-audit 汇总行       │
│     （12/31 PASS，来源标注）    │
└──────────────────────────────┘
      │
      ▼
┌──────────────────────────────┐
│ GEO Validation Day 7/14/30     │  ← 复测节点
│ 动作: 运行 geo-audit-content    │
│       + 读近 30 天双渠道日报趋势 │
│       → 输出「合规率变化 +      │
│         流量承接」对比结论       │
└──────────────────────────────┘
```

## 四、结语

两套流程**职责清晰、天然互补**：一个是「出厂质检」（内容合规，静态门禁），一个是「上市后监测」（流量 / 可见性，动态日报）。真正需要做的是**堵住 §5.3 的计划内重复**与**清理过期 GEO 监测自动化**，让内容合规始终只有一个计算器（`geo-audit-content.mjs`），流量监控始终只有一个管道（`bookconv-daily-analysis`）。
