# 诊断：18 个零曝光页卡在哪（Discovered-not-indexed 根因分析）

> **诊断对象**：`/convert/*` 下 18 个零曝光页面
> **诊断方式**：GSC URL Inspection 原始数据 + 生产代码静态分析 + 线上实测
> **诊断时间**：2026-10-25
> **数据源**：`数据分析/GSC_URLInspection_2026-10-20.csv`、`src/lib/internal-links.ts`、`src/components/tools/RelatedConversions.tsx`、`src/app/sitemap.ts`、线上 curl 实测

---

## 〇、先纠正一个口径

「18 个 Discovered-not-indexed」这个说法来自 10-11 的旧报告。**10-20 的最新 URL Inspection 实测**（15 个 URL 样本）真实分布是：

| 状态 | 数量 | 页面 |
|---|---|---|
| `Discovered - currently not indexed` | **11** | epub-to-pdf, mobi-to-pdf, epub-to-html, html-to-epub, fb2-to-epub, cbr-to-pdf, txt-to-epub, doc-to-epub, mobi-to-txt, djvu-to-pdf, lit-to-mobi |
| `URL is unknown to Google` | **3** | azw3-to-pdf, epub-to-jpg, epub-to-png |
| `Submitted and indexed`（但零曝光） | **1** | azw-to-mobi |

其中 3 个 unknown 页里有 2 个是**刻意 noindex**（`epub-to-jpg.ts:5`、`epub-to-png.ts:5` → `noindex = true`），不属于故障。真正需要处理的是 **11 个 Discovered + 1 个 azw3-to-pdf**。

## 一、诊断结论（三层根因，按权重排序）

| 层级 | 根因 | 权重 | 一句话 |
|---|---|---|---|
| **L1 主因** | **抓取预算严重超载** | 60% | sitemap 有 165 个 URL，convert 只占 24 个（14.5%），而站点权重只支撑 11 个自然关键词 |
| **L2 放大器** | **内链分配极化** | 30% | 所有 convert 页的「其他转换」模块都指向同一批头部 6 页，10 个页面入链为 0 |
| **L3 信号衰减** | **lastmod 停滞** | 10% | 21 个 URL 共享 `2026-08-25`，站点两个月无更新信号，Google 降低抓取频率 |

**关键判断：不是内容质量问题。** 11 个 Discovered 页 Google **根本没抓取过**（`lastCrawlTime` 全为空），无从评价内容。任何"改文案/改标题"的动作在当前阶段都是无效投入。

---

## 二、L1 证据：抓取预算被 92 个非转换页稀释

线上 `sitemap.xml` 实测：

| 路径 | URL 数 | 占比 |
|---|---|---|
| `/blog` | **66** | 40.0% |
| `/guide` | 26 | 15.8% |
| `/convert` | **24** | **14.5%** |
| `/es` | 19 | 11.5% |
| `/formats` | 15 | 9.1% |
| 其他（静态页/data/compat 等） | 15 | 9.1% |
| **合计** | **165** | 100% |

**问题**：站点自然关键词总数只有 **11 个**（SEMrush 数据），却向 Google 提交了 **165 个 URL**。按 11 个关键词的权重水平，实际可被有效抓取的容量远小于 165。

**后果**：Google 只能挑着抓。挑选依据是「内链密度 + 更新频率」，而这两项 convert 页都处于劣势——blog 66 个页面互相链接、更新频繁，抢走了大部分预算。

**旁证**：`epub-to-pdf` 入链高达 23 条（全站头部），**依然是 Discovered**。这证明预算紧张到连头部页都排不上队，问题不在单页。

## 三、L2 证据：内链分布极化（本次实测）

### 3.1 算法缺陷定位

`src/components/tools/RelatedConversions.tsx:27-34`：

```ts
const related = SUPPORTED_KEYWORDS
  .filter((k) => {
    const key = `${k.source}-${k.target}`
    if (key === currentKey) return false
    return k.source === currentSource || k.target === currentTarget
         || k.source === currentTarget || k.target === currentSource
  })
  .slice(0, max)   // max = 6
```

两个缺陷叠加：

1. **`SUPPORTED_KEYWORDS` 只有 31 条**（`KEYWORDS` 50 条 ∩ `CONVERSION_MAP` 60 对），候选池本身就小
2. **`.slice(0, 6)` 无排序、无轮转** —— 永远取 `KEYWORDS` 数组**最前面**的 6 个匹配项

**实测结果**：`epub-to-rtf`、`epub-to-jpg`、`epub-to-html` 三个页面的「其他转换」输出**完全相同**：

```
epub-to-pdf, mobi-to-epub, azw3-to-epub, pdf-to-epub, docx-to-epub, epub-to-mobi
```

即：**所有冷门页都在向同一批热门页单向输送权重，自己拿不到任何回馈。** 这是典型的内链漏斗倒置（马太效应）。

### 3.2 全站入链实测（28 个 convert 页）

| 入链数 | 页面数 | 页面 |
|---|---|---|
| **0** | **10** | azw-to-mobi, doc-to-epub, epub-to-html, epub-to-jpg, epub-to-png, epub-to-rtf, epub-to-zip, html-to-epub, lit-to-mobi, rtf-to-epub |
| 1–2 | 7 | cbr-to-pdf(1), djvu-to-pdf(1), epub-to-doc(1), fb2-to-epub(1), epub-to-txt(2), mobi-to-azw3(2), txt-to-epub(2) |
| 3–9 | 5 | azw3-to-pdf(3), azw3-to-mobi(4), mobi-to-txt(5), mobi-to-pdf(8), epub-to-azw3(10) |
| 19–25 | 6 | docx-to-epub(19), azw3-to-epub(22), epub-to-pdf(23), pdf-to-epub(23), epub-to-mobi(25), mobi-to-epub(25) |

**头部 6 页拿走 19–25 条入链，尾部 10 页是 0。** 中位数约 2。

### 3.3 与 GSC 状态交叉验证

| 页面 | 实测入链 | GSC 状态 |
|---|---|---|
| epub-to-html | 0 | Discovered |
| doc-to-epub | 0 | Discovered |
| html-to-epub | 0 | Discovered |
| lit-to-mobi | 0 | Discovered |
| fb2-to-epub | 1 | Discovered |
| cbr-to-pdf | 1 | Discovered |
| djvu-to-pdf | 1 | Discovered |
| txt-to-epub | 2 | Discovered |
| mobi-to-txt | 5 | Discovered |
| mobi-to-pdf | 8 | Discovered |
| epub-to-pdf | 23 | Discovered |

**入链 ≤2 的 8 个页面，100% 落在 Discovered。** 相关性成立。

但 `epub-to-pdf`（入链 23）也是 Discovered，说明内链只是放大器而非唯一原因 —— 回到 L1。

### 3.4 一个反常数据，它反而是最强的证据

`azw-to-mobi` **入链为 0，却是唯一被索引的页面**（`lastCrawlTime: 2026-08-09`）。

合理解释：该页在 **8 月**被爬过，那时站点结构/权重与现在不同。**此后两个多月，Google 再没抓过任何 convert 页**（其余 14 个页面的 `lastCrawlTime` 全为空）。

这说明抓取频率在 8 月后**整体塌陷**，不是某个页面单独的问题。

## 四、L3 证据：lastmod 停滞

线上 sitemap 的 `<lastmod>` 分布（top 5）：

| lastmod | URL 数 |
|---|---|
| 2026-08-25 | **21** |
| 2026-08-02 | 17 |
| 2026-08-09 | 14 |
| 2026-08-08 | 10 |
| 2026-09-04 | 9 |

- **21 个 URL 共享同一个日期** —— 典型的批量生成痕迹，Google 会识别为低差异内容
- **9 月之后几乎无更新** —— 站点向 Google 发出「两个月没动」的信号，直接压低抓取频率
- 代码层根因：`sitemap.ts:239` `lastModified: new Date(CONTENT_DATES[key] || '2026-07-26')`，26 个键覆盖 28 页，兜底日期是固定的 7-26

## 五、一个次要但真实的负面因素：TTFB

线上实测（3 次取均值）：

| 页面 | TTFB |
|---|---|
| /convert/epub-to-pdf | 0.78s / 0.88s / 0.96s |
| /（首页） | 0.80s |

静态生成页面 TTFB 稳定在 **0.8–1.0s**，偏慢（Vercel 静态页正常应 <300ms）。虽未到致命水平（>2s），但会轻微侵蚀抓取预算。**优先级低于 L1/L2/L3，暂不作为主要修复项。**

## 六、修复优先级（按 ROI 排序）

### P0 · 给 convert 页单独开 sitemap 索引（预计 1–2 小时）

**动作**：拆成 `sitemap-convert.xml`（24 页，priority 0.9）+ `sitemap-content.xml`（blog/guide，priority 0.4），用 `sitemap-index.xml` 聚合。

**理由**：不改内容、不动页面，纯粹调整向 Google 提交的优先级信号。让 convert 页从 165 个 URL 的竞争中独立出来。

**风险**：低。sitemap 结构变更需在 GSC 重新提交。

### P1 · 重构 RelatedConversions 内链算法（预计 2–3 小时）

**动作**：
1. 候选池扩到全量 `CONVERSION_MAP`（60 对），不只 `KEYWORDS` 交集
2. 排序改为「**目标格式相同** > 源格式相同 > 反向对」，而非按数组顺序
3. 加**入链均衡**：优先链接入链数低的页面（可用静态 map 或构建期计算）
4. `max` 从 6 提到 8

**理由**：把 10 个零入链页的入链从 0 提到 ≥5，直接解决 L2。

**风险**：中。会改变全站 28 个页面的内链结构，需回归测试 404（`dynamicParams=false` 下链到不存在的 slug 会 404）。

### P2 · lastmod 真实化（预计 30 分钟）

**动作**：删除 `'2026-07-26'` 兜底，改用 git 提交时间或内容文件的真实 mtime；同一批页面不再共享同一日期。

**理由**：恢复"站点在更新"的信号。

**风险**：低。

### P3 · 重新提交索引（预计 10 分钟/页）

**动作**：P0–P2 上线后，对 11 个 Discovered 页逐条在 GSC 请求编入索引（有配额，分批）。

**理由**：加速验证修复效果。**必须在 P0–P2 之后做**，否则等于让 Google 重新确认"这些页还是不值得抓"。
