# 诊断：doc→epub 转换 100% 失败（两头堵第三例）

- 日期：2026-11-01
- 触发：飞书红卡告警 Job `1f80d108-02aa-49a2-8eb5-331e59b6c98f`（2026-11-01T14:03:36Z）
- 现象：`/api/convert` 同步路径，doc → epub，CloudConvert 两次尝试均报 `This conversion type is not supported`（engine=auto ×2），用户收到 500。

## 一、结论（TL;DR）

**这不是系统故障，是一个未被 422 拦截的「两头堵」死组合**——与 2026-10-28 已结案的 `epub→doc/jpg/png`（方案 A，commit 0a3f469）完全同类，但当时漏了反方向：

1. **CloudConvert 侧**：CC 不存在 doc→epub 转换路径。官网转换页 https://cloudconvert.com/doc-to-epub 返回 404 "This conversion type is not supported"（本次实测 + 生产错误双确认）。
2. **自建 Calibre 后端侧**：Calibre `ebook-convert` **不支持 .doc 输入**。官方手册输入格式清单只有 DOCX，无 DOC（无 "DOC Input Options" 章节）。且后端源码里不存在任何 LibreOffice 调用——`CONVERSION_MAP` 里 `"doc-epub": { tool: "libreoffice+calibre" }` 的标签自始就是**规划性标注，从未有实现**。
3. **拦截层**：`UNSUPPORTED_CONVERSIONS` 注册表（src/lib/unsupported-conversions.ts）只登记了 `epub-doc / epub-jpg / epub-png` 三个键，**没有 `doc-epub`** ⇒ 请求畅通无阻地走完 上传→§3.5→CC→两次失败→500→红卡告警 全流程。

**判定：doc→epub 在当前架构下 100% 必然失败，属确定性缺陷而非偶发故障。** 每一次 SEO 流量进入 /convert/doc-to-epub 页面并上传，都会得到一次失败。

## 三、附带发现

1. **告警误分级**：该确定性失败走红卡 🚨 "System-side fault — investigate now"，稀释告警信噪比（M8-8 同类关切）。根因不是分级逻辑错，而是**这类请求根本不该到达转换层**——加拦截后此告警自然消失。
2. **落地页内容失实（P1）**：`src/data/content/doc-to-epub.ts` 明文宣称 "The Calibre engine parses DOC structure..."、FAQ 教用户跑 `ebook-convert input.doc output.epub`——与 F4 矛盾。页面承诺了一个任何引擎都做不到的事。`src/data/blog/ebook-formats-explained.ts:112` 同样引导用户去 /convert/doc-to-epub。
3. **CONVERSION_MAP 标签债务**：`tool: "libreoffice+calibre"` 是唯一无实现的标签，审计时应视为"CC 依赖"处理（它实际走 CC，且 CC 也不支持）。

## 四、修复建议（待拍板，方案 A 延伸，零成本）

**最小修复 = 在 UNSUPPORTED_CONVERSIONS 注册表加一个 `doc-epub` 条目**（一处改动同时激活 API 422 拦截 + 前端页面提示，两消费点自动生效）：

- `alternativeHref: "/convert/docx-to-epub"`（站内已有纯 JS 实现，免疫 CC 402/402 墙）
- 提示语义：老 .doc 请先另存为 .docx（Word/LibreOffice 均可），再用 DOCX→EPUB——诚实、可操作。
- **必须同步**（铁律：改能力必须同步改门禁基线）：
  1. `scripts/audit-claims` 基线核对（doc→epub 页面文案是否声明了可转换能力）；
  2. 落地页 doc-to-epub.ts 的 Calibre/DOC 声明改为诚实版（保留页面引流，参照 epub-to-doc 页的"诚实展示"先例）；
  3. blog 内链 ebook-formats-explained.ts:112 的引导语同步。
- 不建议的方向：后端装 LibreOffice 解 .doc 输入（与零成本优先冲突，且为单一低流量组合引入新运维面）；等 CC 未来支持（无时间表）。

**反向验证要求（若实施）**：注入 doc-epub 请求 ⇒ 应得 422 UNSUPPORTED_CONVERSION（而非 500）；恢复（删条目）⇒ 回到 CC 路径。门禁基线改动须双向验证退出码。

## 五、红队自审（结论产出后、实施前）

- 「会不会是 CC 瞬时抖动？」——否：两次尝试同错 + 官网页面 404 + Calibre 手册三源互证，确定性结论。
- 「会不会是 .docx 改名的假 .doc？」——不影响：CC 按声明的 input_format 判死，真 .doc 假 .doc 同样失败。
- 「还有没有其他漏网组合？」——F10 已排扫全部 17 个非纯 JS 组合，仅已知 3+1 个死组合。CC 网页 200 ≠ API 一定可用（如 cbr-to-pdf 走 CC 是否真成功仍属运行期问题，但至少路径存在，与本案"路径不存在"不同性质）。
- 「alert 的 localValidation passed 会不会误导？」——告警已自带 "inferred, NOT measured §3.5" 标注（11-01 修正后），无误导。

### 6.2 红队修正（修复清单更新）

1. 🔧 **撤回「同步 audit:claims 基线」这条必做项**。实测 audit-plan-claims.mjs 扫描面 = 文件大小/配额/批量/OCR 类声明（`50 MB` 等 CLAIM 正则），**不管转换组合能力**（F15）。昨晚把 MEMORY「改能力必须同步改门禁基线」铁律错误套用到了不相关门禁。修正为：改动提交前跑常规内容门禁三件套（`audit:content` / `audit:meta-desc` / `audit:syntax`）即可——这是 TASK-GOVERNANCE §1 既有纪律，无需新增基线。
2. 🔧 **落地页失实程度比昨晚报告更严重**（修复文案范围扩大）。doc-to-epub.ts:80 描述了一个 "**DOC to DOCX (LibreOffice), then DOCX to EPUB (Calibre)**" 两步管线并作为本站转换器的实现原理介绍——该管线在代码中**完全不存在**（后端无 LibreOffice）。除已记录的 line 30/34/164 Calibre 声明外，line 80-82、102、165、167、170 均需纳入文案修正范围。
3. 🔧 **西语版情况确认（降低实施复杂度）**。doc-to-epub **无 ES 页面**（epub-to-doc.ts 有 `export const es`，doc-to-epub.ts 无），新注册表条目的 `noticeEs` 字段仍必填（接口要求 + 共享组件兜底），但不会被本页 ES 版消费（不存在）。ES 变体漏网风险（audit:claims 曾踩的坑）在本案不适用。
