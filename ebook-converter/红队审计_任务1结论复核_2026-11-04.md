## 1. C1 — 立论前提误归因（重要，非阻断）

**断言**：任务 #1 的动机是"本次告警 f547b469 本质=后端瞬时 5xx 被熔断误判宕机、job 白烧给 CC 回退"。

**攻击**：
- 测试注释（`conversion-backend-client.test.ts:448-450`）原文："后端瞬时 5xx 是本次告警 f547b469 的本质——单次 5xx 直接回退 CC 会把本可在后端成功的 job 白烧。"
- 但原始诊断文档（`诊断_epub转azw3_Invalid_zip_file_2026-11-03.md` §1.2）铁证：f547b469 的 500 是 `CONVERSION_FAILED`（BadZipfile，用户文件损坏），耗时 3.693s、**非超时、非宕机、非 429**，且同一客户端 22:42–22:52 共 5 次 epub→azw3 其中 4 次成功。
- 即该 500 是**转换失败**而非**基础设施瞬时故障**。对坏文件重试必再失败 → 仍回退 CC，多一次后端往返。重试对这种 500 **零收益**。

**裁定：修正**。任务 #1 的代码（对真·瞬时 5xx 重试）仍有价值，但"针对本次告警"的叙事是错的——那次告警根本不属于重试能救的类别。诊断文档 §3.2 自己已正确表述"真正的改进方向在减少后端瞬时失败窗口"，与测试注释矛盾。代码行为不变（fail-safe），不需回滚，但**测试注释与任务 #1 诊断文档必须校正**，否则误导未来维护者。

## 2. C2 — 重试收益范围被夸大

**断言**："对快速返回的 5xx 重试 1 次能挽救瞬时抖动、避免白烧 CC job"。

**攻击**：代码路径 5（`conversion-backend-client.ts:230-255`）对所有 5xx 一视同仁重试，无法区分 `code: CONVERSION_FAILED`（坏文件）与基础设施抖动。占多数的"坏文件 500"重试后必再失败，最终仍回退 CC，且每次多花数秒后端往返 + 后端负载。在后端本就繁忙时反而轻微加负。

**裁定：部分成立**。重试仅对"后端重启/过载抖动"这类**真·基础设施瞬时 5xx** 有价值；对"转换失败 500"是净开销。可选增强（P2，非阻断）：若响应体 `code === "CONVERSION_FAILED"` 则**跳过重试**，省一次必败往返。建议记录为观察项，本次不强制。

## 3. C3 — "7 天 GA4 监控证伪" 是弱验证

**断言**：部署后 7 天 GA4 `conversion_failed` 回退计数变化可"证伪"重试有效性。

**攻击**：若后端 5xx 率极低（<1%），7 天内可能观测到 0 次 5xx → 无信号 → 既不能证真也不能证伪（absence of evidence）。且 `conversion_failed` 不区分"5xx 回退 CC"与"坏文件回退 CC"，归因 muddy。

**裁定：降级**。该监控只能做趋势观察，**不是证伪机制**。真正的运行时证伪需要 fault-injection 探针（此前标为 churn）或一条受 env 保护的合成测试端点。应如实降级该验证承诺，不得写成"已验证"。

## 4. C4 — FormData 复用发空 body 的担忧（实测推翻，重要）

**断言担忧**：`backendForm` 在 `conversion-backend-client.ts:119` 建一次、`attemptOnce` 第 139/239 行各 fetch 一次；Node undici 的 `fetch` 把 FormData 当 body 可能消费其流，第二次请求发空 body，使重试在生产环境静默失效。

**攻击（实测）**：写 `_wb_tmp/redo-formdata-probe.mjs`，本地起 HTTP server，用**真·fetch**（非 mock）对同一个 FormData 连发两次（模拟 attemptOnce 复用），server 第一次返 500、第二次返 200：

```
first.status = 500  retry.status = 200
SECOND request body length = 396
SECOND body has filename 'book.epub' = true
SECOND body has file bytes 'fake-epub-bytes' = true
SECOND body has 'source_format' = true
VERDICT: REUSE OK — second attempt carries the file
```

**裁定：通过（担忧被实测推翻）**。undici 每次重新序列化 FormData（它是可重读容器，非一次性流），重试带完整 body。需注意：单测 `retry sends a fresh, valid FormData`（行 536-553）靠 mock 只断言"对象引用仍在"，本身不足以证明真·序列化；真正证据是本次实测。建议把实测固化为集成测试或在文档标注"已实测证伪"。实际路径（`formData.get("file")` 缓冲式 File、`prebuiltFile` R2 缓冲式 File）均为可重读，无流耗尽风险。

## 6. C6 — "已上线/已部署" 未独立验证（L3 缺口）

**断言**："Vercel 正在冷启部署，新代码已上线"。

**攻击**：仅核实了 push（remote HEAD=`6a4e390`，落后 0，禁 force），但 Vercel 实际构建/部署成功从未查过。诊断文档 §6.5 自己强调过"push ≠ deployed（CI 绿≠Vercel 构建成功，且无客户端探针能判断新部署是否上线）"。声称"已上线/已同步"按规则属 L3，需独立通道复核；本环境无 Vercel 工具。

**裁定：修正**。该断言必须降级为"**已 push，部署状态待核实**"，不得声称已上线。补验证方法（二选一）：① 像 §6.5 那样 POST 一个合成探针到生产，观察告警卡是否含任务 #1 特征串（如 `(after 1 retry)` 仅在运维日志、或确认重试行为）；② 查 Vercel deployment 状态。本次未做，标 `L3-UNAVAILABLE · 单源自证·未经独立复核`。

> **2026-11-04 补做（用户批准 B）**：生产 `/api/health` 直接访问（不经代理）**HTTP 200**（2.77s）→ 部署在响应、未崩溃，**部分闭合 C6**（证明"部署在 serving"）。但 health 体无 commit SHA，无法区分 `6a4e390` 新构建 vs 旧构建（新构建失败会保留旧版）→ **commit 级证明仍 L3-UNAVAILABLE**，需到 Vercel 后台核对最新 READY 部署 commit=`6a4e390`。本沙箱无 Vercel 凭据（`~/.config/vercel` 空、`VERCEL_TOKEN` 无、shell rc 无 token），独立通道不可达。

> **2026-11-04 二次补做（用户批准「加字段」）：C6 正式闭环**。给生产 `/api/health` 加 `commitSha`(=Vercel 注入 `VERCEL_GIT_COMMIT_SHA`)+`environment` 字段（commit `409aa98`），push 后 Vercel 自动部署，轮询生产 health：第 4 次返回 `commitSha=409aa98cfeccd91f2d7241773ddc83b300ee8437`、`env=production`，与 `git rev-parse HEAD` 完整 SHA **精确匹配** → 线上构建即 `409aa98`，**无需 Vercel 后台即可独立证伪 deploy-state**。原 L3-UNAVAILABLE 缺口消除（前提是 Vercel 注入 `VERCEL_GIT_COMMIT_SHA`，已在生产实测成立）。
