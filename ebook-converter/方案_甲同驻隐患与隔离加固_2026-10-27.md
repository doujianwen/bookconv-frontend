# BookConv 转换后端「甲·同驻香港机」隐患论证与隔离加固方案

> 配套文档：`方案_BookConv转换后端部署_新服务器_2026-10-27.md`
> 适用决策：**甲·同驻**（转换后端放 HK 2C4G，与 GEO 增长系统同机）
> 用户硬性要求：**单独建文件夹、与 GEO 增长系统完全隔离**
> 日期：2026-10-27

---

## 〇、结论先行（TL;DR）

1. **甲方案能行，但"同机同目录"本身就是最大的隐患来源**——4GB 内存要与 GEO 官网 + 增长后台 + 渠道控制台 +（可能）GEO 的 DB 同驻，Calibre 峰值内存 0.5–1GB，不加隔离会反噬 GEO。
2. **"单独建文件夹" ≠ 隔离**。文件夹只是目录，真正隔离 = 独立 OS 用户 + 独立 systemd/docker 单元 + cgroup 资源硬上限 + OOM 保护 + 独立磁盘/日志 + failover。本方案把这六层都补齐。
3. **对 SEO/GEO 影响 ≈ 0**，条件是隔离到位。迁移的只是 server-to-server 的「转换后端」，用户和爬虫永远不直接访问它；BookConv 前端仍在 Vercel。唯一真实杠杆是"同机资源争用拖慢 GEO 的 TTFB"，隔离后这一项也被消除。
4. **后端形态必须用「无状态 slim HTTP」（选项 B）**，而不是整个 Next 应用容器——后者要 Postgres/Redis，会把 BookConv 的状态耦合进 GEO 的机器，破坏隔离。

## 一、甲·同驻的隐藏隐患（10 项，含机制与严重度）

| # | 隐患 | 严重度 | 机制（为什么"同住"比"独居"更危险） |
|---|------|--------|------|
| R1 | **内存争用 → OOM killer 误杀 GEO/DB** | 🔴 高 | Linux OOM killer 默认优先杀"占用内存最多"的进程。Calibre 是瞬时任务，跑完即退；而 GEO 的 node/DB 是长驻且持续累积内存，**OOM 时反而更可能杀掉 GEO/DB**，BookConv 自己全身而退。这是最阴险的反直觉风险。 |
| R2 | **磁盘占满 → GEO DB 写失败** | 🔴 高 | Calibre 把 EPUB(zip) 解压到临时目录处理，解压后体积常达原文件 3–10 倍。50MB EPUB → 约 500MB 临时文件。若临时目录在 GEO 共用的根文件系统上，清理慢/并发堆积会写满磁盘 → GEO 的数据库写入失败、站点报错。 |
| R3 | **CPU 饥饿 → GEO TTFB 飙升** | 🟠 中高 | Calibre 转 EPUB→PDF 是突发重 CPU。2 核被转换吃满时，GEO 页面响应从百毫秒级退化到秒级，直接冲击 GEO 的 Core Web Vitals（GEO 信号之一）。 |
| R4 | **安全爆炸半径** | 🔴 高 | 转换后端接收用户上传文件并跑 Calibre（电子书解析历史上有 CVE）。若被绕过/提权，攻击者与 GEO 同处一台机器、可能触达 GEO 的密钥与数据库，爆炸半径从"一个无状态 worker"扩大到"整个 GEO 业务"。 |
| R5 | **单点故障耦合** | 🟠 中 | 机器重启、内核升级、docker daemon 重启会同时干掉 GEO 和 BookConv 后端。维护窗口无法独立。 |
| R6 | **网络出口争用** | 🟠 中 | Calibre 做 EPUB→PDF 时会抓取远程图片/字体；若它占满出口带宽，GEO 对外的 API 调用（LLM、分析、Webhook）会被拖慢。 |
| R7 | **运维/升级耦合** | 🟠 中 | 共用 docker-compose 或同一 daemon 时，升级 BookConv 镜像可能误重启 GEO；配置漂移难以区分归属。 |
| R8 | **可观测性混乱** | 🟡 中低 | 日志混在一起 → 事故时难以快速定位是 GEO 还是 BookConv 引起的，拉长 MTTR。 |
| R9 | **端口/防火墙误暴露** | 🟡 低 | 同在 nginx 下若 server block 配错，`/api/convert-internal` 可能被公网直连，密钥泄露。 |
| R10 | **状态耦合（若选错后端形态）** | 🔴 高 | 若部署"整个 Next 应用容器"当后端，它需要 Postgres/Redis——等于把 BookConv 的数据库也搬上 GEO 机器，隔离彻底失败。必须用无状态 slim 后端规避。 |

> 注：R1/R2/R3 是同驻路线特有的、独居路线（乙）天然不存在的风险；其余为通用加固项。

## 二、对应解决方案（逐项映射 + 加固基线）

### 2.1 消除 R1（OOM 误杀）—— 双层防线
- **cgroup 内存硬上限**：BookConv 后端单元设 `MemoryMax=1.5G`（systemd）或 `docker --memory=1.5g`。Calibre 一旦超界，**在自己的 cgroup 内先被 OOM kill**，绝不会溢出到整机去杀 GEO。
- **OOM 评分保护 GEO**：给 BookConv 后端 `OOMScoreAdjust=800`（更易被杀），给 GEO 关键进程 `OOMScoreAdjust=-500`（受保护）。即使整机 OOM，也优先杀转换任务、保 GEO。

### 2.2 消除 R2（磁盘占满）
- **独立 tmpfs 挂载**：`/opt/bookconv-conversion/data/tmp` 挂 `tmpfs`，`size=1G,noexec`。内存盘，重启自动清空，且被 1GB 天花板锁死，永远写不满根盘。
- **逐任务清理**：转换完成/失败立即 `rm -rf` 临时目录；cron 兜底每 5 分钟扫过期文件。
- **磁盘告警**：根盘使用 >80% 即告警（独立于 GEO 告警路由）。

### 2.3 消除 R3/R6（CPU/网络争用）
- `CPUQuota=80%`（systemd）或 `docker --cpus=1.5`，预留 0.5 核给 GEO 系统进程。
- `IOWeight=50`（低于 GEO 默认 100）降低磁盘 IO 优先级。
- 转换并发锁 1（代码层 `CONVERSION_CONCURRENCY=1` + 进程层单 worker）。

### 2.4 消除 R4（安全爆炸半径）
- **独立非 root 用户** `bookconv-backend`，与 GEO 用户完全分离，home 互不可读。
- 容器 `read-only rootfs` + `cap_drop=ALL` + `no-new-privileges` + seccomp 默认。
- `.env` 只放 `CONVERSION_INTERNAL_SECRET`，**绝不挂载 GEO 的任何密钥/目录**。
- 后端只监听内网/隧道端口，不绑 0.0.0.0 公网。

### 2.5 消除 R5/R7（故障与运维耦合）
- **独立 systemd 单元 / 独立 docker-compose**：`bookconv-conversion.service` 与 GEO 各服务完全分开，重启互不影响。
- 维护窗口依赖 **failover**：重启前 Vercel 侧路由自动切 CloudConvert（见 2.7）。

### 2.6 消除 R8/R9（可观测性与误暴露）
- 独立日志文件 `/opt/bookconv-conversion/logs/`，独立监控面板与告警路由（飞书单独频道）。
- 后端经 **WireGuard / 内网隧道** 与 Vercel 互联；nginx 仅开 GEO 公网站点，BookConv 内部端点不进公网 server block。

### 2.7 消除 R10 + 全站转换单点（P0 failover）
- **后端形态 = 无状态 slim HTTP**（包 `worker/src/converters/calibre.ts`，约 100–200MB），不引 Postgres/Redis。
- **Vercel 侧 `route.ts` 必须补 failover**（既有 P0 项 WP4）：后端转发失败/超时不返回 503，而是回退 CloudConvert；并加熔断（连续失败 N 次后短时跳过后端，避免每次 30–60s 超时）。
- 验收硬指标：**关停后端 → 请求自动走 CloudConvert 不 503**（无此反向验证不得切生产）。

## 三、对 SEO/GEO 的影响论证

### 3.1 迁移的到底是什么
- 迁移的仅是 **转换后端**（Vercel 函数 → HK 机的 server-to-server 调用）。
- BookConv 前端、GEO 官网前端均**不在迁移范围**（前端留 Vercel / GEO 原部署）。
- 转换后端**既不被用户直接访问，也不被搜索引擎爬取**（Google/Linux 不会去抓你的 `/api/convert-internal`）。

### 3.2 逐项判断
| 信号 | 影响 | 结论 |
|------|------|------|
| BookConv.com 自身 SEO | 爬虫只命中 Vercel 前端，后端位置/IP 对爬虫不可见 | **无影响** |
| GEO 官网 SEO（若 GEO 前端也在 HK 机） | 真实杠杆 = 同机资源争用拖慢 GTFB（见 R3） | **隔离后 ≈ 0**（cgroup 已锁 CPU/IO） |
| 地理/IP 定位信号 | BookConv 前端在 Vercel，不随后端变；GEO 站点地理定位保持 HK 不变 | **无影响** |
| GEO（LLM 引用）信号 | LLM 引用取决于内容质量与 citation，与后端位置无关 | **无影响** |
| 间接 UX（转换慢→跳出率） | 仅作用于 bookconv.com，且 failover 兜底 | **可忽略** |

**结论**：隔离到位时，对 SEO/GEO 的影响趋近于零。你要求"单独文件夹 + 完全隔离"恰恰消除了唯一真实的风险项（R3 资源争用），方向完全正确。

### 3.3 一个反例提醒
若把"前端也搬上 HK 机"，欧美用户的 TTFB 会变成真实 SEO/UX 隐患——那才是该避免的。本方案**不迁前端**，与此一致。

## 四、隔离架构落地（单独文件夹 + 六层隔离）

```
HK 2C4G 服务器
├── /opt/geo-*/                      ← GEO 增长系统（独立用户 geo，独立 systemd 单元）
│   ├── website/  growth-backend/  channel-console/  (db/)
│   └── logs/   （独立监控/告警）
│
└── /opt/bookconv-conversion/        ← ★ 单独文件夹，与 GEO 完全隔离
    ├── docker-compose.yml           （仅 slim 后端，无 Postgres/Redis）
    ├── Dockerfile                   （node:22-alpine + calibre + imagemagick + ghostscript + poppler）
    ├── .env                         （仅 CONVERSION_INTERNAL_SECRET）
    ├── data/
    │   └── tmp/                     （tmpfs, size=1G, noexec —— 消除 R2）
    └── logs/                        （独立日志 + 独立飞书告警）
    运行身份：bookconv-backend（非 root，与 geo 互不可读）
    资源边界：MemoryMax=1.5G / CPUQuota=80% / IOWeight=50（消除 R1/R3/R6）
    OOM 保护：OOMScoreAdjust=800（GEO 进程 = -500）
    网络：WireGuard 隧道接 Vercel，内部端点不进公网
```

六层隔离清单（上线前逐条验收）：
1. 文件夹层：`/opt/bookconv-conversion` 独立于 `/opt/geo-*`
2. 用户层：`bookconv-backend` ≠ `geo`，权限隔离
3. 进程层：独立 systemd/docker 单元，重启不互扰
4. 资源层：cgroup MemoryMax / CPUQuota / IOWeight 硬上限
5. 数据层：独立 tmpfs + 独立磁盘配额，不碰根盘
6. 故障层：Vercel 侧 failover → CloudConvert（后端死连不 503）

## 五、后端形态最终建议（锁死选项 B）

- **用选项 B（slim 无状态 HTTP）**，不要选项 A（整个 Next 容器）。
- 理由：选项 A 需 Postgres/Redis → 状态耦合（R10）→ 隔离失败。slim 后端只包 `calibre.ts`，接收 Vercel 经 `CONVERSION_BACKEND_URL` 转发的请求，返回转换后文件，本身无状态、可随时重启。
- `worker/BullMQ` 只暴露 `/health:3001`，**不能直接当 `CONVERSION_BACKEND_URL` 目标**；slim HTTP 需新建一个轻量服务暴露 `/api/convert-internal`，或复用 Next 容器内现有该路由（但后者会把整个 Next 拉上机，违背 slim 原则）。建议**独立 slim 服务**。

## 六、残余风险与回滚

- **残余 R-A**：HK 机整机宕机时，GEO 与 BookConv 后端同死——但 BookConv 靠 failover 转 CloudConvert，影响可控；GEO 自身需有自己的 HA/备份（超出本方案）。
- **残余 R-B**：4GB 在 GEO 业务增长后可能仍偏紧。验收期持续盯 GEO TTFB，若转换跑着时 GEO P95 > 800ms，立即升 4C8G 或把后端迁独立盒（乙路线）。
- **回滚**：`CONVERSION_BACKEND_URL` 置空即全量回 CloudConvert；slim 服务 `systemctl stop bookconv-conversion` 即停，零代码改动。

## 八、正面收益（回应「收益有多少」）

在六层隔离落地的前提下，甲方案是低成本、高回报的选择——核心收益是**零成本打破 CloudConvert 10 credits/天 的结构性硬顶**，顺带把整体可用性从「单点常挂」升级成「双活冗余」。收益成立的前提正是上一轮那份隔离方案被执行；隔离不到位，隐患会反噬把收益吃光。

### 8.1 收益清单（按量级）

1. **打破 402 硬顶（核心，零成本）**：近 6 天 5 天 CloudConvert 触顶 10/天，402 是结构性的。自托管 Calibre 后转换次数不再受 vendor 配额限制，从「10/天 硬顶」变为「日处理量由 2C4G 算力决定」。并发锁 1 下，单次 EPUB→MOBI 几秒到十几秒、PDF 几十秒，保守也到几百/天量级（约 1–2 个数量级提升），且不受付费与否约束。
2. **零边际成本**：HK 机已购（给 GEO 用），放后端不增加开支。对比 Oracle 路线 B（需国际信用卡被卡）与萤光云独立盒（多一笔钱），甲最大优势是花 0 元拿破顶能力。
3. **整体可用性增强（双活冗余）**：现在「只有 CC 且常 402」；加自托管 + failover 后变「HK 机主体 + CC 兜底」，多一层冗余。CC 免费额度留给 Calibre 覆盖不了的格式，比现在稳。
4. **格式与质量可控**：Calibre 覆盖 epub/mobi/azw3/pdf/txt 主力格式，可自定义字体嵌入 / PDF 样式 / Kindle 适配，输出比 CC 免费档排队限流更稳。（覆盖不了全部 25 个 CC 格式 → 白名单：能转走 HK 机，不能转回退 CC。）
5. **隐私加分 + 可观测**：用户文件在自家机器处理不外传（HK 机端补隐私声明 + TTL 清理）；日志 / 耗时 / 失败原因全在自己手里。
6. **为 monetization 铺路**：零成本先跑通架构，盈利后随时升 4C8G 或迁独立盒。

### 8.2 净判断

| 维度 | 隔离到位（执行上轮方案） | 隔离不到位 |
|------|------|------|
| 破顶收益 | ✅ 拿到，零成本 | ✅ 拿到，但… |
| GEO 安全 | ✅ 不受影响 | ❌ OOM / 磁盘 / CPU 反噬 GEO，收益被吃光甚至变负 |
| 总评 | **净正，推荐** | **净负，不如不迁** |

收益是实的，但**绑死在隔离六层上**——用户「单独文件夹 + 完全隔离」的要求正是把收益与隐患剥开，安全拿收益。

### 8.3 诚实保留（未定量）

- 日处理吞吐为粗算、未实测；验收期须用代表文件真压一遍确认。
- 4GB 在 GEO 业务增长后或仍偏紧；转换跑着时 GEO P95 TTFB > 800ms 即升配或切独立盒（乙路线）。回滚只需 `CONVERSION_BACKEND_URL` 置空。
