# 诊断_转换失败_空文件与过小输入_2026-11-02

> 触发：飞书两条红卡告警（Job f3937005 / 729f7eae），时间 2026-11-02T07:03Z，均走 `/api/convert` 同步路径，目标格式 epub。
> 结论先行：**不是系统故障，是用户侧输入错误（空文件 / 过小文件）被误判为系统故障（红卡）**。真正的代码缺陷在同步入口缺少「空/最小体积」守卫。

## 0. TL;DR

| Job | 格式 | 报错 | 输入 | 真因 |
|---|---|---|---|---|
| f3937005 | html→epub | Either fileBuffer or inputFilePath must be provided | 0 B | multipart 上传了 **0 字节 file**，通过入口守卫 → `buffer.toString('base64')===''`（falsy）→ executeConversion 抛该错 |
| 729f7eae | txt→epub | Invalid input file: too small (14 bytes) | 14 B | 14 字节 < 30 字节最小守卫 → executeConversion 抛「too small」；14 字节 ≈ 空 txt |

两条错误串都不命中 alerts.ts 的用户侧规则 → fail-closed 判 `system`（红卡值班）→ **误报**。

**代码缺陷单一来源**：`convertAndStream` 的 multipart 分支只拦「缺失 file / 超大」，**不拦空文件与最小体积**；R2 分支有空文件守卫（`UPLOAD_EMPTY`），multipart 没有 → 两者行为不一致。

## 1. 数据流与逐条根因

同步入口 `POST /api/convert` → `convertAndStream`（`src/lib/convert-handler.ts`）。

**关键事实：该路径永远把 `inputFilePath` 传 `null`**（convert-handler.ts:275-281 的 `runConversion(buffer.toString("base64"), null, ...)`）。所以输入只能经 `fileBuffer` 进入，`buffer` 来源二选一：

| 输入分支 | 现有守卫 | 缺失 |
|---|---|---|
| **R2 `upload_key`**（直传，大文件） | line 186 `buffer.length===0 → 400 UPLOAD_EMPTY`；line 192 超 `MAX_UPLOAD` → 413 | — |
| **multipart `file`**（≤4.5MB） | line 201 `!file → 400`；line 207 `file.size > MAX_FILE_SIZE → 413` | **空文件（0B）与最小体积（<30B）无守卫** |

之后进入 `executeConversion`（`src/lib/conversion.ts`）：
- line 1208-1209：`if (!fileBuffer) throw new Error('Either fileBuffer or inputFilePath must be provided')`
  —— 空 Buffer 的 `toString('base64')` 是 `""`（falsy）→ 命中。
- line 1213-1214：`if (Buffer.byteLength(fileBuffer,'base64') < 30) throw new Error('Invalid input file: too small (N bytes)')`

### Job 1（0 字节 → "Either fileBuffer or inputFilePath must be provided"）
0 字节 multipart `file` 通过 line 201（`file` 存在）与 line 207（未超限）→ `buffer` 长度 0 → base64 = `""` → line 1208 抛出。

**为什么判定是 multipart 而非 R2**：0 字节 R2 对象会在 line 186 就被 `UPLOAD_EMPTY` 直接 `return` 400；该 return 位于 `try` 之外，**不经过 catch（line 282）→ 不会触发 `notifyConversionFailure`**。因此这条「Either fileBuffer…」红卡只可能来自 multipart 分支。

### Job 2（14 字节 → "too small (14 bytes)"）
14 字节输入通过入口守卫 → base64 非空 → 过 line 1208 → 命中 line 1213 `< 30`。14 字节是一个几乎空的 txt，无实际可转换内容。
分支判定：**最可能同为 multipart**（14 字节 `file` 通过 `>MAX` 检查、且缺最小守卫）；理论上 14 字节 R2 对象也能到达此处（非 0、未超 `MAX_UPLOAD`），但 #1 已确定 multipart，两告警相隔 3 秒、同型，判 multipart 最合理。

### 共同根因
边缘入口未校验最小体积/空文件，把「输入是否合法」下放到深层 `executeConversion`，于是产出**面向系统的错误串**而非干净的 400，并被告警层当成系统故障。

## 2. 告警分级判定：**错误**

`classifyAlertSeverity`（alerts.ts:135-143）判据：
1. 先匹配 `USER_SIDE_PATTERNS`（line 115-126）—— 其中含 `'too large'`，但**没有 `'too small'`**；
2. 再 `mapErrorCode()` 是否落入 `USER_SIDE_ERROR_CODES`（DRM/CORRUPT/FILE_TOO_LARGE/VERIFICATION_FAILED）。

两条错误串（`too small`、`Either fileBuffer…`）均不命中 → fail-closed → `system`（红卡、值班）。

**正确分级应为 `user`（灰卡、不值班）。** 空/过小文件与 DRM/损坏/超限同属用户输入可预期错误。当前红卡属误报，会稀释告警通道信噪比——这正是 alerts.ts:80-89 注释所警示、并已为 DRM/损坏做过分级的问题。

## 3. "Local validation (inferred, NOT measured §3.5): passed"：**误导**

该字段是**反推**（convert-handler.ts:303-304）：
```
localValidationInferred = errorCode === 'CORRUPT_INPUT' ? 'failed' : 'passed'
```
两条错误码都不是 `CORRUPT_INPUT` → 标 `passed`。但空/过小输入根本没走到任何实质校验，`passed` 会被误读成「输入已校验干净」。这类场景应为 `unknown`（修复后在边缘即 400、根本进不了 catch，标签自然消失）。

## 4. 修复方案（精确到文件/行）

> ⚠️ **本节 4.2 / 4.3 已被 §8 红队复核推翻，以 §8 为准。**
> 4.1 的方向正确但位置与常量需按 §8 修订（守卫必须在两路输入汇合处，阈值必须共享常量）。

### 4.1 边缘守卫（`src/lib/convert-handler.ts`，取到 `buffer` 后、进入 CloudConvert 缓存/预算与 `runConversion` 之前，约 line 216）
```ts
// 输入体积下限守卫（2026-11-02）：multipart 分支此前只拦「缺失 / 超大」，
// 不拦「空 / 过小」。空文件 → buffer.toString('base64')==='' → 深层
// executeConversion 抛 "Either fileBuffer or inputFilePath must be provided"；
// 1–29 字节 → 抛 "Invalid input file: too small"。二者都被 alerts.ts 误判为
// 系统故障（红卡值班），实为用户输入错误。统一在边缘按 400 拦截。
// 注：R2 分支已单独处理 0 字节（UPLOAD_EMPTY），此处统一兜住 <30 字节。
const MIN_INPUT_BYTES = 30;
if (buffer.length < MIN_INPUT_BYTES) {
  return NextResponse.json(
    buffer.length === 0
      ? { error: "Uploaded file is empty.", code: "UPLOAD_EMPTY" }
      : { error: "File is too small to be a valid document.", code: "INPUT_TOO_SMALL" },
    { status: 400, headers: rateHeaders },
  );
}
```
效果：空/过小输入在**进入 runConversion / 计 CloudConvert credit / 触发告警之前**就被 400 拦截，且与 R2 分支语义统一。对合法用户零行为回归（这些输入原本就是失败）。

### 4.2 告警分级（`src/lib/alerts.ts`，`USER_SIDE_PATTERNS`）
加入 `'too small'`（可再补 `'file is empty'` / `'uploaded file is empty'`），使深层（如队列路径 `queue.ts:298/306`）残留抛出也判灰卡。
> 更规范做法：按项目 §6 纪律新增 `INPUT_TOO_SMALL` 错误码并纳入 `USER_SIDE_ERROR_CODES` 单一事实源，避免再硬编码字面量（新增 error_code 先归类再改共享常量）。

### 4.3 可选
`convert-handler.ts` 的 `localValidationInferred`：空/过小输入标 `unknown` 而非 `passed`。

### 🔴 新发现：自建后端 `convert.tuozhigeo.com` 当时返回 429
两条请求都在**委托自建后端时拿到 429（非 200）**，才回退 CloudConvert；回退后按非法输入失败。**这不是「输入非法」的因，而是同一时刻的第二个异常信号**，需单独跟进：

- 说明：后端 429 不改变「误报系统故障」的结论——后端即使正常（200），这两条非法输入也会在其侧失败并回退，同样走到 CC 失败。

输入确为**自动化脚本（Python-urllib/3.12）发送的真实 0B/14B 载荷**：两次回退分别读到「0 字节」「14 字节」且与告警完全一致，最合理解释是输入本就是 0/14 字节（而非 parse-once 委托消费导致的截断；undici 的 multipart `File` 为内存 Blob、可重复读）。**告警仍属用户侧误报。**

### 下一步建议
1. 修边缘守卫 + 告警分级（见 §4）：这类请求返回干净 400，且不再红卡值班。
2. 查明 `Python-urllib/3.12` 来源 IP（Vercel → Firewall 日志）：确认是自家监控脚本（应改用真实小样或跳过）、还是外部刷量/探测；若是恶意刷量，考虑在 Firewall 加规则。
3. 排查后端 `convert.tuozhigeo.com` 的 429 是否为「共享 egress IP 限流」（会影响全站），必要时调整 `limit_req` 键（按 `X-Forwarded-For` 或内部密钥维度）或放宽阈值。

### 8.2 被推翻的原方案（本节的实际价值）

**R1「改 `alerts.ts` 补 `too small` 能让队列路径也降级灰卡」→ REFUTED。**
`queue.ts` 有自己的一份 `executeConversion`（`:272`）和自己的红卡构造（`:631` 硬编码 🚨 + `template: 'red'`），全程不 import `alerts.ts` 的 `classifyAlertSeverity`。改 `alerts.ts` 对队列路径**零影响**。且 `alerts.ts` 头注释已说明生产走同步路径、worker 不存在。

**R2「补 `too small` 模式本身是有效修复」→ REFUTED（更深一层）。**
`runConversion` 全仓库唯一调用点 = `convert-handler.ts:275`。守卫一旦前置，该签名在同步路径**不可达** ⇒ 新加的模式永远匹配不到 = 死代码，且写不出能触发它的反向用例。按项目纪律「不可验证的判据不得入库」⇒ 改为走**错误码**路径（`mapErrorCode` 与告警分级都能单测，两层都可反向验证）。

**R3「GA4 侧也被这两条污染」→ 部分推翻。**
`conversion_failed` 是**浏览器**埋点（`ToolPageClient.tsx:298`），本次两条是 `Python-urllib/3.12`，**没有任何 GA4 事件**——「这两条污染 GA4」不成立。
但同类真实风险存在：真实浏览器用户传 0B/14B 时，服务端 500 + `INTERNAL_ERROR` 被客户端上报，而 `INTERNAL_ERROR` 不在 `CLIENT_INTERCEPT_CODES` / `QUOTA_CODES` / `INFRA_CODES` 任何集合 ⇒ `ga-inspection` 计入 `engineFailed` ⇒ 日报当引擎失败报（假报警）。这条**必须随本次修复一并处理**。

| **0 字节 txt → epub** | **HTTP 200 + 75,128 字节**（空书，但确实成功） |

**结论：「小于 30 字节 = 无效输入」不成立。** 后端（Calibre）能正常转换极小 txt。
因此 `INPUT_TOO_SMALL` 不是用户输入错误，而是**回退链的能力边界**。

### 9.2 429 的真实根因：并发锁，不是限流

- nginx 侧：`limit_req_zone $binary_remote_addr zone=bookconv_conv rate=10r/s burst=20 nodelay`。
  键是直连对端 IP，即 **Vercel 出口 IP**（`13.221.4.55`），属**共享额度**（潜在风险，但今日峰值仅 3 req/s，远未触限）。
- **决定性反证**：`/var/log/nginx/error.log` 自 11-01 00:00 起为 **0 字节**，无任何 `limiting requests` 记录 ⇒ 今日 429 **无一条**由 `limit_req` 产生。
- 真实来源：`/opt/bookconv-conversion/app/index.js` 用全局布尔 `busy`，**并发=1**，第二个请求**立即**返回 429 `{code:"BACKEND_BUSY"}`，不排队、不等待。
- 现场对齐（access.log，均来自 Vercel egress `13.221.4.55`）：

```
15:03:49  429 (60B)    ← Job f3937005 撞车
15:03:49  429 (60B)    ← 另一并发请求
15:03:49  200 (192,238B)  html→epub 930ms   ← 占住锁的那个
15:03:52  429 (60B)    ← Job 729f7eae 撞车
15:03:52  429 (60B)
15:03:52  200 (158,852B)  html→epub 954ms
```

`conversion.log` 印证两次成功均为 `OK html -> epub`。**Job2（14 字节 txt）本该成功，是撞上别人在跑而被挤出。**

- 今日 backend 请求 29 条：25×200 / **4×429** / 3×500 / 1×422 ⇒ 争用率约 14%。
- 影响：任何两次转换重叠，就有一个请求被推给 CloudConvert（烧免费额度）或失败。这不是用户错误，是**容量瓶颈**。

### 9.3 因此回滚第一稿的体积守卫（代码现状）

| 项 | 第一稿（已回滚） | 第二稿（现行） |

## 10. 红队复核：三项待批准改动的必要性（2026-11-02 16:40，实施前）

纪律：每条先找能推翻它的实测证据；「听起来合理」不作为立项理由。**本节否定 1 项原方案、修正 2 项、并发现 1 项比这三项都严重的缺陷。**

### 10.1 第 1 项「nginx 记录 XFF」→ ❌ 原方案无效，必须改成两段

**原假设**：「Vercel 转发时会透传真实客户端 IP，nginx 记 `$http_x_forwarded_for` 就能回溯。」

**实测（对照实验，非推断）**：在 HK 服务器上启动 `tcpdump -i lo -A tcp port 3001`，再由**服务器自己**（公网 IP = `43.129.176.38`）经 `https://www.bookconv.com/api/convert` 发起一次 html→epub，抓 nginx→node 的明文请求头：

```
POST /api/convert-internal HTTP/1.0
Host: convert.tuozhigeo.com
X-Real-IP: 3.90.42.96          ← Vercel 出口 IP
X-Forwarded-For: 3.90.42.96    ← 同上，真实客户端 43.129.176.38 已丢失
x-vercel-id: hkg1::mssp6-1793608495517-7a4a18c77895
user-agent: node               ← 出站 UA 被改写
```

**结论：真实客户端 IP 在 Vercel 出站时就已经丢了**，nginx 记不记 `$http_x_forwarded_for` 都只能拿到 Vercel egress IP（今日 access.log 里的 `32.200.152.130` 也是 Vercel 的另一个出口 IP）。

**根因**：`conversion-backend-client.ts:96` 的 fetch **只设了 `x-internal-convert` 一个头**（已核对源码），Vercel 出站也不会自动补 XFF。

**有效方案必须两段**（否则做了也没用）：

| 段 | 改动 | 说明 |
|---|---|---|
| ① Vercel 侧 | `route.ts` 从入站 `request.headers` 读真实 IP，经 `delegateToBackend` 以 `x-client-ip` 传出 | 入站 IP 源优先 `x-vercel-forwarded-for`（Vercel 专用、不可伪造）；回退 `x-forwarded-for` 时取**最后一段**（若上游是追加语义，首段可能是伪造值） |
| ② 后端侧 | nginx `log_format` + 记录 `$http_x_client_ip` 与 `$request_time` | 顺带补 `$request_time`：当前 access.log 用默认 combined，**完全没有耗时字段**，容量决策缺基础数据 |

**顺带发现**：`access.log` 无 `$request_time` ⇒ 线上转换耗时分布从未被记录过。这比 IP 更有长期价值（本次容量判断只能靠临时手工实测）。

### 10.2 第 2 项「立即 429 → 有限等待」→ ⚠️ 方向对，但必须排在熔断修复之后

**支持数据（本次实测，HK 直连 127.0.0.1:3001）**：

| 任务 | 纯后端耗时 |
|---|---|
| html 162B → epub | 0.85s |
| html 3.5KB → epub | 0.93s |
| html 16KB → epub | 1.16s |
| html 16KB → **pdf** | 2.57s |

转换耗时集中在 **0.85–2.6s**，故「等 ≤5s」在数学上能吃掉绝大多数短重叠——这个方向是成立的。

**但「提高并发」这条路被实测堵死**：`memory.peak = 474MB`，`MemoryMax=1.2G`。两个并发峰值 ≈ 950MB，余量不足 300MB，大文件可能更高 ⇒ 并发 2 有 OOM 风险。**排队（等待）不增加内存，是当前唯一安全的容量平滑手段。**

**必须先修的排序问题**：`conversion-circuit-breaker.ts` 的 `recordBackendFailure()` **无差别计数**——`delegateToBackend` 在 `res.status !== 200` 时一律计入（`:116`）。即 **429 BACKEND_BUSY 与「后端宕机」同一权重**，3 次即熔断 60s。等待若单独上线，只会把「快速 429」变成「慢速 429」，失败计数照样累积，收益被熔断吃掉。

### 10.3 第 3 项「告警卡透传 delegation 原因」→ ✅ 做，但有实现陷阱

**事实依据（本次误诊的直接原因）**：`delegateToBackend` 返回类型是 `NextResponse | null`，**失败原因在返回时被丢弃**，只 `console.warn` 一行（`:120`）。`convertAndStream` 完全不知道 delegation 发生过，告警卡只能显示最终的 `too small`，于是值班人被引向「用户传错文件」。这是本次诊断走弯路的**唯一**直接原因。

**实现陷阱（必须避开）**：不能用模块级变量传递原因——Serverless 同实例并发请求会互相污染（`alerts.ts` 的 `lastSentAt` 是节流表，语义上允许串；诊断上下文不允许串）。必须走参数：`delegateToBackend` 返回结构化结果 → `route.ts` → `convertAndStream(formData, headers, { uploadKey, delegatedFrom })` → 告警 payload 新增可选字段。

### 10.4 新发现 P0：熔断器把「忙」当「死」（优先级高于上述三项）

| 项 | 内容 |
|---|---|
| 缺陷 | `res.status !== 200` 一律 `recordBackendFailure()` ⇒ 429 BACKEND_BUSY 与 5xx/超时同权；`FAILURE_THRESHOLD=3`、`COOLDOWN_MS=60s` |
| 后果 | 连续 3 次并发争用 ⇒ 熔断开 ⇒ 该实例 **60s 内所有请求绕过后端**，全部压给 CloudConvert（本项目已知额度紧张）+ 每次多 10–30s 延迟 |
| 语义错误 | 熔断的目的是「避免向已死后端反复等 90s 超时」。而 busy 429 **响应极快（60 字节、毫秒级）**，回退 CC 本就是预期降级路径——它不该被当作健康度证据 |
| 今日是否已触发 | **未确认触发**（运气）：15:03:49 与 15:03:52 两波均为 `2×429 + 1×200` 交错，`recordBackendSuccess()` 在 200 时会把 `failures` 归零。但只要出现「连续 3 次 429 无成功插入」就会误开。今日 4 次 429 占 34 条请求的 11.8% |
| 建议修法 | 429（BACKEND_BUSY）不计入 `recordBackendFailure`；改为独立的「容量计数」，仅用于观测/告警，不驱动熔断。5xx / 超时 / 网络错误才计入健康失败 |

### 10.5 红队裁定表

| # | 事项 | 裁定 | 理由（关键证据） |
|---|---|---|---|
| 0 | **熔断：429 不计入健康失败** | ✅ **先做（P0）** | 否则第 2 项的收益被熔断抵消；容量问题会被放大成可用性问题 |
| 1 | nginx 记录 XFF（**原方案**） | ❌ **不做** | 实测只记到 Vercel egress IP，零取证价值 |
| 1′ | 两段式客户端 IP 透传 + `$request_time` | 🟡 **做，但次优先** | 唯一可行取证通道；`$request_time` 有独立价值（当前完全无耗时数据） |

## 12. 限流键实测：全站共用一个桶（2026-11-02 17:2x）

> §11.5 把「`getClientIp` 可能不是真实 IP」列为独立待查项。查完了：**不是「可能」，是确定——而且后果比原设想严重。**

### 12.1 决定性实验（跨客户端共用计数器）

方法：`epub→jpg` 属已知「两头堵」组合，会在取文件前直接 422 并带回限流响应头，**零转换开销、零后端负载**。从两个不同公网出口各发请求，看 `X-RateLimit-Remaining` 是否各自独立。

| 顺序 | 客户端出口 | 结果 |
|---|---|---|
| A | HK 服务器 `43.129.176.38`（IPv4） | `remaining=19` |
| B | 本机 `2401:ce20:7::7`（IPv6） | `remaining=18` |
| C1 | HK 服务器（再次） | `remaining=17` |
| C2 | HK 服务器（再次） | `remaining=16` |

**连续递减、跨 IPv4/IPv6 两个完全不同的客户端共用同一个计数器** ⇒ 限流标识不是客户端 IP。

⚠️ 判据陷阱：`X-RateLimit-Reset` 是 `now + 60s` 算出来的，不是窗口真实到期时刻（`rate-limit.ts` 里 `resetAt = now + windowMs`），**不能拿它判断是否同一窗口**。判同一窗口要靠「计数是否继续递减」。

### 12.2 为什么退化成常量（两个缺陷叠加）

| # | 缺陷 | 代码证据 |
|---|---|---|
| 1 | 生产环境三个分支全部落空 | Next **16.2.10** 的类型层已无 `request.ip`（`node_modules/next/dist/server/web/spec-extension/request.d.ts` 无 `ip?`）；`TRUST_PROXY` 未配置（默认 `false`，仓库里只有博客文案提到该变量，`.env` 无）；App Router 的 `NextRequest` 无 `socket` ⇒ 只能落到 `'unknown'`，Redis 键固定 `ratelimit:ip:unknown` |
| 2 | 即使开 `TRUST_PROXY=true` 也修不好 | 原代码 `if (isTrustedSource(firstIp)) return firstIp;` —— 校验的是**链首（客户端 IP）**，而注释写的是「immediate peer（链尾代理）」。客户端 IP 永远不在可信代理名单里 ⇒ 分支被跳过 ⇒ 仍旧 `'unknown'` |

### 12.3 影响面（比「限流失效」更糟）

不是「限流不起作用」，而是「限流作用在所有人身上」：

| 策略 | 原意 | 实际 |
|---|---|---|
| `convertApi` 20/60s | 每 IP 每分钟 20 次 | **全站**每分钟 20 次 |
| `presignApi` 30/60s | 每 IP 每分钟 30 次 | **全站**每分钟 30 次 |
| `feedback` 5/10min | 每 IP 每 10 分钟 5 次 | **全站**每 10 分钟 5 次 |

两点后果：
1. **可用性**：任何人发 20 次请求，就能让全站转换接口在窗口剩余时间全部 429——零成本 DoS。
2. **误伤**：两个正常用户同时用，各自额度被对方吃掉；`feedback` 5 次/10 分钟最容易先撞上。

### 12.4 伪造防御实测（决定能不能直接采信转发头）

修法依赖「入站转发头可信」。用已有链路验证：`x-client-ip` 会被后端 nginx 记成 `client=`，故发带哨兵值的伪造头，看落盘值。

| 伪造向量 | 后端落盘的 `client=` |
|---|---|
| `X-Forwarded-For: 203.0.113.11` | `43.129.176.38`（真实） |
| `x-real-ip: 203.0.113.22` | `43.129.176.38`（真实） |
| `x-vercel-forwarded-for: 203.0.113.33` | `43.129.176.38`（真实） |

三个向量全部被平台覆盖/追加，**没有一个哨兵值落盘**。XFF 取**最后一段**（最近一跳代理写入）因此是安全的；若取链首则会被客户端自带值污染。

诚实边界：这只证明上述三个向量不可伪造，不等于「对所有头向量不可伪造」。

### 12.8 明确不做

- **不给 `TRUST_PROXY` 加环境变量了事**：缺陷 2 证明即使置 true 也仍旧 `'unknown'`，那只是把假修复留在配置里。
- **不改限流阈值**：桶被共享是标识问题，不是阈值问题。阈值调大只会同时放大 DoS 影响面。
