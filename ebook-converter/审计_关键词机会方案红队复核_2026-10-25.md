## 一、审计结论

原方案的核心主张是「375,000 月搜索量，成本是一个 if 判断」。经代码复核：

**该主张建立在一个生产环境中根本不运行的代码路径上**；即使修正路径，生产侧仍有 4 项硬约束使该功能不可交付。

一句话定性：**这不是零成本机会，而是把一次已复发的全站故障放大 1000 倍的风险动作。**

## 二、致命缺陷（5 项，均为否决级）

### F1 · 论证基于非生产代码路径（方法论错误）

| 项 | 内容 |
|---|---|
| 原主张 | 「`worker/src/index.ts` 图片分支不区分源格式，加一个 if 判断即可」 |
| 代码事实 | `worker/src/index.ts:46` 该分支确实存在 |
| 但 | 该文件是 BullMQ **常驻 Worker** |
| 反证 | `DEPLOYMENT.md:12` — 荧光云 VPS（Calibre 后端）**2026-10-05 到期未续费，实例不可用**<br>`DEPLOYMENT.md:13` — 「Vercel serverless 不支持常驻 Worker，异步队列已降级为同步请求内处理」 |
| 结论 | **生产从不执行 `worker/src/index.ts`**。以其为成本依据，论证无效 |

生产真实路径：`src/lib/conversion.ts:1060 executeConversion()` → 尝试 Calibre → 失败 → `conversion.ts:1224` 降级 CloudConvert。

### F2 · 生产无 ImageMagick，pdf→jpg 只能走已耗尽的 CloudConvert

| 项 | 内容 |
|---|---|
| 反证 | `conversion.ts:976-977` 注释明示：图片输出（jpg/png）**不在**纯 JS 降级范围内，「仍走 CloudConvert（额度可用时）」 |
| 现状 | `诊断_CloudConvert额度耗尽_2026-10-24.md`：免费档 **10 credits/天**，10-01 / 10-17 / 10-24 **三次复发**，该报告出具日仍处故障中 |
| 结论 | 新页面上线即 402。用户点「转换」→ 100% 失败 |

### F3 · 多页输出交付链路不成立（即使额度充足也失败）

| 项 | 内容 |
|---|---|
| 返回结构 | `cloudconvert.ts:366-378` 返回**单个** `base64Data` |
| 校验规则 | `conversion-verifier.ts:166` → `jpg: ['jpg']`；`:115` 只接受单文件 JPEG 魔数 `0xFFD8FF` |
| 冲突 | 多页 PDF→JPG 天然是**多文件**输出。单个 base64 无法承载；若 CC 返回 zip，魔数为 `PK`（`:117`）→ 校验判 fail → 整次转换判失败 |
| 结论 | 交付层需重写（zip 打包 + 多文件下载 UI + verifier 支持），远超「加页面」范畴 |

### F4 · 4MB 上传上限与目标用户需求结构性冲突

| 项 | 内容 |
|---|---|
| 限制 | `file-size-limit.ts:23-24` 默认 **4MB**；`DEPLOYMENT.md:76` Vercel Hobby 对 >4.5MB 请求体返回 413 |
| 冲突 | pdf to jpg 的真实需求方是扫描件、合同、教材、设计稿，典型体积 **10–50MB** |
| 结论 | 即使功能做出来，绝大多数目标用户在上传环节就被拦下。转化率结构性偏低，页面即使有排名也拿不到有效使用 |

### F5 · 60s 硬超时

| 项 | 内容 |
|---|---|
| 限制 | `DEPLOYMENT.md:86` — Hobby 计划 `maxDuration=300s` 被静默忽略，实为 **60s 硬上限** |
| 先例 | `conversion.ts:1126` 注释：「实测 2026-10-18 该路径触发 60s 超时 conversion_failed」 |
| 结论 | 多页 PDF 拆图（上传 + 转换 + 下载）在 60s 内不可靠，页数稍多必超时 |

## 四、若强行上线，风险量化

| 风险 | 传导机制 |
|---|---|
| **全站故障放大** | 301K 词若带来日 100 次转换，10 credits/天 在当天上午即耗尽 → 25 个格式全挂。该传导链已在 `诊断` 文档中实证 |
| **无守卫可拦** | `SUPPORTED_FORMATS` 由 `CONVERSION_MAP` 自动派生（`conversion-map.ts:117`）。加入 `pdf-jpg` 后，`pdf` 与 `jpg` 均已在该集合内 → `convert-handler.ts:91/97` 校验**必然通过**。系统内不存在任何机制阻止这个必然失败的页面被索引 |
| **SEO 负资产** | 一个 100% 失败率的页面被索引，等于给站点叠加「低质」信号。当前已有 18 页卡在 `Discovered-not-indexed`，再叠负信号只会恶化 |
| **上轮逻辑自相矛盾** | 「用入口页给 31 页导权重」不成立：新页自身权重为 0，无法向任何人导权重。正确方向是「先有可用引擎 / 先修索引」 |

## 五、修正后的可行路径（三选一）

### 选项 A · 引擎先行（推荐）

恢复 Calibre 执行能力（重续 VPS，或 CloudConvert 升级付费档），使 `conversion.ts` 的 Calibre 分支重新可用。

- 前提：VPS 成本或 CC 付费额度
- 收益：25 个存量格式**同时**恢复，pdf→jpg 顺带可行
- 顺序：修引擎 → 再上图片页

### 选项 B · 纯 JS 图片渲染

用 `pdfjs-dist` + node-canvas（或 wasm 方案）在服务端把 PDF 页面渲染为图片，绕开 CloudConvert。

- 前提：解决 Vercel 上原生依赖 / wasm 体积问题
- 成本：真实工程量，**不是「一个 if」**
- 风险：冷启动体积、60s 超时、内存限制

### 选项 C · 先修存量，不扩词

在引擎不可用的当下，优先解决 18 页 `Discovered-not-indexed` 与 0 点击问题。

- 成本最低，但无法获得新增流量

**推荐**：A（若预算允许）→ 否则 C。B 可并行评估，但同样不是本轮能落地的。
