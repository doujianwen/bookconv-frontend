# 异步队列方案可行性评估

> 评估时间：2026-10-14
> 背景：Vercel Hobby 60s 硬超时导致转换失败率偏高

---

## 现状分析

### 已有基础设施
- `src/lib/queue.ts`：BullMQ + Redis 队列实现已存在
- `src/lib/redis.ts`：Redis 客户端封装已完成
- `.env.production`：REDIS_URL 占位配置已存在（当前为 dummy 值）

### 当前架构瓶颈
```
用户请求 → Vercel Serverless (60s 硬限) → CloudConvert/Calibre → 响应
              ↑ 超时风险 ↑
```

**核心矛盾**：Vercel Hobby 的 60s 函数超时是硬限制，`maxDuration=300` 配置被静默忽略。

---

## 异步队列方案架构

```
┌─────────────┐     ┌──────────────┐     ┌─────────────┐
│   用户浏览器  │────▶│  API 路由     │────▶│ BullMQ      │
│  (轮询/UI)   │◀────│  (创建Job)    │     │ Queue       │
└─────────────┘     └──────────────┘     └──────┬──────┘
                                                │
                                                ▼
┌─────────────┐     ┌──────────────┐     ┌─────────────┐
│  下载结果    │◀────│  Webhook回调  │◀────│  VPS Worker  │
│  (存储/S3)   │     │  (通知前端)   │     │ (持续运行)   │
└─────────────┘     └──────────────┘     └─────────────┘
```

### 技术栈
| 组件 | 方案 | 成本 |
|------|------|------|
| 队列 | BullMQ (已有) | 免费 |
| Redis | Upstash Free (10MB) 或 VPS 自建 | $0-10/月 |
| Worker | 莹云 VPS (已有 ECS) | $5-10/月 |
| 存储 | S3 (已有) | 按量计费 |

## 收益评估

### 解决的问题
1. ✅ 彻底消除 60s 超时风险
2. ✅ 支持大文件转换（无大小限制）
3. ✅ 更好的用户体验（进度反馈）
4. ✅ 批量转换能力
5. ✅ 失败重试机制

### 当前流量规模
- 日活跃用户：~10-20
- 日转换请求：~20-30
- 成功率：41%（主要问题）

### ROI 分析
- **投入**：6-8 天开发 + $10-20/月运维
- **收益**：成功率提升至 95%+，支持大文件
- **结论**：当前流量规模下 ROI 偏低

---

## 推荐方案（按优先级排序）

### 方案 A：纯 JS 路径扩展（推荐 ⭐⭐⭐）
- **投入**：1-2 天
- **效果**：覆盖 epub→{txt,rtf,fb2,docx,zip} + mobi/azw3→txt
- **优点**：零运维成本，完全免疫超时和 402
- **局限**：仅覆盖文本类格式

### 方案 B：文件大小智能引导（推荐 ⭐⭐）
- **投入**：0.5 天
- **效果**：前端根据格式+大小动态提示
- **优点**：低成本改善用户体验
- **局限**：不解决根本问题

### 方案 C：异步队列（长期规划 ⭐）
- **投入**：6-8 天 + $10-20/月
- **效果**：彻底解决超时问题
- **触发条件**：日活 > 100 或大文件需求明显
