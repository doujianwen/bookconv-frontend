## 案例 1：Google Spam Update 断崖归因与修复

### 背景
- 上线时间：2026-07-26
- 高位期：8/9–8/21，日均印象 160.8
- 低位期：8/22–9/5，日均印象 16.6（−89.7%）
- Google 官方确认 2026-08-18 Spam Update

### 归因过程（四步排查法）

| 轮次 | 假设 | 验证方法 | 结果 |
|---|---|---|---|
| 第一轮 | 内容质量问题 | 审计 112 个 /es 页 | 发现 99 页是英文正文 + lang="es" 矛盾 |
| 第二轮 | 抓取预算被占 | 检查 223 URL 覆盖 | 44% URL 是重复的 /es 伪西语页 |
| 第三轮 | 核心页未重抓 | 检查 lastCrawl 日期 | `/convert/epub-to-mobi` 37 天未重抓 |
| 第四轮 | 结构层问题 | 卡方检验页面类型与零引用关系 | 暗页率 convert 90% / blog 72% / guide 20% |

### 核心结论
- **病灶在结构层不在内容层**：前 3 轮审计全漏
- 223 URL（44% 重复）→ 质量信号稀释 + 抓取预算被占 → 核心页 37 天不重抓 → 旧快照重排
- 首页豁免 86%（快照新）解释了为何改内容无用

### 可复用方法
1. 先穷举维度再验证（内容层 → 结构层 → 技术层）
2. API 字段语义先反例证伪再当判据
3. 维度决定结论——同一数据不同维度得出不同结论

## 案例 8：`curl` 能通、Node 超时 —— 把"有响应"误读成"不通"

### 背景

需要从本机拉取 GSC（Google Search Console）Search Analytics 数据。历史上多次失败，症状各异：
`ETIMEDOUT`、`https.ProxyAgent is not a constructor`、`SSL UNEXPECTED_EOF_WHILE_READING`。
此前结论是「网络不通 / 代理节点有问题」，于是**没有继续推进**。

### 误判链条

| 步 | 观察 | 错误推论 |
|---|---|---|
| 1 | Node 脚本 `ETIMEDOUT` | 网络不通 |
| 2 | 换 Python 也 SSL 报错 | 确认网络问题 |
| 3 | 试手写代理隧道，仍失败 | 环境太复杂，放弃 |

### 转折点：一个被忽略的状态码

直接裸连测试：

```
direct oauth2:  411     ← 411 = Length Required
direct googleapis:  401 ← 401 = Unauthorized
```

**这两个数字是"链路已通"的铁证**：
- `411` = 服务端收到了请求但缺 body → TCP + TLS 全通
- `401` = 已到达 API，只是缺凭证 → 链路完全正常

**只有 `000` 才代表真的没通。**

### 真正的根因

环境里宿主已注入代理：`https_proxy=http://127.0.0.1:8837`。而：

| 客户端 | 自动读 `https_proxy`？ |
|---|---|
| `curl` | ✅ 读 |
| Python `requests` 默认会话 | ✅ 读 |
| **Node `https.request`** | ❌ **不读** |

**⇒ 症状是"curl 通、Node 超时"，问题在客户端，不在网络。**

附加坑：Node 22 没有 `undici.ProxyAgent`；`NODE_USE_ENV_PROXY=1` 要 Node 24+。

### 解法（职责分离）

```js
// Node 只做本地 JWT 签名：纯 crypto，零网络 → 绝不触发代理问题
const signature = jwt.sign(payload, privateKey, { algorithm: 'RS256' });

// HTTP 全部交 curl 子进程：curl 自动读 https_proxy，零配置
import { execFileSync } from 'child_process';
function curlJson({ url, method = 'GET', body, headers = {} }) {
  const args = ['-sS', '--max-time', '60', '-X', method, url];
  for (const [k, v] of Object.entries(headers)) args.push('-H', `${k}: ${v}`);
  if (body) args.push('--data-binary', body);
  return JSON.parse(execFileSync('curl', args, { encoding: 'utf8', maxBuffer: 64e6 }));
}
```

**结果**：一次跑通，数据末日从 9/14 推进到 9/15，还回补了此前缺失的 8/18–8/19。

### 可复用方法

1. **建立"状态码 ≠ 失败"的直觉**：`401 / 404 / 411` 都是好消息。
2. **`curl 通 + 脚本不通` 的组合，永远先怀疑客户端**，不要怀疑网络层。
3. **代理端口禁止硬编码**：本项目实测见过 `7897` → `13425` → `9890` → `8837`，先 `env | grep -i proxy` 现读。
4. **跨语言传输的最小方案是"计算归 A、传输归 curl"**，比研究各语言的代理 API 稳得多。

### 检查清单

```
□ 出错时先看 HTTP 状态码，不是先看错误类型
□ 状态码非 000 → 判定链路通，转查客户端
□ 用 curl 与目标语言各测一次，对比差异
□ 代理地址从 env 现读，不写死
```

## 案例 9：窗口平移 1 天，结论翻号

### 背景

GSC 断崖（8/22 起，−89%）后，日报需要回答一个核心问题：**有没有反弹迹象？**

原日报结论：

> 「近 7 天 vs 前 7 天：**+6.5%**（62→66 印象），微升但仍在低位」

### 真相

同一份数据，同一个"近7天 vs 前7天"，**只把窗口整体平移 1 天**：

| 对比窗口 | 前 | 近 | 变化 |
|---|---:|---:|---:|
| 9/1-9/7 → 9/8-9/14（日报用的） | 62 | 66 | **+6.5%** |
| 9/2-9/8 → 9/9-9/15（平移 1 天） | 68 | 59 | **−13.2%** |
| 9/1-9/8 → 9/9-9/15（8天对7天） | 83 | 59 | **−28.9%** |

**结论符号直接翻转。**

### 为什么这么脆弱

该站日曝光在 3–21 之间跳动，标准差约 5.9，7 天合计只有 60 上下。
**分母是两位数时，任何单日波动都能造出两位数的百分比。**

（注意：9/8 那天恰好 21，9/2 那天恰好 13——这两个点落在窗口的哪一侧，就决定了符号。）

### 补一层检验

| 项 | 值 |
|---|---|
| 前7天 | 均值 9.71，sd 5.88 |
| 近7天 | 均值 8.43，sd 5.88 |
| t 值 | **−0.409** |
| 自由度 | 12 |
| p.05 临界值 | 2.179 |
| 判定 | **不显著** |

### 双重教训

- **第一层（红队最初指出）**：+6.5% 统计不显著。
- **第二层（本次加深）**：问题不止"不显著"——是**方向本身不稳定**。
  红队原话是"不能断言'微升'"，修正后更准确的说法是 **"任何单窗口百分比在此样本量下都不可作结论"**。

### 正确的结论

> **GSC 处于低位平台期，既无显著回升，也无显著继续下滑。断崖延续第 30 天。**

### 可复用方法

1. **窗口由规则固定**：默认「数据末日往前 7 天」vs「再往前 7 天」，末日取最新可得日，不做人工调整。
2. **强制敏感性自查**：产出任何百分比前，把窗口平移 1 天再算一次。**符号翻转 ⇒ 该百分比作废。**
3. **n < 30 必须附检验**；不显著时最高只报"弱信号"。
4. **警惕 window shopping**：反复试窗口直到出现想要的数字，是数据分析里最隐蔽的自欺。

### 检查清单

```
□ 窗口是规则定的还是我挑的？
□ 平移 1 天后符号还一样吗？
□ n 是多少？做了检验吗？
□ 我的表述里有没有"微升/微降"这种抹平不确定性的词？
```

## 案例 10：同一个"日均"，项目内有三个值

### 背景

Bing AI 引用数据。日报写：

> 「Bing AI 引用稳定（日均 **70.4**，累计 3,311）」

### 真相：同一指标三个值

| 值 | 算式 | 分母性质 | 评价 |
|---:|---|---|---|
| **70.4** | 3311 ÷ 47 | 日历天（含 15 个零值天） | 🔴 系统性低估 |
| 103.5 | 3311 ÷ 32 | 活跃天（非零天） | ⚠️ 高估，不能用于规模陈述 |
| **214.6** | 近 7 天总量 ÷ 7 | 近 7 天 | ✅ 权威 |

两处独立错误叠加：

**错误一：算法已被自我否决，但仍被沿用。**
项目内 5 天前（9/13）的红队修正文档白纸黑字写着：

> 🔴 P1：日均计算错误 —— 原报告使用总天数（含零值天）计算日均；正确做法：仅使用活跃天数；**影响：日均被低估约 25–30%**

而 9/18 日报用的 `70.4 = 3311 ÷ 47`，**正是被否决的那个算法**。

**错误二：数据窗口写错。**
该文件 `snapshot_date` 标 `2026-09-13`，但数据实际截至 **9/9**（见案例 11）。

### 后果

| | 原日报 | 修正后 |
|---|---|---|
| 数值 | 70.4 | 214.6 |
| 叙事 | 「稳定/停滞」 | **「加速中，环比 +22.1%」** |

**一个数字口径错误，把"加速"讲成了"停滞"。** 这直接改变了双渠道战略判断。

### 为什么"活跃天均值"也不是答案

活跃天均值天然 ≥ 日历天均值，**其差值反映的是"有多少天是零"，不是"每天效率多高"**。
用它宣布"日均提升"等于说"我们少了几天空转"——这是把**覆盖率伪装成效率**。

### 规范

> **任何"日均"必须标注分母类型。没标分母的日均，一律视为无效指标。**

| 分母类型 | 公式 | 用在哪 | 禁用在哪 |
|---|---|---|---|
| 日历天均值 | 总量 ÷ 窗口总天数 | 对外披露累计规模 | 判断趋势 |
| 活跃天均值 | 总量 ÷ 非零天数 | 内部效率评估 | 规模陈述 |
| **近 7 天日均** ✅ | 近 7 天总量 ÷ 7 | **默认真相口径** | —— |

### 可复用方法

1. **"日均"是个歧义词**，必须追问分母。
2. **项目内同一指标出现多值时，先建对照表**，标注每个值的算式、分母、出处、状态（权威/已废弃）。
3. **纠正要落到产出端**：只在文档里写"用活跃天"不够——`70.4` 这个字段还躺在 JSON 里，早晚被再引用一次（见案例 13）。

### 检查清单

```
□ 这个"日均"的分母是什么？
□ 同一指标在项目内有几个值？哪个是权威？
□ 已废弃的值有没有被标记，还是仍能被动引用？
```

## 案例 11：`snapshot_date` 骗人 —— 文件标的日期 ≠ 数据截止日

### 背景

文件 `bing_analysis_2026-09-13.json`，文件名含 `2026-09-13`，内部字段也写：

```json
{ "snapshot_date": "2026-09-13" }
```

日报据此认定为"9/13 的现状"。

### 真相：数据实际截至 9/9

**文件对自己的描述不可信**，要用数据自身的结构反推：

| 字段 | 值 | 推论 |
|---|---|---|
| `total_days` | 47 | 窗口长度 47 天 |
| `days_active` | 32 | 其中 32 天有数据 → **15 天为零** |
| `citations` | 3311 | 累计总量 |
| `daily_avg` | 70.4 | 验算 3311 ÷ 47 = 70.45 ✅ → 确认用**日历天**分母 |

再用这些数字去匹配真实日期区间 → **反推出实际截止日是 9/9，而非 9/13**。

**后果**：日报用 4 天前的存量描述当下。

### 最强验证：跨文件增量

| 快照 | 累计 citations | 数据实际截止 |
|---|---:|---|
| 9/13 文件 | 3,311 | 9/9 |
| 9/16 文件 | 3,936 | 9/13 |

```
增量 = 3936 − 3311 = 625，落在 9/10–9/13 共 4 天
⇒ 625 ÷ 4 = 156.3 引用/天
```

**156.3 落在 103.5（活跃天）与 214.6（近7天）之间** → 支持"加速"，否定"停滞(70.4)"。

> 📌 **通用原则**：两个文件对同一指标给出不同值时，**不要选"看起来对"的那个**。
> 用增量、比率、字段内部算术关系做交叉验证，**让数据自己说话**。

### 可复用方法

1. **判据优先级**：数据自身结构（`days_active` / `total_days` / 内部验算）> 文件名 > 内嵌 `snapshot_date`。
2. **跨文件增量是最好的交叉验证**，成本极低（两个数一减），信息量极高。
3. **快照必须记录"数据实际截止日"**，不是"导出日"。
4. 推荐命名：`xxx_导出2026-09-18_数据截至2026-09-15.json`。

### 检查清单

```
□ 我用 file.snapshot_date 下结论了吗？
□ 能不能用内部字段反推真实窗口？
□ 有没有第二个文件可以做增量对比？
```

## 案例 12：曝光和引用不能放进同一张表

### 背景

日报的"双渠道对比"表：

| 维度 | Google | Bing 传统 | Bing AI |
|---|---:|---:|---:|
| 日均 | 9.4 imp | 15.3 imp | 70.4 cites |

据此宣布：**「双渠道背离格局确认」**。

### 为什么无效

`impression` 与 `citation` 是**不同量纲、不同采集口径、不同触发条件**的量：
- impression = 搜索结果页展示了我们的链接
- citation = AI 生成答案时把我们的内容作为来源列出

把 9.4 和 70.4 并列，再据此宣布一个方向性结论，**等于用"苹果个数"对比"橘子甜度"**。

而且注意：**这张表本身连单位都没统一**（前两列是 imp，第三列是 cites），却直接推出了"背离"。

### 解法：归一化为变化率

$VI_{ch} = \dfrac{\bar{V}_{recent7} - \bar{V}_{prev7}}{\bar{V}_{prev7}} \times 100\%$

只比**相对自身基线的变化率**，量纲自动抵消。

| 渠道 | VI | 符号 | 过 20% 门槛？ |
|---|---:|---|---|
| Google | −13.2% | 负 | ❌ |
| Bing AI | +22.1% | 正 | ✅ |

### "背离"的三条件（须同时满足）

1. 两渠道 VI **符号相反**；
2. 两渠道 VI **均 ≥ 20%**（各自都构成信号）；
3. 两渠道数据末日相差 **≤ 3 天**。

**本案**：符号相反 ✅，但 Google 侧未过门槛 ❌
⇒ **只能称「不对称（asymmetric）」，不得称「背离」。**

### 信号门槛表

| \|VI\| | 判定 | 允许的表述 |
|---|---|---|---|
| < 10% | 🚫 无信号 | "持平/波动"（**禁止**"上升""微升"） |
| 10–20% | ⚠️ 弱信号 | "可能变化" + "需继续观察" |
| ≥ 20% | ✅ 信号成立 | 可作结论，附检验 |

### 可复用方法

1. **跨渠道对比一律用变化率**，不用绝对值。
2. **给百分比设门槛**，避免把噪声叙述成趋势。
3. **给"背离"设前置条件**，防止用强词描述弱证据。
4. **术语降级机制**：不满足条件就用更弱的词（不对称 / 差异 / 待观察），不要为了叙事流畅而升级措辞。

### 检查清单

```
□ 我对比的两列，单位一样吗？
□ 用的是绝对值还是变化率？
□ 过门槛了吗？
□ 说"背离"前，三条件逐条核过了吗？
```

## 案例 13：已否决的算法会复活

### 背景

这是本篇**最有长期价值**的一条，因为它不是一次性错误，而是**系统性故障模式**。

时间线：

| 日期 | 事件 |
|---|---|
| 9/13 | 红队修正文档**明确否决**了"总量 ÷ 日历天"算法，改为"÷ 活跃天"，并量化影响（低估 25–30%） |
| 9/16 | 基于新口径产出分析，权威值定为 **214.6/天**，写入 `optimization-standards-v2`（现行标准文档） |
| **9/18** | **日报又用了 70.4** —— 即 9/13 被否决的那个算法 |

**五天之内，同一个错误原样复发。**

### 为什么会复发

因为纠正只落在了**文档层**，没有落在**产出层**：

| 层 | 状态 |
|---|---|
| 红队文档 | ✅ 已写明"用活跃天" |
| 标准文档 | ✅ 已更新为 214.6 |
| **产出 `70.4` 的那个 JSON 文件** | ❌ **字段还在，值还是 70.4，仍可被 `require` 引用** |

**分析师的注意力在文档上，而脚本读的是文件。** 两者一分叉，错误就复活。

更深一层：`daily_avg` 这个名字**没有暴露口径**。任何人看到 `daily_avg: 70.4` 都会默认它是对的——
**问题不是"人记性不好"，是字段本身没有自证清白的能力。**

### 解法：让错误无处可藏

**1. 产出端不再产出歧义字段。**

```js
// ❌ 旧：名字不表达口径，谁读谁错
{ daily_avg: 70.4 }

// ✅ 新：口径写进字段名，误用即显形
{
  daily_avg_calendar: 70.4,      // 3311/47，含零值天，禁止用于趋势
  daily_avg_active: 103.5,       // 3311/32，活跃天
  daily_avg_recent7: 214.6,      // 近7天，权威口径
  authority: "daily_avg_recent7" // 显式声明哪个是权威
}
```

**2. 权威源唯一化。** 同一指标只留一个权威出处，其余全部标注 `deprecated: true` + `supersededBy`。

**3. 加检查清单**（写入分析 SOP，每次取数后过一遍）。

### 更普遍的教训

> **纠正的终点不是"文档改好了"，而是"错误的值不可能再被取到"。**

这条规则适用于所有"发现声明≠实现"的场景：
- 内容层写了新文案 → 旧文案还在数据库里，早晚被渲染
- 定价页改了权益 → `PLANS` 常量还在，早晚被引用
- 修了算法 → 旧口径字段还在，早晚被读

**判据：问"这个错误的值现在还能从哪里取到？"能取到 = 没修完。**

### 检查清单

```
□ 纠正后，旧值还能被引用吗？
□ 字段名是否暴露了口径？
□ 有没有显式的 authority 声明？
□ 修复是否落在了"产出端"，而不只是"文档端"？
```

## 案例 14：用纯 Python 生成多源对比曲线图

### 背景

日报里需要一张图展示 Google GSC、Bing AI、Bing Web 三个渠道的每日趋势。

**不能用现成工具的原因**：
- Google Sheets / Excel：CSV 来自不同来源，字段名不统一
- Chart.js / D3：需要写 JS、部署，对一次性分析过度工程
- BI 工具（Metabase / Superset）：太重，不适合"单文件输出"

**解法**：用标准库（csv + datetime），输出内联 SVG。零依赖，直接浏览器打开。

### 输入源（三份 CSV）

| 数据源 | 文件示例 | 关键字段 |
|---|---|---|
| GSC 日期报告 | `gsc-2026-09-18-extracted/*.csv` | `日期,展示` |
| Bing AI OverviewStats | `AIPerformanceOverviewStats_*.csv` | `日期,Citations` |
| Bing Web SearchPerformanceOverview | `SearchPerformanceOverview_All_*.csv` | `日期,印象数` |

**陷阱**：
1. **文件名是乱码/英文，但 header 是中文** → 不能靠文件名判断，必须扫 header
2. **日期格式不统一**：GSC 用 `2026-09-18`，Bing 用 `2026/9/18 12:00:00`
3. **Bing CSV 是 BOM 编码** → 用 `encoding='utf-8-sig'`

### 核心代码

```python
import csv
import os
from datetime import datetime

# ── 1. 自动找 GSC 日期报告（header 含"日期"）────────────────
gsc_dir = r'C:/Users/29537/Downloads/gsc-2026-09-18-extracted'
gsc_file = None
for f in os.listdir(gsc_dir):
    fp = os.path.join(gsc_dir, f)
    if os.path.isfile(fp) and f.endswith('.csv'):
        with open(fp, 'r', encoding='utf-8') as fh:
            if '日期' in fh.readline():  # 只读第一行 header
                gsc_file = fp
                break

# ── 2. 加载三份数据 ──────────────────────────────────────────
# GSC: 日期→展示
gsc_data = {}
with open(gsc_file, 'r', encoding='utf-8') as f:
    for row in csv.DictReader(f):
        gsc_data[row['日期']] = int(row['展示'] or 0)

# Bing AI: 日期→Citations（日期格式 2026/9/18 → 标准化）
bing_ai_data = {}
with open(r'C:/Users/29537/Downloads/.../AIPerformanceOverviewStats_*.csv',
          'r', encoding='utf-8-sig') as f:
    for row in csv.DictReader(f):
        date = datetime.strptime(row['日期'].split()[0], '%Y/%m/%d').strftime('%Y-%m-%d')
        bing_ai_data[date] = int(row['Citations'])

# Bing Web: 日期→印象数
bing_web_data = {}
with open(r'C:/Users/29537/Downloads/.../SearchPerformanceOverview_All_*.csv',
          'r', encoding='utf-8-sig') as f:
    for row in csv.DictReader(f):
        date = datetime.strptime(row['日期'].split()[0], '%Y/%m/%d').strftime('%Y-%m-%d')
        bing_web_data[date] = int(row['印象数'] or 0)

# ── 3. 统一时间轴 ────────────────────────────────────────────
all_dates = sorted(set(gsc_data) | set(bing_ai_data) | set(bing_web_data))
max_val = max(*gsc_data.values(), *bing_ai_data.values(), *bing_web_data.values())
y_max = int(max_val * 1.1)  # 留 10% 上边距

# ── 4. 生成 SVG ─────────────────────────────────────────────
WIDTH, HEIGHT = 900, 450
ML, MR, MT, MB = 60, 50, 50, 60
CW, CH = WIDTH - ML - MR, HEIGHT - MT - MB

date_idx = {d: i for i, d in enumerate(all_dates)}
x_step = CW / max(len(all_dates) - 1, 1)

def pts(data, color, name):
    """生成 polyline 坐标字符串 + legend 行"""
    parts = []
    for date, val in data.items():
        if date in date_idx:
            x = ML + date_idx[date] * x_step
            y = MT + CH - (val / y_max) * CH
            parts.append(f"{x:.1f},{y:.1f}")
    return ' '.join(parts)

svg = [f'<svg viewBox="0 0 {WIDTH} {HEIGHT}" font-family="system-ui,sans-serif">']
svg.append(f'<rect width="{WIDTH}" height="{HEIGHT}" fill="#fafafa"/>')

# 标题
svg.append(f'<text x="{WIDTH//2}" y="30" text-anchor="middle" '
           f'font-size="16" font-weight="bold" fill="#1f2937">Bing vs Google — Daily Trend</text>')
svg.append(f'<text x="{WIDTH//2}" y="48" text-anchor="middle" '
           f'font-size="12" fill="#6b7280">Google 展示(红) · Bing AI 引用(绿) · Bing Web 展示(蓝)</text>')

# 网格 + Y 轴刻度
for i in range(6):
    y = MT + (CH / 5) * i
    val = y_max - (y_max / 5) * i
    svg.append(f'<line x1="{ML}" y1="{y:.1f}" x2="{WIDTH-MR}" y2="{y:.1f}" '
               f'stroke="#e5e7eb" stroke-width="1"/>')
    svg.append(f'<text x="{ML-5}" y="{y:.1f}" text-anchor="end" '
               f'font-size="10" fill="#6b7280">{int(val)}</text>')

# 断崖标记线（8/23）
if '2026-08-23' in date_idx:
    x = ML + date_idx['2026-08-23'] * x_step
    svg.append(f'<line x1="{x:.1f}" y1="{MT}" x2="{x:.1f}" y2="{MT+CH}" '
               f'stroke="#f97316" stroke-width="2" stroke-dasharray="5,5"/>')
    svg.append(f'<text x="{x:.1f}" y="{MT-8}" text-anchor="middle" '
               f'font-size="10" fill="#f97316">断崖 8/23</text>')

# 三条曲线
for data, color, label in [
    (gsc_data, '#dc2626', 'Google 展示'),
    (bing_ai_data, '#16a34a', 'Bing AI 引用'),
    (bing_web_data, '#2563eb', 'Bing Web 展示'),
]:
    p = pts(data, color, label)
    if p:
        svg.append(f'<polyline points="{p}" fill="none" stroke="{color}" '
                   f'stroke-width="2" stroke-linejoin="round"/>')
        # 非零点打点
        for date, val in data.items():
            if date in date_idx and val > 0:
                x = ML + date_idx[date] * x_step
                y = MT + CH - (val / y_max) * CH
                svg.append(f'<circle cx="{x:.1f}" cy="{y:.1f}" r="2" fill="{color}"/>')

# 图例
ly = MT + 10
for label, color in [('Google 展示', '#dc2626'), ('Bing AI 引用', '#16a34a'), ('Bing Web 展示', '#2563eb')]:
    svg.append(f'<line x1="{ML}" y1="{ly}" x2="{ML+20}" y2="{ly}" stroke="{color}" stroke-width="2"/>')
    svg.append(f'<text x="{ML+25}" y="{ly+4}" font-size="11" fill="#374151">{label}</text>')
    ly += 18

# X 轴日期标签（每 7 天一个）
for i, d in enumerate(all_dates):
    if i % 7 == 0:
        x = ML + i * x_step
        svg.append(f'<text x="{x:.1f}" y="{HEIGHT-10}" text-anchor="middle" '
                   f'font-size="10" fill="#6b7280">{d[5:]}</text>')  # 只显示 MM-DD

svg.append('</svg>')

with open(r'E:/一人公司/电子书格式转换站/ebook-converter/数据分析/Bing-Google非对称曲线_2026-09-18.svg',
          'w', encoding='utf-8') as f:
    f.write('\n'.join(svg))

print(f"✅ 生成完成：GSC={len(gsc_data)}条 Bing AI={len(bing_ai_data)}条 Bing Web={len(bing_web_data)}条")
print(f"   日期范围：{all_dates[0]} ~ {all_dates[-1]}")
print(f"   Y 轴最大值：{y_max}")
```

### 关键设计决策

| 决策 | 原因 |
|---|---|
| 用 **标准库**（csv/datetime），不装包 | 分析脚本应零依赖，任何人能直接跑 |
| **自动扫 header 找 GSC 文件** | 文件名是乱码（`https___www.bookconv.com_-Performance-on-Search-2026-08-10 (1)`），不能靠 glob |
| **日期统一标准化为 `YYYY-MM-DD`** | 三份 CSV 格式不同，必须归一化才能合并时间轴 |
| **Y 轴最大值 = max × 1.1** | 留 10% 上边距，避免最高点贴边 |
| **断崖标记线** | 一眼看出 Google 断崖点 8/23，与 Bing 无断崖形成对比 |
| **SVG 而非 PNG** | 无损缩放、可编辑、文件小、可直接嵌入文档 |

## 案例 15：双渠道交叉分析的工作流程

### 为什么需要交叉分析

单一渠道的数据只能回答「这个渠道怎么样」，**交叉分析才能回答「是哪个渠道的问题」**。

BookConv.com 的经典问题：Google 断崖了，是全站问题还是 Google 专属问题？

**单看 Google**：→ 全站惩罚（恐慌）
**单看 Bing AI**：→ 没事（乐观）
**两者交叉**：→ Google 单方面重排，Bing 不受影响（冷静）

### 交叉分析的三道门槛

```
门槛 1：数据截止日是否对齐？
  → 不等末日就对比，是比苹果和橘子
  → BookConv 案例：GSC 截至 9/15，Bing AI 截至 9/16，相差 1 天 ✅ 可对比

门槛 2：指标是否可比？
  → impression vs citation = 不可比（量纲不同）
  → 必须归一化为变化率（VI）才能跨渠道对比

门槛 3：变化率是否过信号门槛？
  → VI < 10% = 无信号，不能说话
  → 10% ≤ |VI| < 20% = 弱信号，只能说"可能"
  → |VI| ≥ 20% = 信号成立，可作结论
```

### BookConv.com 的交叉分析结论树

```
Google VI = -13.2%（🟡 弱信号，符号负）
Bing AI   VI = +58.8%（✅ 信号，符号正）
Bing Web  VI = +53.7%（✅ 信号，符号正）

三条件检验：
  ① 符号相反？ → Google(-) vs Bing(+): ✅
  ② 双方均 ≥20%？ → Google 仅 13.2% < 20%: ❌
  ③ 末日相差 ≤3 天？ → 9/15 vs 9/16 = 1 天: ✅

结论：背离不成立 → 叫「不对称」
解释：Google 处于断崖后的低位平台（7v7 测不出断崖），
      Bing 按自身节奏爬坡（未受 Google spam update 影响）
```

### 交叉分析检查清单

```
□ 每个渠道的数据末日已确认（文件名 ≠ 数据截止日）
□ 指标已归一化为变化率（VI），不是绝对值对比
□ VI 三条件已逐条检验（符号 / 门槛 / 末日差）
□ 结论措辞符合实际证据等级（不对称 ≠ 背离）
□ 断崖类历史事件用事件窗口单独描述，不与 VI 混用
```

## 案例 16：术语降级机制 —— 背离 vs 不对称

### 为什么术语很重要

在数据分析里，**一个词的准确度决定结论的重量**：

| 术语 | 触发条件 | 允许的行动 |
|---|---|---|
| **背离（Divergence）** | 三条件全满足 | 强结论，可指导战略调整 |
| **不对称（Asymmetric）** | 仅部分条件满足 | 弱结论，需持续观察 |
| **无差异** | 双方均无信号 | 无行动，维持现状 |

### BookConv.com 的术语纠错过程

```
初稿结论："双渠道背离格局确认"
         ↓ （红队挑战：Google VI=-13.2% < 20% 门槛）
修正结论："不对称格局确认，非背离"
         ↓ （VI v1.0 正式定义）
现行表述："Google 单方面重排，Bing 维持原样并按自身节奏爬坡"
```

### 术语降级表（教学用）

```
证据强度：★★★★★
    │
    ├─ 三条件全满足 → 「背离」→ 战略级行动
    │
    ├─ 两条件满足   → 「不对称」→ 战术级关注
    │
    ├─ 一条件满足   → 「差异待观察」→ 维持监控
    │
    └─ 零条件满足   → 「无显著差异」→ 无行动

↓ 每一次降级都要明确标注「XX 条件不满足」
```

### 检查清单

```
□ 我用的词是「背离」还是「不对称」？
□ 如果是「背离」，三条件是否逐条通过？
□ 如果不满足，是否降级到了更弱的词？
□ 结论里的措辞是否配得上证据强度？
```

## 教学结构建议

| 阶段 | 案例范围 | 教学目标 | 配套产物 |
