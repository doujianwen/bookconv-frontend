## B 组 · 页面看着正常，但产品根本交付不了

### B1 4MB 上限把三个页面变成死页 `[E]` ★ 最高价值

上限来自 Vercel Hobby 档 4.5MB edge 413，写死在 `src/lib/file-size-limit.ts`。

| 页面 | 真实文件大小 | 4MB 下结果 | Ahrefs 机会 |
| --- | --- | --- | --- |
| `djvu-to-pdf` | DJVU 扫描件 10–100MB | 必然失败 | 5.9K/mo，KD 8 |
| `cbr-to-pdf` | 漫画 50–200MB | 必然失败 | 长尾 |
| `pdf-to-epub` | 扫描 PDF 10–50MB | 大部分失败 | 6.8K/mo，KD 8 |

`djvu-to-pdf` 正文自己写着「超过 4MB 请用 djvulibre 桌面版」——页面在主动送客。

- [x] 代码实现：R2 预签名直传（`src/lib/upload-presign.ts` + `/api/upload/presign`）
- [ ] **R2 桶 CORS 加 PUT 规则**（不做则浏览器 PUT 被拦，功能不可用）
- [ ] R2 `uploads/` 前缀加 1 天生命周期规则（清理失败路径的孤儿对象）
- [ ] 上线后验证 20MB DJVU 可完成转换
- [ ] `djvu-to-pdf` 正文里「用 djvulibre」的引导改写（现在有了大文件能力）

**附带发现**：Pro 的「50MB 大文件」卖点此前**未实现**（`MAX_FILE_SIZE_MB` 是全局 env，不按 plan 区分）。本次改动后单文件路径才真正兑现。

- [ ] 301 到 `/convert/epub-to-pdf`（LRF 是 Sony 格式，搜索量极小，不值得补页）

## C 组 · 页面看着正常，但配置互相打架

### C1 `lit-to-epub` 的西语版被自己的 301 规则杀掉 `[E]`

三份配置各说各话：

| 位置 | 说法 |
| --- | --- |
| `middleware.ts:32` | `/convert/lit-to-epub` → 301 到 `/blog/why-convert-lit-to-epub` |
| `es-routes.ts:43` | `lit-to-epub` 在 `ESP_CONVERT_SLUGS` 里（3 篇） |
| `lit-to-epub.ts` | 有完整 `export const es` 西语块 |
| `sitemap.ts:216` | 用同名局部变量硬编码 2 个，遮蔽第 7 行的单一源 import |

实测：`/es/convert/lit-to-epub` → 301，西语译文永远不会渲染。而 `lit→epub` 是 Ahrefs 报告里月搜索量最大的词（10.8K/mo，KD=0）。

- [ ] 决定：要么放开 301（保留西语版），要么从 `ESP_CONVERT_SLUGS` 移除
- [ ] `sitemap.ts` 改为 `import { ESP_CONVERT_SLUGS }`，消除同名变量遮蔽

**危险点**：当前是「两个错抵消成一个对」（sitemap 硬编码 2 恰好避开 301 页）。若有人"修正"成 import，会把 301 页写进 sitemap，情况更糟。

### C2 convert 标题缺 "Online" 29/31 `[E]`

项目自订「分工契约」（`CANNIBALIZATION_REPORT` §3）要求 convert title 含 `Online`，实测仅 2/31 含。

- [ ] 补 29 页标题

**注意**：pos>30 时 CTR 无对象，这是"排名进前 20 后的预备动作"，不是当前杠杆。优先级低于 A1/B1。

## 排序建议

1. **R2 预签名直传收尾**（CORS + 生命周期规则 + 验证）—— 解掉 4MB，救活三个页，同时给 Pro 一个真卖点
2. **移动端上传区**（流量已存在，纯站内）
3. **lit-to-epub 三处配置对齐**（一行改动，救一个 10.8K/mo 的词）
4. **epub-to-lrf 加 301**（一分钟）
5. **Online 属性补 29 页**（预备动作）

## 附：本次诊断对我上一轮建议的修正

上一轮建议「换战场到 djvu/chm/cbr/cbz」，但**没检查产品能不能交付**。最肥的 djvu→pdf 恰恰被 4MB 卡死。
