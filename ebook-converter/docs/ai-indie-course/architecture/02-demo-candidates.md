# 实战演示「最小可上线产物」候选评估

> 用途：专家团现场重跑 6 阶段流程并录制的对象。
> 评估基准：真实仓库现状（见 `00-fact-check.md`），不做乐观假设。
> 核心约束：产物必须**同时满足**——(a) 6 个 Phase 全覆盖、(b) 录制过程可控不翻车、(c) 真实上线且效果可测量。

---

## 候选 ①：零痛点长尾页面批量生成模块

### 建议收敛后的具体形态
不做「LLM 批量生成文案页」，改做**「转换兼容性实测报告页生成器」**：
用仓库里**已经存在**的 `verifyConversion()` 真实跑一批格式对，把机器实测结果（是否丢图 / 是否丢目录 / 文件体积变化 / 失败原因）沉淀成每页独有的数据，再走现有内容系统发布。

### 技术可行性：高
- 复用 `src/lib/conversion-verifier.ts:162 verifyConversion()`（已接线，非新建）
- 复用 `src/lib/queue.ts` 批量跑转换
- 复用 `src/data/content/index.ts` 的 `import * as X` + Map 注册表模式，新增平行的 `COMPAT_MAP`
- 复用 `src/app/sitemap.ts` 的 `Object.keys(MAP)` 派生逻辑，新增一段循环即可

### 依赖
| 依赖 | 状态 |
|------|------|
| Calibre 转换管线 | 已有 |
| BullMQ + Redis | 已有（`REDIS_URL` 需就绪） |
| 测试用电子书样本 | 需准备，`tests/fixtures/` 已有基础 |
| 新增第三方服务 | **无** |

### 与现有架构契合度：★★★★★
是唯一一个**四个核心资产全部命中**的候选：App Router 动态路由、单源数据 + index 注册、SEO 自动派生、Vercel 部署。新增代码基本是「照着 `content/` 抄一份 `compat/`」，教学上等于把第 9 章的模式当场再跑一遍。

### 6 阶段覆盖度：6/6
需求（从 GSC 真实 query 选格式对）→ Spec（数据 schema + openapi）→ 设计（报告卡片组件）→ 开发（生成脚本 + 新路由）→ 测试（快照 + E2E）→ 增长（sitemap 派生 + GSC 测量），深度报告还可挂 Pro 门禁打通付费。

### 不可行警告
1. **Google「大规模内容滥用」政策（2024-03 起）**——如果只是 LLM 洗稿批量铺页，属于明确打击对象，可能连累主站整体权重。**这是本候选最大的风险，且不可通过技术手段绕过。**
   - 缓解：每页必须承载**机器实测产生的独有数据**，不是文字改写；上线量设硬上限（首批 ≤ 30 页）；发布前设人工审核闸门。
2. **实测数据要真跑转换**——需要样本书 + 机器时间，不是纯前端活。若样本准备不足会退化成假数据，直接触发风险 1。
3. **样本版权**——必须用公共领域书目（如 Project Gutenberg），不能拿受版权保护的书做实测样本。

### 技术可行性：中
管线本身已有（`conversion.ts`、`queue.ts` 661 行、`cloudconvert.ts` 207 行），但这恰恰意味着**改造点在系统最深处**。

### 依赖
| 依赖 | 状态 |
|------|------|
| Calibre worker 容器 | 已有（`worker/`、`docker-compose.yml`） |
| Redis / BullMQ | 已有，需 `REDIS_URL` |
| R2 / S3 | 已有 |
| CloudConvert 配额 | 外部付费服务 |
| LLM API | **新增**，按次计费 |

### 与现有架构契合度：★★★☆☆
契合后端，但**几乎不碰 SEO 派生与内容系统**——课程最有价值的那套资产用不上。

### 6 阶段覆盖度：4/6
UI/UX 只有一个上传框，设计阶段没什么可讲；增长/SEO 阶段基本空白。

### 不可行警告
1. **录制翻车概率最高**。仓库里有一份真实事故记录 `诊断_转换管线生产故障_2026-08-04.md`——这条链路在生产环境已经炸过。录课时长任务失败、超时、worker 掉线都会直接毁掉一条录制。
2. **Vercel 函数执行时长限制**——长转换任务本来就跑不进 serverless，这也是项目当初要单独拆 worker + Docker 的原因。演示时需要额外起本地/远端 worker，录制环境复杂度陡增。
3. **成本不可控**——LLM 按次 + CloudConvert 按次，反复重录会真实烧钱。
4. **调试时间不可预估**，与「课程排期」直接冲突。

## 推荐结论

### 主线选 ①（转换兼容性实测报告页生成器）

四条理由：

1. **唯一 6/6 覆盖 6 个 Phase 的候选。** 课程卖的是完整方法论，主线产物必须能把 6 个阶段都走一遍。② 和 ③ 分别缺 2 个和 3 个阶段，主线用它们就得靠别的例子补，学员的连贯感会断。

2. **它把 bookconv 最值钱的资产讲透了。** 单源数据 + index 注册 + sitemap 自动派生这套模式，是这个项目真正可迁移到任何独立开发项目的东西。候选 ① 等于让学员**照着这个模式再造一次**——学完就能用。② 和 ③ 完全绕开了它。

3. **录制可控。** 全程纯静态生成 + 类型检查 + 构建，没有长任务、没有外部 API 计费、没有 worker 掉线。② 那条链路生产环境已经炸过一次（有事故文档为证），拿它当主线是在拿课程排期赌运气。

4. **效果能被真实测量。** 上线后进 GSC 看收录和曝光，Phase 6「增长与数据」才有真东西可讲，而不是空谈。

### 但必须带着这个约束做

候选 ① 唯一的死穴是 Google 的规模化内容滥用政策。**破解方式是「每页承载机器实测出来的独有数据」，而不是让 LLM 写 300 篇相似文章。** 仓库里 `verifyConversion()` 已经能产出这种数据，这是别人抄不走的原始素材。

这一点本身就是极好的一课：**教学员在什么地方该用 AI（写代码、写生成器），什么地方绝不能用 AI（批量生产内容骗收录）。** 建议在第 15 章专门讲这条红线。

首批发布量卡在 30 页以内，配人工审核闸门，观察 GSC 两周再决定是否扩量。

### 补充建议：③ 的 CLI 版本作为 Phase 4 的加餐小节

不进主线，但可以做一个 20 分钟的独立小节。理由：npm 发布是即时的，能让学员在「部署」之外多见一种交付形态，且 `file-type` 依赖仓库里已有，成本极低。**浏览器插件方案直接排除**，审核周期不可控。

### ② 的处置：降级为讲解素材，不做演示产物

`queue.ts` / `conversion.ts` / `cloudconvert.ts` 这套代码本身很值得讲——重试、降级、幂等、事故复盘都是好内容。建议在第 10 章和第 14 章**作为「读别人的代码」素材**出现，而不是让学员跟着从零重建。
