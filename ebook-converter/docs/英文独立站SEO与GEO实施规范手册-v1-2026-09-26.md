# 第零章 手册使用说明

## 0.1 本手册解决什么问题

英文工具站/内容站冷启动后普遍会遇到三类问题：**排名长期在 50–80 名徘徊、AI 引擎里查无此站、改了半天但部署根本没生效**。bookconv.com 上线 62 天的完整日志，恰好把这三类问题全部踩了一遍。

本手册把「踩过的坑 + 验证过的做法」固化为可执行规范，回答六个问题：

1. 一个上线两个月的新站，SEO 现状怎么诊断？关键问题有哪些？
2. 关键词怎么分层、内容怎么写才能同时被 Google 和 AI 引擎接受？
3. 技术 SEO 有哪些**必须做**和**绝对不能做**的动作？
4. GEO（生成式引擎优化）的核心原则是什么，具体怎么落地？
5. 资源有限时，先做什么、后做什么？
6. 用什么指标衡量效果，怎么避免被假数据骗？

# 第一章 SEO 现状诊断与关键问题

## 1.1 三阶段演进（62 天完整时间线）

把日志按形态切成三段，是理解这个站的关键。**每一段的"成功"和"失败"含义完全不同。**

### 阶段一：爬坡期（7/26 – 8/21）——新站评估期的自然增长

| 指标 | 起点 | 终点 | 变化 |
|------|------|------|------|
| 日均展示 | 6 天累计 36 | 157.4/天 | 持续爬坡 |
| 累计有排名词 | 73（8/6） | 379（8/24） | +419% |
| 窗口展示（累计） | 469（8/9） | 2,117（8/21） | +351% |
| 平均排名 | ~58 | ~53 | 缓慢改善 |
| 点击 | 0 | 1（8/18 首次点击） | — |

**形态特征**：三周持续爬坡（14.8 → 115.0 → 157.4），不是"稳定基线"。

> 🔴 **最重要的方法论教训**：8 月底复盘时曾把 157.4 当作"基线"，得出"断崖 -85%"的结论。**正确的基线是"爬坡曲线"本身**——157 是顶点，不是基线。任何"跌幅百分比"的分子分母，都必须先确认基线是不是被裁剪出来的。

### 阶段二：断崖期（8/21 → 8/22）——算法与结构性问题叠加

| 口径 | 数值 |
|------|------|
| 高位期（8/17–8/21）日均 | 157.4 |
| 低位期（8/22–8/27）日均 | 23.2 |
| 跌幅（日均口径） | **-82.3%** ⚠️【待实测】按表内数值复算为 -85.3%，与 -82.3% 不一致，回源 CSV 前勿对外引用 |
| 事件窗口（8/23 点，前 14 天 vs 后 14 天） | 2,123 → 217（**-89.8%**） |
| 转换页展示 | 175 → 6（**-96.6%**） |

**归因结论（已收敛）**：

- **外因**：对齐 Google 官方 **2026-08-18 spam update**（8/18 09:27 PDT 开始，8/21 01:49 PDT 完成）。
- **内因（可修复）**：**内页规模化去索引 / 覆盖坍塌**。
  - 铁证：**加权 position 持平（68 → 64，不是排名惩罚）**，但**活跃 page 从 14 → 3（-81%）**。
  - 含义：不是"排名被压低"，而是"页面根本没被收录/展示"。
- **促成因素**：`sitemap.ts` 曾用 `new Date()`，导致 73 个 URL 共享同一毫秒 lastmod（`2026-08-29T03:47:47.781Z`），Google 忽略抓取提示。
- **靶心**：**52 个程序化生成页的差异化**（30 convert + 22 guide）。

### 阶段三：双渠道分化期（9 月至今）——Google 与 Bing 走向相反

| 渠道 | VI（7v7，9/18） | 解读 |
|------|----------------|------|
| Google | **-13.2%**（8.4 vs 9.7） | ⚠️ n≈60–70/窗口，**不满足 n>400 判定门槛**（§6.2），仅方向参考，**不作判定依据** |
| Bing AI | **+58.8%**（289.3 vs 182.1） | 强增长（n≈2000/窗口，满足门槛） |
| Bing Web | **+53.7%**（56.0 vs 36.4） | 强增长 ⚠️ n≈390/窗口，临界，方向参考 |

**最强渠道归属证据**：21 个双渠道交集页的**加权平均排名 —— Bing 5.7 vs Google 56.7**。
→ 结论：**Google 单方面重排，不是内容质量问题**。

> 🔴 **术语铁律**：Google −13.2% / Bing AI +58.8% / Bing Web +53.7%，**只能叫「不对称」，禁止叫「背离」**。VI 的"背离"有严格三条件（见 §6.2），本组数据不满足。

## 1.5 诊断结论

1. 站点**技术 SEO 正常**（canonical/hreflang/schema/sitemap 全部正确，Schema 全站覆盖 30/30 + 22/22）。
2. 当前瓶颈是**内容差异化**与**域名权威**，不是技术缺陷。
3. **渠道必须分开归因**：Google 是"匹配广度被回收"，Bing 是"AI 引用增长"。用同一套指标衡量两者会得出错误结论。
4. **GEO 是这个站当前性价比最高的战场**：Bing AI 引用从 8 月的 249 涨到 9,012，且新站在 AI grounding 池里没有成熟站的历史包袱。

# 第二章 目标关键词策略与内容优化框架

## 2.1 用户画像（5 个细分，直接决定内容与外链分层）

| 细分 | 画像名称 | 核心场景 | 主要入口关键词 | 内容侧重 |
|------|---------|---------|--------------|---------|
| **A** | Kindle 生态迁移者 | 旧 MOBI/AZW3 藏书 → EPUB；新 Kindle 该用 AZW3 还是 EPUB | `mobi to epub` / `convert mobi to epub` / `azw3 vs mobi` | 转换页 + 格式对比博客 + Send to Kindle FAQ |
| **B** | Calibre 拒绝者 | 不想装桌面软件，要一次性浏览器转换 | `calibre alternative` / `online ebook converter` / `no install ebook converter` | Calibre Alternative 指南、首页价值主张 |
| **C** | 自出版/小型作者 | 手稿需多格式分发（EPUB/MOBI/PDF） | `docx to epub` / `epub to mobi` / `best ebook converter` | 指南、批量转换、格式保真说明 |
| **D** | AI 工具使用者 | 把 EPUB/MOBI 转 TXT/PDF 喂给 AI | `ai ebook converter` / `epub to txt` / `convert ebook for chatgpt` | AI Ebook Converter 指南、EPUB→TXT/PDF 转换页 |
| **E** | 多平台同步读者 | 手机/平板/阅读器/电脑跨设备阅读 | `read epub on any device` / `kobo to epub` / `ebook formats explained` | 格式百科、设备迁移指南 |

**优先级判断**：细分 **A（Kindle 迁移者）+ B（Calibre 拒绝者）** 意图最明确、流量最大，优先拿外链与深化内容。

> 📌 **画像必须来自真实数据，不能拍脑袋**。本画像的依据是 GSC 关键词分布（`mobi to epub` 50 曝光、`azw3 vs mobi` 32、`convert mobi to epub` 19）+ 设备分布 + 产品功能边界三者交叉验证。

## 2.2 关键词分层模型（四层）

```
第 1 层  钱页词（Money Keywords）    —— 交易/对比意图，直接对应 /convert/*
         例：mobi to epub converter、epub to azw3、azw3 vs mobi
         目标：进前 30（靠外链 + 内链集权）

第 2 层  支柱词（Pillar Keywords）    —— 信息意图，对应 /guide/* 与核心 /blog/*
         例：kindle formats、best ebook converter、ebook formats explained
         目标：进前 20（靠内容深度 + 内链枢纽）

第 3 层  长尾/场景词（Long-tail）     —— 问答式，对应 /blog/* 与 FAQ
         例：how to convert mobi to epub、can kindle read azw3
         目标：被 AI 引用 + 长尾展示

第 4 层  品牌词（Brand）             —— BookConv、bookconv.com
         目标：守住 + 提升 CTR（品牌词 CTR 5.49%）
```

**分层纪律**：
- 第 1 层用**外链深链**打；第 2 层用**内容深度 + 内链枢纽**打；第 3 层用**FAQ/结构化**打。
- **不要用第 4 层的指标（品牌词 CTR）去证明第 1 层的成功。**

## 2.3 意图 → 内容映射（意图作战映射表方法）

为每个关键词建立一行映射：`意图 → 目标页 → 当前状态 → 动作 → 优先级`。

| 意图类型 | 判定特征 | 对应页面类型 | 内容结构 |
|---------|---------|------------|---------|
| 交易型 | `convert X to Y` / `X to Y converter` | `/convert/x-to-y` | 工具 + 步骤 + 对比表 + FAQ |
| 对比型 | `X vs Y` / `which is better` | `/guide/x-vs-y` | 对比表 + 场景推荐 + Bottom Line |
| 信息型 | `how to` / `what is` | `/blog/*` | 定义块 + 步骤 + Key Takeaways + FAQ |
| 决策型 | `best X` / `X alternative` | `/guide/*` | 工具对比表 + Pros/Cons + 定价 |

> curl -s 站点/blog | grep -oE 'href="/blog/[a-z0-9-]+"' | sort -u | wc -l
> ```

# 第四章 GEO 核心原则与落地方法

## 4.1 GEO 是什么，与 SEO 的区别

**GEO（Generative Engine Optimization）= 让你的内容被 AI 引擎（ChatGPT / Gemini / Perplexity / Copilot / Claude）发现、引用、复述。**

| 维度 | SEO | GEO |
|------|-----|-----|
| 目标 | 争搜索结果里的**排名位置** | 争 AI 摘要里**被引用的片段质量** |
| 输出 | 10 个链接的排名列表 | 带来源标注的合成答案（平均只引 2–7 个源） |
| 核心信号 | 关键词、外链、元标签、域名权重 | 实体清晰度、结构化数据、知识图谱、E-E-A-T、全网事实一致性 |
| 抓手 | 外链、TDK、结构 | 机器可读结构化数据 + 可引用内容 |
| 度量 | 排名、点击 | 被 AI 引用频次、AI 声量份额（Share of Voice） |
| 内容策略 | 围绕关键词创作 | 围绕问题和子查询（Query Fan-out）创作 |
| 权威来源 | 外链（Backlinks） | 提及与引用（Mentions & Co-citations） |

> **一句话**：SEO 争排名，GEO 争引用。AI 平均只引 2–7 个源【行业通用，约值】，不在里面 = 完全不可见。
>
> ⚠️ **v1.2 官方校准**：上表"结构化数据/知识图谱"是**跨引擎 GEO（含 Bing AI 等）与富媒体结果**的通用抓手；但 **Google 官方 2026 指南明确"生成式 AI 搜索不需要结构化数据、无需特殊 schema.org 标记"**。因此 Schema 对本手册的价值定位为"富结果 + 部分 AI 引擎"，**不是 Google 生成式 AI 可见性前提**（详见 §4.8）。

## 4.2 底层模型：Retrieved → Cited → Trusted

GEO 遵循一条管道模型（类似传统搜索的"爬取→索引→排名"）：

```
阶段 1  Retrieved（被检索）  —— 进入 AI 候选池
        · 传统 SEO 基础仍是门票（排名越高，进池概率越大）
        · TTFB 是硬指标【行业说法，待实测验证】（影响实时检索毫秒级抓取）
        · 元数据完整（title / description / 结构化数据）

阶段 2  Cited（被引用）      —— 从候选池被选中
        · 事实密度 > 字数长度
        · 可引用格式：清晰小标题、定义型段落、FAQ
        · 权威信号：第三方引用、共引、E-E-A-T 显性标注

阶段 3  Trusted（被信任）    —— 用户点击/信任
        · 推荐上下文质量（品牌在正确场景被提及）
        · 品牌在多来源中描述一致
```

> **关键认知**：这是**概率性系统**，同一问题每次可能引用不同来源。目标是"在长期中持续被引用"，不是追逐单一位置。**AI 引用量月波动 40–60% 是常态。**

## 4.3 GEO 六大核心原则

### 原则 1：优化实体，而非关键词

传统 SEO 优化关键词，GEO 优化**实体**（AI 可唯一识别的人/品牌/地点/概念）。现代 AI 有"三道脑"：LLM 聊天脑 + 搜索索引脑 + **知识图谱脑**（用于事实核查）。实体信息不清晰 → AI 要么不引用，要么引用错误信息。

**落地**：建 Entity Home（About 页）+ 全网事实一致性 + 页面内可见的实体关系。

### 原则 2：可见内容结构 > 隐藏的 JSON-LD

WordLift 实验【供应商研究，n 与方法未公开，证据等级有限】表明：**单纯嵌入 Schema JSON-LD 对 AI 检索提升微乎其微**（JSON-LD 与正文争夺有限上下文窗口——机制为推断）；而把页面重构为**结构化实体枢纽**后，AI 回答准确率提升 34%。结论方向与本项目实测佐证一致（见下），故保留结论、降级证据等级。

→ Schema 是基础，但不是银弹。**真正起作用的是可见页面内容里的 H1–H6、列表、表格、FAQ 区块。**
→ 实战佐证：Gemini 曾"没看到"本站已有的 JSON-LD，反而建议"补 JSON-LD"——**前提错，勿当缺失去重加**（会破坏已生效 schema）。

### 原则 3：答案前置（Answer-first）

每篇文章**开篇 200 字内直接回答核心问题**，为 AI 提供可即时提取的"摘要块"。段落 ≤200 字，用清晰 Topic Sentence。

### 原则 4：Query Fan-out —— 建主题集群，不建孤立页

AI 把复杂问题拆成多个子查询，分别检索后合成。**你的内容必须覆盖所有子查询。**
→ 建**主题集群**（pillar + cluster），不建孤立页面。

### 原则 5：事实密度 > 字数

AI 偏好高信息密度、有独特数据支撑的内容。可引用句 = **具体数字 + 命名来源 + 年份**。

```
✅ QUOTABLE:  "Third-party testing found whey isolate bioavailability of 90–95%,
               compared to 70–80% for whey concentrate."
❌ NOT:       "Protein powder is a popular supplement choice."
```

### 原则 6：EEAAP 内容质量标准

> 📌 **EEAAP 是本项目自建扩展框架，不是行业标准**。行业官方标准是 Google 的 **E-E-A-T**（Experience / Expertise / Authoritativeness / Trustworthiness）。EEAAP = E-E-A-T 拆细 + Data 维度，**对外交流请统一说 E-E-A-T**，避免造成术语混乱。

| 维度 | 全称 | 说明 |
|------|------|------|
| **E** | Experience（真实体验） | 第一手真实经验，而非二手转述 |
| **E** | Expertise（专业深度） | 术语准确，分析有深度 |
| **A** | Authority（权威背书） | 来自权威来源的认可和引用 |
| **A** | Authority Proof（权威证明） | 可验证证据：证书、媒体报道、用户评价 |
| **D** | Data（可信数据） | 有来源依据的数据支撑 |

**EEAAP 自检清单**（发布前逐项过）：
```
[ ] Experience：含第一手真实体验？可验证的团队经历？
[ ] Expertise：术语准确？分析有专业深度？
[ ] Authority：有权威来源引用和背书？
[ ] Authority Proof：有证书/媒体/评价等可验证证据？
[ ] Data：数据有来源标注？样本量/时间范围说明？
```

## 4.4 GEO 资产清单

### 4.4.1 `llms.txt`（低成本对冲资产，v1.1 定位修正）

> 🔴 **v1.1 红队修正——先纠正 v1.0 的高估**：v1.0 曾写"AI 引擎优先读取 llms.txt"，**该说法已被 2026 年公开证据推翻**：
> - 🟢 **Google 官方《AI Optimization Guide 2026》逐字**："LLMS.txt 文件和其他'特殊'标记：您无需为了……在 Google 搜索（包括其生成式 AI 功能）中占有一席之地，而专门创建新的机器可读文件……**Google 搜索本身并不使用这些文件或标记**……**Google 搜索会忽略这些文件**。"（URL：developers.google.com/search/docs/fundamentals/ai-optimization-guide）
> - OtterlyAI 90 天日志研究：62,100+ 次 AI bot 访问中仅 84 次（**≈0.1%**）请求 llms.txt；Ahrefs ~13.7 万站分析：**97% 的 llms.txt 从未被 AI 爬虫读取**；SE Ranking：AI 引用 Top 50 域名中仅 1 个有此文件。
> - **无任何证据表明 llms.txt 影响 AI 引用**。本站 9,012 引用来自 Bing 索引与内容结构，与该文件无关。对 **Google 渠道 llms.txt 完全无效**（官方明确忽略），仅可能作用于其他 AI 系统且实测使用率 ≈0.1%。

**v1.1 定位**：仍保留维护，理由是三个**可辩护的次要价值**：
1. **CI 一致性校验的副产品**——`llms.txt` 与 sitemap/注册表三数一致的强制校验，实际防的是"新增页后忘同步"这一真实事故；
2. **编写过程 = 一次内容审计**（每页一句话定位，暴露孤岛页/重复页）；
3. **对冲未来 agent 标准化的低成本期权**（成本 ≈ 0，当前真实使用方是 Cursor/Claude Code 等编码 Agent 读开发者文档）。

位置：`public/llms.txt`（构建后落到站点根）。格式：

```
# 站点名
> 一句话定位（含核心差异点）

## Core Conversions
- [EPUB to AZW3](https://www.bookconv.com/convert/epub-to-azw3)
- [AZW3 to EPUB](https://www.bookconv.com/convert/azw3-to-epub)

## Guides
- [Ebook Formats Explained](https://www.bookconv.com/blog/ebook-formats-explained)

## About
实体信息（站点归属、服务范围）+ 隐私/信任说明（无注册、文件 1 小时删除）
```

**要点**：
- **全覆盖**：每个可索引页都列，不只列首页。
- URL 用**绝对地址**，描述带差异点（"free, no registration"）。
- 写进"关于/隐私/信任"——即使未来被 Agent 读取，也有信任锚点。
- 🔴 **`llms.txt` 是静态文件，不会自动更新**——新增页后必须手动同步。
- 🔴 **CI 必检**：Guides 数 == 注册博文数、Troubleshooting 数 == guide 数、Conversions 数 == CONVERSION_MAP 数（31）。
- ⚠️ **对外材料禁止把 llms.txt 列为"GEO 引用杠杆"或"AI 可见性措施"**——它是内部一致性资产，不是引用保证。GEO 资源排序应以 **§4.6 的 ②–⑥**（内容结构、FAQ Schema、可引用句）优先于 ①。

### 4.4.2 `robots.txt` 放行 AI 爬虫

确认以下 UA 未被 Disallow：`GPTBot` / `ClaudeBot` / `CCBot` / `Google-Extended` / `Applebot-Extended` / `PerplexityBot`。

验证：`curl https://站点/robots.txt | grep -i gptbot`。

### 4.4.3 实体结构化数据（全局 layout 的 JSON-LD `@graph`）

- `Organization`：`areaServed`（服务区域，如 `Worldwide`）、`availableLanguage`（如 `[en, es]`）
- `WebSite`：`inLanguage`（同上）
- ⚠️ **不要编 `sameAs` 社媒链接**，没有就留空 `[]`。

### 4.4.4 FAQ 结构化 → `FAQPage` JSON-LD（富结果 + 部分 AI 引擎有用，Google 生成式 AI 非必需）

> ⚠️ **v1.2 官方口径修正**：Google 官方指南明确——"生成式 AI 搜索**不需要结构化数据**，您也**无需添加任何特殊的 schema.org 标记**"。因此 FAQPage Schema 对本站的价值须重新定位为：**① 帮助 Google 富媒体搜索结果（FAQ 富摘要）；② 对 Bing AI / 其他引擎的问答抽取更可靠**（结构化字段远比散文可靠）。它**不是** Google 生成式 AI 可见性的前提条件。实战佐证见 §4.3 原则 2（Gemini 曾"没看到"本站已有 JSON-LD，反而建议"补 JSON-LD"——勿当缺失去重加，会破坏已生效 schema）。

- 内容层**必须有结构化 FAQ 字段**（`faqs: BlogFaq[]`），而不是只把 FAQ 写成散文 "Q:/A:" 段落。
- 只有结构化字段才能发射 `FAQPage` JSON-LD；AI 抽取问答时结构化远比散文可靠。
- 渲染 FAQ **只从一个来源取**，避免页面重复渲染两遍。
- 答案用**纯文本**（`stripMarkdown`）。

### 4.4.5 Key Takeaways + 可引用句

- 每篇文章顶部/尾部放 **3–6 条要点**，每条带具体数字/百分比/排名，可独立成立。
- 正文刻意写"可引用句"：具体数字 + 命名来源 + 年份。

## 4.5 页面级 GEO 标准

### 4.5.1 Convert 页 —— 7 要素（0–7 分制）

| # | 要素 | 标题关键词 | 字数要求 | GEO 价值 |
|---|------|-----------|---------|---------|
| 1 | About Source Format | `About.*Format` | — | 主题权威性 |
| 2 | About Target Format | `About.*Format` | — | 主题权威性 |
| 3 | Why Convert | `Why Convert` | — | 匹配搜索意图 |

| 7 | **Quality Checklist** | `Quality\|Checklist` | ≥150 词 | 提升权威性 |
| 8 | FAQ | `FAQ\|Frequently Asked` | ≥6 条 | 配合 FAQPage Schema |

**评分（0–7 分）**：
```
总分 = 字数(0/0.5/1) + FAQ(0/0.5/1) + When(0/1) + HowTo(0/1) + Comparison(0/1) + Quality(0/1) + Headings(0/1)

PASS（可发布）: score ≥ 5.0
WARN（阻断部署）: 3.0 ≤ score < 5.0 → exit 1
FAIL（阻断部署）: score < 3.0        → exit 1
```

**阈值（校准后，2026-09-25）**：

| 常量 | 值 | 含义 |
|------|-----|------|
| `TARGET_WORD_COUNT` | 1000 | 深内容满分线 |
| `WARN_WORD_COUNT` | 600 | 合格底线 |
| `MIN_HEADINGS` | 8 | 章节结构完整（仅 EN） |
| `MIN_FAQ` | 6 | FAQPage 支撑 |

> 🔴 **阈值必须基于实测分布**。原设"总字数 ≥2000 词"——实测 31 页**最高仅 1287 词**，导致所有页面误判 FAIL，门禁形同虚设。**校准前必须先 probe 真实分布。**

`KeyTakeaways ≥3` / `FAQ ≥5` / `Headings ≥5` / `Authorship` / `WordCount` / `InternalLinks ≥1` / `Intro`。
阈值（22 页实测 min=80 max=491）：WordCount TARGET=400 / WARN=250 / MIN=100。

### 4.5.3 Blog 页

`Key Takeaways（3–6 条）` + `FAQ（5–7 条 PAA 句式）` + `Article Schema` + `FAQPage Schema` + `作者块`。

# 第五章 分阶段实施路线图与优先级

## 5.1 优先级判定框架

```
优先级 = 影响面 × 可修复性 ÷ 成本

P0  影响面大 + 立即可做 + 成本可控   → 本周做
P1  影响面大 + 需 1–2 周            → 本月做
P2  影响面中 + 长期                 → 排期做
P3  观察项 / 依赖前置条件           → 挂起，设复评估锚点
```

**四条判定纪律**：
1. 🔴 **先修"可修复的内因"，再谈"不可控的外因"**。断崖归因里 spam update 是外因，但 52 个程序化页差异化是可修复内因 → 内因优先。
2. 🔴 **技术 SEO 正常时，不追加技术投入**。Google 低表现 = 排名竞争问题，追加技术 SEO 是浪费。
3. 🔴 **区分"内容问题"与"权威问题"**：位置 60–80 的词是权威度问题（页面优化天花板约到位置 30–40，上首页必须靠外链）。
4. 🔴 **发现"声明 ≠ 实现"先按法律权重排序**：要约 > 宣传 > 科普 > 文档。只改低权重面会制造"已处理"的假象。

## 6.2 统一度量衡：可见性指数（VI）

**公式**：
```
VI = (近 7 天均值 − 前 7 天均值) / 前 7 天均值 × 100%
```

**门槛**：

| VI 区间 | 判定 |
|---------|------|
| < 10% | 无信号 |
| 10–20% | 弱信号 |
| ≥ 20% | 成立 |

**「背离」三条件（必须同时满足）**：
1. 符号相反
2. 双方均 ≥20%
3. 末日相差 ≤3 天

> 🔴 **VI（7v7）与事件窗口（14v14）是两套数，禁互引**。断崖 **2,123→217（−89.8%）**只能标"事件窗口口径"。
> 🔴 **VI 跨轮不可比**（窗口不同）。
> 🔴 **VI ≥20% 阈值只适用 n>400 量级**；小 n 指标须泊松区间检验，否则是范畴错误。

## C.4 R7 事故复盘（法律权重排序）

**事故**：在售 Pro（$5/月）承诺 "Up to 50MB"，实际管线固定 10MB。Free 承诺 "5 conversions per hour"，实为 20 req/60s/IP（**低估 240 倍**）。`priority` 字段全库无赋值点。

**根因**：旧记忆把该现象记成"pricing 写 50MB、实际硬编码 10MB → 新文案不提文件大小"，给出的是**文案侧规避**——压住了新增文案，**却完全没碰根因**（定价页是真正收钱的那一页）。

**教训**：**发现"声明 ≠ 实现"时，先按法律权重排序（要约 > 宣传 > 科普 > 文档），再决定改声明还是改实现。只改低权重面会制造"已处理"的假象。**
**补充**：修复后 grep 必须**双语跑**（西语文案 "cinco conversiones por hora" 不会被英文关键词捕获）；`_archived/` 目录同样会被门禁扫描（= 投放面）。
