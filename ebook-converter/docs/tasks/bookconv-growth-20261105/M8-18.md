## 现状核查
- `src/lib/conversion-budget.ts`：Redis UTC 日预算，默认 10 credits；Redis 不可用时 fail-open 且 `degraded=true`。
- `src/lib/cloudconvert.ts`：本进程 402 冷却缓存 TTL 5 分钟；实例级，不是全局状态。
- `src/lib/conversion-cache.ts`：缓存命中不消耗 CloudConvert credits；`convert-handler.ts` 先查缓存，再查日预算。
- `BatchUpload.tsx`：首次 `CONVERSION_QUOTA_EXCEEDED` 后停止后续 CloudConvert 路线，纯本地路线继续；本轮不重写。
- 缺口：无 no-store 的额度状态查询接口；单文件转换无上传前提示。

## 本轮最小方案
1. 新增 GET `/api/conversion-status?source=&target=`，返回 `available | limited | unknown`。
2. 纯 JS 路线标为 `available/local`，不查询 CloudConvert 预算。
3. CloudConvert 路线依据 Redis 预算记录判断：`degraded`→`unknown`；预算触顶→`limited`；有剩余→`available`。
4. `available` 只表示“本地日预算记录有余量”，不承诺 CloudConvert 上游一定可用；402 冷却状态是实例级，不能伪装成全局保证。
5. 页面加载时查询并展示状态与 `checkedAt`；API `Cache-Control: no-store` / `ttlSeconds=0`，提示仅为快照，提交时服务端重查；不因 `limited` 自动拦截，因为服务端可能命中零额度缓存。
6. 不改预算计数、缓存、批量停止逻辑；不增加付费依赖，不更改生产配置。

## 红队（N3 动作前）
- A「预算接口可报告全局上游可用」：推翻。Redis只反映本系统记账；CloudConvert外部余额可能提前耗尽。
- B「未知状态应阻断转换」：推翻。Redis fail-open 是既有可靠性设计，阻断会把观测故障扩大为业务故障。
- C「纯JS路线受CloudConvert额度限制」：推翻。纯JS路线不消耗CC credits。
- D「批量逻辑需要重写」：不改。现有逻辑已在首次配额错误后跳过剩余计费路线并保留本地路线。

## 验收
- helper 单测覆盖 available / limited / unknown。
- API 强制动态、`Cache-Control: no-store`；校验格式参数。
- 单文件上传前查询；状态提示在选择文件前可见；limited 不自动拦截，服务端按“缓存优先、预算其次”复核；unknown 不阻断。
- 执行 helper 单测、相关既有预算/缓存测试、`npx tsc --noEmit`。
- 不部署、不 push、不提交。本地验收不等于生产生效。

## 红队（N4 交付前复核）`limited` 不能在浏览器端直接拦截：服务端缓存命中不消耗 credits，若预检拦截会误伤缓存资产。已修正为页面加载提示、上传仍由服务端裁决。

## 残余
- CloudConvert真实余额不能由本地Redis预算可靠读取；available不是上游保证。
- 402冷却缓存是函数实例级；跨实例一致性UNKNOWN。
- 批量仍依赖首次真实配额错误后停止，不在本轮增加第二套预检。
