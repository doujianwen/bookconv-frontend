## 1. 5 项 FAIL 的原始断言（逐条查明，非推测）

## 2. 第 44 个自动化是什么（改基线前必须先查清）

- id `a9306382-949b-4b2d-af45-0e0f53608cf4`，名 `AIOS-DailyPlan-ReadOnly-Sync`，`status=PAUSED`，`created_at=1794715931590`（11-15 12:12），无 `next_run_at`。
- 不是 BookConv 经营任务，不是重复创建的调度器。43 个快照 id **全部仍在库**（`native - sqlite = 空`）。
- 若当时直接把 43 改成 44 而不查来源，就会掩盖「出现了一个来历不明的自动化」——因此改为**白名单增量审计**：登记 id + 原因，未登记的新增仍然 FAIL。

## 3. 第 5 项的第二重根因：API 的 `RECENT` 判据是 10 分钟

`server.py::workbuddy_bridge_status()`：`state = 'RECENT' if 0<=age<=600 else 'STALE'`（600 秒）。
而快照由每日任务刷新，实测 age=17.3h ⇒ `RECENT` 在非同步瞬间**不可达**。这不是运行故障，是断言口径错误（把「10 分钟心跳」当成「每日同步」的健康判据）。
修正为：`count == sqlite live A1`（双源一致）+ `age <= 26h`（日更 + 2h 容差）。日更停 1 天即 FAIL，不会漏。

## 6. 为什么不构成「放宽断言掩盖问题」

| 原断言 | 新断言 | 新断言多抓什么 |
|---|---|---|
| live A1 == 43 | 43 ≤ live ≤ 43+白名单，且白名单 id 必须真实存在 | 未登记的第 45 个自动化；白名单腐烂 |
| nids == sids | nids ⊆ sids 且 sids−nids ⊆ 白名单 | 自动化「消失」；未登记新增 |
| 7d A1 ≥ 95 | 活跃天数≥6 且 ≥0.7×上一等长窗口 且 ≥50 | 断崖式下跌（绝对值阈值抓不到） |
| API count==43 & RECENT | count==sqlite & age≤26h | API/DB 漂移 |

7d 的归因证据：11-03→11-16 逐日 `10,17,5,11,13,20,9,19,6,9,6,19,14,11`；本期 84 / 上期 85，比值 0.99。95 这个数依赖已滚出窗口的 11-08(20)、11-10(19) 峰值日。
