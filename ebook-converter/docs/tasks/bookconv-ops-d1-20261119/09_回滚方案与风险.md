## 2. 回滚触发条件

| 条件 | 动作 |
|---|---|
| 新验证 job 在正常成功部署时误报 FAIL（假红）且确认非环境因素 | revert + 登记 P1 |
| 验证 job 对生产构建造成任何写操作（设计上不可能，若观察到即 revert） | 立即 revert |
| 集成通道部署行为异常且疑似与本变更相关（设计上无耦合，若有即 revert 隔离变量） | revert + 诊断 |

## 3. 部分回滚（不 revert commit）

- 仅关闭验证 job：GitHub UI disable workflow「Verify Production Deployment (push to main)」或删除 workflow 文件——生产部署不受影响（唯一通道=集成）。
- 仅回退脚本行为：workflow `run` 行为可临时加 `continue-on-error: true`（不推荐，等于引入新假绿；仅作应急记录）。

## 4. 风险登记

| 风险 | 等级 | 缓解 |
|---|---|---|
| Vercel 构建偶发 >10min → 验证 job exit 3 假红 | P2 | 失败方向安全（不假绿）；可调 VPD_DEADLINE_MS 或接受重跑 |
| HTTP 回读无 cache-buster，CDN 可能对旧缓存回 200 | P2 | 前置条件已是 deployment success，风险极低（复审确认） |
| REPO 硬编码兜底（仓库改名→404 误报） | P2 | 非阻断加固项（GITHUB_REPOSITORY 优先） |
| 429/5xx 重试仅受 deadline 约束 | P2 | 语义与 T6b 自洽，可选加次数上限 |
| 验证 job 自身失败 vs 生产部署成功的区分 | 已明确 | 07 文件按两层分别报告，不互相冒充 |

## 5. 结论

回滚路径真实可用、成本 ~1 分钟；风险全部 P2 且失败方向安全（宁可假红不可假绿）。
