## 1. 四层诘问

### Layer 1 · 审「我自己的判断」

**【已核验】A1：两条告警都是用户侧真坏文件？→ 推翻。**

先自我攻击这条「决定性证据」：告警里的 `inputHash` 真的是 `sha256[:12]` 吗？
查 `src/lib/convert-handler.ts:345-348`：

```ts
const inputHash =
  buffer && buffer.length > 0
    ? createHash('sha256').update(buffer).digest('hex').slice(0, 12)
    : undefined;
```

`buffer` 是 `convertAndStream` 收到的原始上传字节，无变换。口径确认后，实测：

```
tests/fixtures/valid.epub | size=1095 | sha256[:12]=c518ca05a2a4
告警 Job 7a9b3d76         | size=1095 | Input hash=c518ca05a2a4
```

大小与哈希**双匹配**。再查 `.workbuddy/memory/2026-11-04.md:216`：

> ⚠️ 首测用 `tests/fixtures/valid.epub` 得 500 CORRUPT_INPUT —— **假警报**：
> 该夹具 OPF 的 manifest 引用 `nav.xhtml` 而包内无此文件，属不合法 epub，CC 报错正确。

同日生产「每日故障检查」自测记录，与告警时间 `2026-11-04T07:15:56.537Z` 吻合。
该夹具 ZIP 内只有 `mimetype` / `META-INF/container.xml` / `OEBPS/content.opf`，
OPF 引用了不存在的 `OEBPS/nav.xhtml` —— 正是告警里的 `manifest reference missing`。

**结论（Fact）**：第一条告警来自**项目自测流量**，不是真实用户坏文件。

**【不可答】A2：第二条 `e6b90936` 是真实用户文件吗？**

无 1703936 字节文件、无哈希命中。生产日志在 Vercel，Hobby 仅留 1h，本地 `logs/` 只有 125B。
→ **UNKNOWN**，不得定性。上一轮「两条都是用户坏文件」整体降级。

### Layer 2 · 审「来源共享的前提」

**【已核验】A3：预检只覆盖「会走后端委托」的路径？→ 推翻（注释与实现矛盾）。**

`src/app/api/convert/route.ts:109` 注释写：

> 注意：仅覆盖「会走后端委托」的路径；非委托路径由 convertAndStream 内的
> runConversion→validateInputFile 兜底，行为不变。

但代码里预检位于 `route.ts:111-138`，`if (canDelegate)` 在 **`route.ts:140`**。
即只要 `backendConfigured()` 为真，**`canDelegate=false`（熔断打开 / 目标不在白名单 /
epub→html 例外）的请求照样执行预检**。误杀面比注释声称的更大。
证据形态：源码行号（Fact，静态位置）；未做 handler 级运行时注入，标为代码路径分析。

**【已核验】A4：预检「廉价」吗？→ 部分成立，但成本性质被误述。**

`input-validation.ts:22` 声称 jszip 只读中央目录、不解压大成员。实测（20MB 不可压缩正文）：

```
arrayBufferMs=7.7   preflightMs=91.2   section35Ms=510.5
preflightCorrupt=false  section35=PASS  rssMB=252
```

预检自身确实比 §3.5 便宜约 5.6 倍，**声明成立**。但 `validateInputFile()` 的生产调用点只有
`conversion.ts:1280`（`runConversion` 内）与 `queue.ts:320` ——
**后端委托返回 200 的 happy path 原本根本不执行 §3.5**。
所以这 ~100ms + 一次全量 `arrayBuffer()` 复制，是叠加在**每一个成功请求**上的纯新增成本，
不是「把原有成本前移」。原注释「省掉后端往返」只对坏文件成立，对好文件是净增。

**【已核验】A5：`Response` 连续两次 `clone().text()` 安全吗？→ 通过。**

`conversion-backend-client.ts:242-243` 先 `readBackendCode(res)` 再 `readBackendDetail(res)`，
两次 `res.clone().text()`。独立实测两轮：

- Node 原生 `Response`：first === second，原 body 仍可读；
- **真实 fetch 到本地 HTTP server（500 + JSON body）**：
  `firstEqSecond=true`，`code=CONVERSION_FAILED` 正确解析 → `VERDICT_REAL_FETCH: PASS`。

隐藏假设成立。`onFallback` 串 / 计 1 次故障 / 回退行为由既有 36 例 + 新增 2 例 + 代码比对支持，未破坏。

**【可答】A6：「输出完全不变」有一处边界差异。**
新分支 `failWith(..., await readBackendDetail(res))` 的 detail 取自**首次** 5xx；
原重试失败分支取自 **`retry.res`**。若后端两次 500 返回不同 body，告警卡 detail 会不同。
`retryTag` 只进 `console.warn` 不进 `onFallback`，这部分确实不变。→ P2 观察项，非阻断。

### Layer 3 · 审「数据本身」

**【已核验】A7：新增预检与既有 §3.5 判定口径一致吗？→ 推翻，6 处不一致。**

独立对比脚本 `redteam-preflight-compare.test.ts` 对 **25 个样本**同时调用
`preflightValidateInput()` 与 `validateInputFile()`（均为真实产品函数，非复刻），
由脚本自动计算 verdict。`JEST_EXIT=0`，输出落 `preflight-vs-section35.stdout.txt`。

| id | 样本 | 预检 | §3.5 | 判定 |
|---|---|---|---|---|
| S2 | 合法 EPUB，OPF **注释**里含 `<item href="ghost.xhtml">` | CORRUPT | PASS | **新增误杀** |
| S3b | 合法 EPUB，`data-href` 排在真 `href` 之后 | CORRUPT | PASS | **新增误杀** |
| F1 | 合法 **FB2**（纯 XML） | CORRUPT | PASS | **新增误杀** |
| F2 | 合法 **LIT**（MOBI 派生） | CORRUPT | PASS | **新增误杀** |
| S4 | 真断链，但 `href` 用**单引号**（合法 XML） | PASS | CORRUPT | 新增漏检 |
| S5 | 真断链，`<opf:item>` **命名空间前缀** | PASS | CORRUPT | 新增漏检 |

四个误杀分支的 reason 全部映射 `CORRUPT_INPUT` + `classifyAlertSeverity=user`——
**告警卡会把误杀显示成「用户输入错误（预期内）」灰卡**，运维不会收到任何系统侧信号，
坏味道会静默潜伏。这与治理规则 §5 实证表「缓慢失真、届时无法归因」同型。

**根因 1（P0，格式分类错）**：`input-validation.ts:36-38`

```ts
const ZIP_BASED_SOURCES = new Set(['epub','zip','docx','xlsx','pptx','fb2','lit','oeb']);
```

项目自己的权威分类 `conversion-cache.ts:52-54` 写得很清楚：

```ts
const ZIP_FORMATS = new Set(['epub','zip','docx','htmlz','cbz','kepub','oeb']);
const MOBI_FORMATS = new Set(['mobi','azw3','azw','lit','pdb','lrf','rb']);
const TEXT_FORMATS = new Set(['txt','rtf','fb2','html','xml','shtml','txtz']);
```

`fb2` 是纯 XML（`conversion-cache.ts:73` 还专门检查 `FictionBook` 标记），`lit` 是 MOBI 派生，
**两者都不是 ZIP**。既有 §3.5 的 ZIP 校验只在 `sourceFormat === 'epub'` 时执行
（`conversion.ts:224`），对 fb2/lit 完全不校验。新增魔数硬拦截是**纯粹的新增误杀**。

而 `src/lib/constants.ts:38,39` 显示 `fb2→epub`（SV 1300）、`lit→epub`（SV 1600）
均为 `phase: P0, status: 'live'`，首页 `HomePageClient.tsx:26` 也列出这两个格式。
生产后端已配置（当日 memory 第 215 行 `X-Conversion-Backend: hit`），预检必然执行
→ **一旦部署，这两个 P0 词的所有转换请求直接 400 CORRUPT_INPUT**。

**根因 2（P1，解析器口径分叉）**：§3.5 用 `fast-xml-parser` 的 `XMLParser`
（`conversion.ts:176-215`，`removeNSPrefix: true`，只取 `package.manifest.item` 的 `@_href`），
会忽略 XML 注释、处理命名空间、支持单双引号；新增预检用正则
`/<item\b[^>]*\bhref="([^"]+)"[^>]*>/gi`（`input-validation.ts:59`），
于是：注释里的 `<item>` 被当成真引用、`data-href` 被 `\bhref` 匹配、单引号与命名空间前缀漏检。
**同一份校验意图写出两套实现，必然分叉。**
