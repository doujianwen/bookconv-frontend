## 一、为什么需要这套工作流

这不是理论。下面三个结论**都曾经被写进正式报告、并被当成决策依据**，后来全部被推翻：

| 曾发布的结论 | 实际真相 | 错因 |
|---|---|---|
| 「Bing AI 引用稳定，日均 70.4」 | 实为**加速中**，近7天日均 **214.6** | 用了已否决的均值算法 + 过期窗口 |
| 「GSC 近 7 天微升 6.5%」 | 平移 1 天即 **−13.2%**，且统计不显著 | 窗口挑选 |
| 「/es 伪西语页是断崖主因」 | /es 仅占断崖前 **2.9%** 曝光，量级不成立 | 未做量级校验 |

**共同点**：三次都不是"算错数"，而是**在正确的数字上做了不可靠的推理**。
所以本工作流管的是**从原始数据到结论之间的每一道转换**，不是管算术。

### 核心命题

> **一个结论的可信度，等于它经过的所有转换中最弱那一环的可信度。**

因此把链路拆成五道闸，逐道设卡。任一闸未过，结论只能降级表述，不能照常发布。

---

## 二、五道闸总览

```
原始导出/API
    │
 ① 取数闸  ── 数据真的取到了吗？（客户端 × 代理）
    │
 ② 口径闸  ── 这个"日均"除以的是谁？
    │
 ③ 窗口闸  ── 窗口是规则定的，还是我挑的？
    │
 ④ 溯源闸  ── 文件标的日子 = 数据截止的日子吗？
    │
 ⑤ 可比闸  ── 两个渠道能放进同一张表吗？
    │
  结论
```

**用法**：任何要写进日报/报告的结论，先问自己在哪一闸上站得住。五闸全过才可作强结论；缺一闸降一级。

## 三、闸①：取数闸 —— 数据真的取到了吗

### 3.1 第一个判据：有 HTTP 状态码 = 链路通

这是最容易被误判的一条，代价是**几天的排查方向跑偏**。

| 你看到的 | 你以为 | 实际含义 |
|---|---|---|
| `401 Unauthorized` | 网络不通 | ✅ **已到达 API**，只是缺凭证 → 链路完全正常 |
| `411 Length Required` | 服务异常 | ✅ **已到达端点**，只是缺请求体 |
| `404`（对 `GET /token`） | 端点不存在 | ✅ 该端点只收 POST → 链路正常 |
| `000` | —— | ❌ **只有这个才是真的没通** |

**口诀：只要有状态码，TCP + TLS 就是通的。**

### 3.2 第二个判据：`curl` 能通 ≠ 你的脚本能通

实测规律（2026-09-18）：

| 客户端 | 是否自动读 `https_proxy` 环境变量 |
|---|---|
| `curl` | ✅ 读 |
| Python `requests`（默认会话） | ✅ 读 |
| **Node `https.request` / `https.get`** | ❌ **不读** |

后果：**同一个代理、同一个 URL、同一台机器，`curl` 返回 200，Node 脚本却 `ETIMEDOUT`。**
此时若去怀疑代理节点、DNS、防火墙，方向就错了——**问题在客户端，不在网络**。

补充坑：Node 22 **没有** `undici.ProxyAgent`（`new (require('https').ProxyAgent)` 直接抛 `is not a constructor`）；`NODE_USE_ENV_PROXY=1` 要 Node 24+。

### 3.3 第三个判据：端口会漂移，禁止硬编码

本项目实测见过的代理端口：`7897` → `13425` → `9890` → **`8837`**。

```bash
# ✅ 正确：先读当前实际值
env | grep -i proxy
P=$(env | grep -i '^https_proxy=' | cut -d= -f2-)

# ❌ 错误：把某个历史端口写死在脚本里
curl -x http://127.0.0.1:7897 ...
```

### 3.4 推荐实现：Node 算，curl 传

当必须用 Node（如需 `jsonwebtoken` 签 JWT）但网络要走代理时，**不要让 Node 发 HTTP**：

```js
// Node 只做本地计算：纯 crypto，零网络 → 不触发代理问题
const signature = jwt.sign(payload, privateKey, { algorithm: 'RS256' });

// HTTP 全部交给 curl：自动读 https_proxy，零配置
import { execFileSync } from 'child_process';
function curlJson({ url, method = 'GET', body, headers = {} }) {
  const args = ['-sS', '--max-time', '60', '-X', method, url];
  for (const [k, v] of Object.entries(headers)) args.push('-H', `${k}: ${v}`);
  if (body) args.push('--data-binary', body);
  return JSON.parse(execFileSync('curl', args, { encoding: 'utf8', maxBuffer: 64e6 }));
}
```

**权衡**：零依赖、跨 Node 版本稳定；代价是每次调用起一个 curl 进程（本场景调用个位数，可忽略）。
**不要选**：手写 `CONNECT` 隧道（易出 `Client network socket disconnected before secure TLS connection was established`）；为拿 `ProxyAgent` 而装 `undici`。

## 四、闸②：口径闸 —— 这个"日均"除以的是谁

### 4.1 事故复盘

同一个「Bing AI 引用日均」，在项目内**同时存在三个值**，都被冠以"日均"：

| 值 | 算式 | 分母性质 | 问题 |
|---:|---|---|---|
| 70.4 | 3311 ÷ 47 | 日历天（含 15 个零值天） | 🔴 系统性低估 |
| 103.5 | 3311 ÷ 32 | 活跃天（非零天） | ⚠️ 高估，不可用于规模陈述 |
| **214.6** | 近 7 天总量 ÷ 7 | 近 7 天 | ✅ 默认推荐 |

三者差了 **3 倍**，方向叙事从"停滞"变成"加速"。

### 4.2 规范

> **任何"日均"必须标注分母类型。没标分母的日均，一律视为无效指标。**

| 分母类型 | 公式 | 用在哪 | 禁用在哪 |
|---|---|---|---|
| 日历天均值 | 总量 ÷ 窗口总天数 | 对外披露累计规模 | 判断趋势（零值天会压死） |
| 活跃天均值 | 总量 ÷ 非零天数 | 内部效率评估 | 规模陈述（会虚高） |
| **近 7 天日均** ✅ | 近 7 天总量 ÷ 7 | **默认真相口径** | —— |

### 4.3 为什么"活跃天"也会骗人

活跃天均值天然 ≥ 日历天均值，**差值本身反映的是"有多少天是零"，不是"每天效率多高"**。
用它宣布"日均提升"等于说"我们少了几天空转"——这是把**覆盖率**伪装成了**效率**。

## 五、闸③：窗口闸 —— 窗口是规则定的，还是我挑的

### 5.1 事故复盘（本次最震撼的一条）

同一份数据，同一个"近7天 vs 前7天"，**只把窗口平移 1 天**：

| 对比窗口 | 前 | 近 | 变化 |
|---|---:|---:|---:|
| 9/1-9/7 → 9/8-9/14 | 62 | 66 | **+6.5%** |
| 9/2-9/8 → 9/9-9/15 | 68 | 59 | **−13.2%** |

**结论符号翻转。** 日报当时用的是第一行，得出的"微升"是个纯粹的窗口产物。

### 5.2 为什么小样本这么脆弱

该站点日曝光在 3–21 之间波动（标准差约 5.9），7 天合计仅 60 上下。
分母是两位数时，**任何单点波动都能造出两位数的百分比**。

**补一层统计检验**（同样的数据）：

| 项 | 值 |
|---|---|
| 前7天 | 均值 9.71，sd 5.88 |
| 近7天 | 均值 8.43，sd 5.88 |
| t 值 | **−0.409** |
| 自由度 | 12 |
| 判定 | **不显著**（p.05 临界 2.179） |

### 5.3 规范

1. **窗口由规则固定**：默认「数据末日往前 7 天」vs「再往前 7 天」，末日一律取该渠道最新可得日，**不做人工调整**。
2. **禁止因结果不好看而换窗口**。若确要换，必须**同时呈现新旧两个窗口的结果**。
3. **n < 30 的窗口必须附显著性检验**。
4. **t 检验不显著时，无论百分比多大，最高只能报"弱信号"**。

### 5.4 敏感性自查动作（强制）

产出任何百分比前，做一次：

```bash
# 把窗口整体平移 1 天，结论还成立吗？不成立 → 该百分比不可用
```

## 六、闸④：溯源闸 —— 文件标的日子 = 数据截止的日子吗

### 6.1 事故复盘

一个文件名与内部字段都标注 `snapshot_date: 2026-09-13` 的 JSON，**其数据实际只到今天 9/9**。

日报把它当成 9/13 的现状引用 → 相当于**用 4 天前的存量描述当下**。

### 6.2 怎么识破

**文件的自我声明不可信，要用数据自身的结构反推窗口**：

| 字段 | 值 | 推论 |
|---|---|---|
| `total_days` | 47 | 窗口长度 47 天 |
| `days_active` | 32 | 其中 32 天有数据 → **15 天为零** |
| `citations` | 3311 | 累计总量 |
| `daily_avg` | 70.4 | 验算：3311 ÷ 47 = 70.45 ✅ → 确认它用的是**日历天**分母 |

再看这些数字与哪个日期区间自洽 → 反推出真实截止日。

### 6.3 最强的交叉验证：跨文件增量

| 快照 | 累计 citations | 数据截止 |
|---|---:|---|
| 9/13 文件 | 3,311 | 9/9 |
| 9/16 文件 | 3,936 | 9/13 |

```
增量 = 3936 − 3311 = 625，落在 9/10–9/13 共 4 天
⇒ 625 ÷ 4 = 156.3 引用/天
```

**156.3 落在 103.5 与 214.6 之间** → 与"加速"叙事一致，与"停滞(70.4)"矛盾。
**一句话判真伪**：拿增量速率去比对各候选口径，哪个自洽用哪个。

> 📌 **通用原则**：当两个文件对同一指标给出不同值时，**不要选"看起来对"的那个**。
> 用增量、比率、字段内部算术关系做交叉验证，让数据自己说话。

### 6.4 附带纪律

- 快照**必须记录实际数据截止日**，不能只记导出日。
- 推荐命名：`xxx_导出2026-09-18_数据截至2026-09-15.json`。

## 七、闸⑤：可比闸 —— 两个渠道能放进同一张表吗

### 7.1 事故复盘

日报原文的对比方式：

| 渠道 | 指标 |
|---|---|
| Google | 9.4 **impressions** |
| Bing AI | 70.4 **citations** |

据此宣布"双渠道背离格局确认"。

**为什么无效**：impression 与 citation 是**不同量纲、不同采集口径、不同触发条件**的量。
并列它们并宣布一个方向性结论，等于**用"苹果个数"对比"橘子甜度"**。

### 7.2 解法：归一化为变化率

不要比绝对值，只比**相对自身基线的变化率**——这样量纲自动抵消：

$$
VI_{ch} = \frac{\bar{V}_{recent7} - \bar{V}_{prev7}}{\bar{V}_{prev7}} \times 100\%
$$

其中 $V$ = 该渠道的可见性计数（Google/Bing传统 → impressions；Bing AI → citations）。

### 7.3 信号门槛（关键）

| \|VI\| | 判定 | 允许的表述 |
|---|---|---|
| < 10% | 🚫 无信号 | 只能说"持平/波动"，**禁止**说"上升""微升""下降" |
| 10–20% | ⚠️ 弱信号 | "可能变化"，须附"继续观察" |
| ≥ 20% | ✅ 信号成立 | 可作结论，须附检验结果 |

### 7.4 "背离"的判定条件（三条同时满足才算）

1. 两渠道 VI **符号相反**；
2. 两渠道 VI **均 ≥ 20%**；
3. 两渠道数据末日相差 **≤ 3 天**。

不满足任一条 ⇒ 只能称 **「不对称（asymmetric）」**，不得称「背离」。

**本案判定结果**：

| 渠道 | VI | 过门槛？ |
|---|---:|---|
| Google | −13.2% | ❌ |
| Bing AI | +22.1% | ✅ |

⇒ **不对称**，非背离。原报告"背离格局确认"不成立。

## 八、红队提问清单（12 问）

产出结论后，逐条自问。**任何一问答不上来，该结论降级为"待验"。**

**取数层**
1. 我看到的 HTTP 状态码是什么？是 `000` 还是别的？（有码 = 通）
2. 我的客户端是否真的走了代理？（`curl` 通 ≠ 脚本通）
3. 脚本里的端口/日期是硬编码的吗？现在还对吗？

**口径层**
4. 每个"日均"的分母是什么？日历天 / 活跃天 / 近7天？
5. 同一指标在项目内有几个值？分别出自哪份文件？

**窗口层**
6. 窗口是我按规则定的，还是我挑的？
7. 把窗口平移 1 天，结论还成立吗？
8. n 是多少？做过显著性检验吗？

**溯源层**
9. 文件标的日期 = 数据实际截止日吗？我是怎么核的？
10. 能不能用跨文件增量做一次交叉验证？

**可比层**
11. 我是不是在拿两个不同量纲的东西作对比？
12. 我说"背离"时，三条件都满足吗？

## 九、完整实操演示（2026-09-18 全过程）

| 步 | 动作 | 结果 |
|---|---|---|
| 1 | 直连测 Google API | 得 `401` → 判定**链路通**，不是网络问题 |
| 2 | 对比 `curl` vs Node | `curl` 通、Node 超时 → 定位为**客户端不吃 env 代理** |
| 3 | 改实现 | Node 签 JWT + curl 传输 → 取数成功，末日推进至 9/15 |
| 4 | 检查口径 | 发现 Bing「日均」有三个值（70.4 / 103.5 / 214.6） |
| 5 | 溯源 | 发现标注 9/13 的文件实际截至 9/9 |
| 6 | 交叉验证 | 增量 625÷4 = 156.3/天 → 支持 214.6，"稳定"结论推翻 |
| 7 | 窗口敏感性 | 平移 1 天 → `+6.5%` 翻转为 `−13.2%` |
| 8 | 显著性 | t = −0.409，df = 12 → 不显著 |
| 9 | 可比性 | 引入 VI 归一化 → 判定为"不对称"而非"背离" |
| 10 | 落章 | 日报加**勘误横幅**（不改写正文，保留存证） |

**关键纪律**：第 10 步选择"加勘误横幅"而非"改正文"——**错过的结论要留痕**，否则后人会重新引用。
`append-only` 不是形式主义，它防止同一个错误在半年后被再次发现。

## 十、可打印检查清单

```
□ 状态码不是 000（401/411/404 都算通）
□ 脚本客户端确认会走代理（不是"curl 测过了"就够）
□ 端口/日期无硬编码
□ 每个"日均"都标了分母类型
□ 同一指标只有一个权威出处，其余标注"已废弃"
□ 窗口按规则定，且做过平移 1 天敏感性自查
□ n < 30 的窗口附了显著性检验
□ 文件标注日期 ≠ 数据实际截止日（已反推核实）
□ 做了跨文件增量交叉验证
□ 跨渠道对比用的是变化率，不是绝对值
□ 说"背离"前三条件逐条核过
□ 已过时的结论加了勘误标记，未删原文
```

## 附：术语表

| 术语 | 定义 |
|---|---|
| **VI（Visibility Index）** | 渠道可见性变化率，用于跨渠道归一化对比 |
| **日历天均值** | 总量 ÷ 窗口总天数（含零值天） |
| **活跃天均值** | 总量 ÷ 非零天数 |
| **窗口平移敏感性** | 窗口整体挪动后结论是否稳定 |
| **window shopping** | 通过挑选窗口制造想要的结论 |
| **不对称 / 背离** | 一方有信号另一方无 = 不对称；双方信号相反且均达标 = 背离 |
