## 一、方法论先说清楚（这本身是可移植的第一条）

我先写了一版探针，跑出结果后**自己把它否了**：4/5 条信号在人工构造的正例上就失配，
却照样输出了跨项目对照表。**如果直接拿那张表回答你"能不能移植"，结论就是假的。**

修法（已写进脚本）：

```
第 1 步  判据自检：每条信号必须在「已知含该模式」的样本上命中，且在
                   「已知不含」的样本上不命中。任一不过 ⇒ 标记 DEAD，从统计中剔除。
第 2 步  只用 LIVE 判据扫项目
第 3 步  跨项目对照 + 通用性判定
```

**这就是纪律 21（判据自身出 bug ⇒ 静默假失败）本身成为可移植资产的最强证据**——
它不是一句格言，是一份可执行的探针骨架，能直接套到任何语言的项目上。

## 二、可移植的三档划分

### 档 A：直接移植（13 条，机理与语言/框架无关）

这些不是"我总结的经验"，而是**人的认知偏差在工具链上的投影**——换语言不改变。

| # | 纪律 | 为什么跨栈成立 | 跨项目实测 |
|---|------|----------------|-----------|
| 1 | 唯一真相=实测，AI 审计也会错 | 任何 LLM 都会自信地编造 | 不可机械检测（属方法论） |
| 2 | **静默假成功**（判据可执行却报 PASS） | 所有自动化都有这个失效面 | ✅ Reddit 16 / nancypet 29 / alphashop 9 |
| 3 | 纠正的终点=错误值不可能再被取到 | 任何"打个补丁就算修"的做法 | 方法论 |
| 4 | 中文环境禁在源码字符串写 unicode 转义 | Windows + Python/JS/任何语言 | 见档 B 的补充 |
| 5 | **反向验证**（注入事故→必须被抓） | 假判据只能靠反向证伪发现 | 方法论，**最值钱的一条** |
| 6 | 判据取不到基线 ≠ 基线为空 | 任何"读配置/读清单"的代码 | 方法论 |
| 7 | **「跑通一次」≠判据完整**（写法覆盖率） | 正则只认一种语法就漏同义写法 | ✅ 见下方"被证伪"一节 |
| 8 | 本地绿 ≠ 线上绿 | 任何有部署环节的项目 | 方法论 |
| 9 | **判据的正确性依赖调用姿势** | cwd / 入口 / 环境变量都会改结论 | ✅ 实测命中（本文末） |
| 10 | 有逻辑但不可见也是假门禁 | 短路分支吃掉诊断输出 | 方法论 |
| 11 | **不可判定绝不能报 FAIL** | 任何有环境差异的门禁 | 方法论 |
| 12 | 门禁挂载点本身也会是假门禁 | 任何"配了 CI 就以为在跑" | 方法论 |
| 13 | **无 pre-commit ⇒ 事故在 commit 时已入库** | Git 全平台通用 | ✅ 4 项目均无 pre-commit |

> 说明：标"方法论"的 8 条无法机械检测，但**可移植性最高**——它们是决策原则，
> 换一个项目依然是决策原则。标实测的 5 条有硬数据。

### 档 B：机理通用，判据要重写（5 条）

**这是本次评估最重要的发现**：不是所有经验都能原样搬。搬过去要改形式，否则判据就是坏的。

| # | 纪律 | 本项目形态 | 换栈后必须改成 |
|---|------|-----------|--------------|
| 14 | 抽样偏差（`tail -8` 见 `exit 0` 就判绿） | shell + `exit` 码 | Python：`sys.exit` / Rust：`Result` / 任何语言的"判成败"都可能被中间层吞掉 |
| 15 | Windows Node fork EBUSY | Node `spawnSync` | ⚠️ **这是 Windows+Node 专属**，换栈要重新找等价坑（Python `subprocess`？PHP `exec`？见下方实测） |
| 16 | TS 模板串五道关 | TypeScript 反引号 | **纯 TS 专属**，换栈直接作废 |
| 17 | Edit 对 CRLF 静默失配 | 编辑器 + Git autocrlf | ⚠️ 换栈仍存在（`core.autocrlf` 是 Git 全局）但**表现不同** |
| 18 | 源码里的转义 ≠ 运行时的值 | TS `import` + 运行时探针 | ✅ 通用且重要，形式改成"dump 运行时值而非读源码" |

### 档 C：本项目专属（4 条，不建议移植）

| # | 纪律 | 为什么无意义 |
|---|------|------------|
| 19 | 同一注入代码不能通吃两种引号风格 | 只对"用脚本批量注入 TS 模板串"这个具体工程手法有效 |

任何有多路由/多模块的项目里都成立。

## 三、被证伪的一条（必须写出来）

`re-unbounded-quantifier`（纪律 9：正则取值范围要覆盖异常值）我判定为"✅ 跨技术栈通用"，
**这个结论被我自己的抽验推翻了**：

- nancypet 命中 251 处，看起来是大问题
- 抽验真实内容：`re.findall(r'\d+\.?\d*', s)`、`re.findall(r'[a-z]+', s)` ——
  **全是正常的宽松匹配**，一个是真问题
- ⇒ 我的信号**过宽**（把"用了字符类"等同于"有 bug 风险"），信号无效

同理 `string-replace-mutation` 在 alphashop 命中 15 处，抽验发现
`sys.stdout.reconfigure()` 的 `except Exception: pass` 是**合理的编码兜底**。

**这条本身就是最好的可移植性证据**：纪律 7（跑通一次≠判据完整）在**跨项目场景下**
又复发了一次——我的 v2 判据在自检阶段抓到了 1 条 DEAD（`proc-call-no-status-check`
因误报被剔除），但对 `re-unbounded-quantifier` 这类**"过宽而非过窄"**的缺陷，
自检机制抓不到（因为正例确实命中了）。**过宽的判据比窄的更危险：它让你以为已经防住了。**

## 四、别的项目里真实存在的同类隐患（抽样证据）

### 1. Reddit获客系统 — `engine/progress.py`
```python
try:
    ...
    STATUS_FILE.write_text(json.dumps(payload, ensure_ascii=False), "utf-8")
except Exception:
    pass
```
`STATUS_FILE` 是**流水线状态文件**（`status: running|done`，供外部读取判断任务是否结束）。
写失败静默吞掉 ⇒ 外部看到"永远 running"或读到半截 JSON，**任务实际已结束但状态没更新**。

⇒ 这就是 ebook-converter 纪律 2 的**跨栈同构案例**：
"静默失败 + 外部无感" 在 Python 爬虫管线里以完全相同的方式成立。

### 2. nancypet — `05-工具脚本/*.py`（20 个文件命中 silent-except）
批量抓取/改价脚本里大量 `except: return None`。JSONDecodeError 的兜底合理，
但**混着裸 `except`** 时，抓取失败会返回"空结果"而不是报错，
下游 Excel/CSV 会得到"这个商品没有数据"而不是"抓取失败了"。

⇒ 对应 ebook-converter 纪律 6：**判据取不到基线 ≠ 基线为空**。
`return None` 就是 Python 里的"取不到基线"，`None` 被当成"没数据"往下流。

### 3. 4 个项目**全部**没有 pre-commit 钩子
只有 ebook-converter 有 5 道（虽然 `.git/hooks/` 不入库，换机器要手动重装）。
⇒ 纪律 13 在**所有**你的项目里都成立且都未落地。这是投入产出比最高的一条推广项。

## 五、可移植资产清单（按"落地成本 / 收益"排序）

如果要在其他项目推广，建议这个顺序：

### 🥇 第一批：几乎零成本，今天就能做
1. **pre-commit 门禁**（纪律 13）—— 5 道门禁模板可直接复制：
   `syntax-sweep` / `audit-content-integrity` / `audit-workflow-integrity` /
   `audit-agent-discipline` / `audit-heading-uniqueness`。
   换项目要改的是"扫什么"，不是"怎么挂"。
2. **判据三态**（`实测为真` / `实测为假` / `不可判定` + `exit(2)`）——
   这是所有门禁的骨架，改判据时**必须**带第三态。
3. **反向验证**（纪律 5）—— 写完任何判据，注入一次事故看它抓不抓。
   这条不需要任何代码，纯流程。

### 🥈 第二批：一次半天
4. **判据写法覆盖率**（纪律 7）—— 正则同时兼容单/双/无引号；
   写完用 `grep -c` 统计各种写法的实际分布。
5. **删除/剥离操作的自报比例**（纪律 21）—— 见下方代码，跨语言通用。

### 🥉 第三批：需要按项目改造
6. 把"静默假成功"审计列成清单，对每个数据流水线查一次
   （`except: pass` / `return None` / `|| true` / `catch {}`）。
7. 探针脚本 `_wb_tmp/cross-project-probe-v2.py` 抽成通用版
   （换信号定义即可复用，已支持 py/js/ts/php/ps1/rs）。

## 六、不能移植的，必须明确说清（避免误导）

以下几条**在本项目很有用，搬到别的项目会制造噪音**：

| 纪律 | 为什么在别的项目上会误报 |
|------|------------------------|
| Windows Node EBUSY | Python 的 `subprocess` 没有这个问题；PHP `exec` 又是另一套。**照搬会让你去查不存在的 bug** |
| TS 模板串五道关 | 只对"脚本批量注入反引号模板串"有效。别的语言没有模板串 |
| 中文路径八进制转义 | 你的其他项目路径里没这个组合（`D:/alphashop/...` 是纯 ASCII） |
| `/formats/*` GSC 暗页 | 纯 bookconv SEO 策略 |
| 62s 转换超时 / CloudConvert 402 | 纯 bookconv 后端 |

> 🔴 **我自己踩过这个坑**：初版探针的 `unbounded-delete` 在 ebook-converter 报 0 命中、
> 在 nancypet 报 20 处。差点得出"你这个项目删除操作有风险"的结论——
> 但 nancypet 那 20 处是数据抓取脚本里的正常清理，**不是纪律 21 说的
> "剥离操作没自报比例"**（后者要求的是 sed 剥 script 那种场景）。
> **信号名相似 ≠ 机理相同**，这是移植时最容易犯的错。

## 七、一句话总结

**能移植的是"怀疑一切自动化结论"的思维习惯，不是具体的正则和脚本。**

22 条里真正值钱的是 13 条档 A——它们不依赖任何技术栈。
但移植时最容易犯的错是**把判据连同结论一起搬**：我这次就差点用一条过宽的正则
给你下一个"nancypet 有 251 处正则风险"的假结论。

**推荐姿势**：把纪律当**提问清单**用（"我这条判据的写法覆盖全了吗？"
"这个 except 吞掉的是失败还是空值？""判据跑不通时会 exit(2) 还是静默通过？"），
而不是当**现成脚本**搬。提问清单不会误报，脚本会。
