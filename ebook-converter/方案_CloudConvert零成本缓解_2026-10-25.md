# 方案：CloudConvert 额度耗尽的零成本缓解（2026-10-25）

> 背景：2026-10-24 CloudConvert 402 第三次复发（诊断见 `诊断_CloudConvert额度耗尽_2026-10-24.md`）。
> 用户决策（2026-10-25）：站点流量尚小、未盈利 → **当前阶段零成本优先、流量优先**；付费（充值或重购 VPS）留待 monetization 后。
> 本文只评估 **$0** 的改善 / 解决路线，并给出推荐排序。

---

## 0. 硬约束与事实
- **mobi / azw3 是 Kindle 专有格式**——没有可靠的纯 JS / Node 免费库能生成它们。免费引擎只有两条路：① CloudConvert 免费档；② 自托管 Calibre（需一台机器）。
- 因此"免费解决"= **要么让免费档撑得更久，要么搞一台 $0 的机器跑 Calibre**。
- 已核实：荧光云 VPS 已到期；Vercel 无 Calibre；免费档 10 credits/天；仅 epub→txt / epub→zip 本地可用。

---

## 1. 路线 A：把 CloudConvert 免费档用到极致（零 $、零运维、立即可做）

最契合"零成本 + 流量优先"，且无论后续怎么选都该做。

### A1. 结果缓存（去重）—— 单一最高杠杆
- 机制：成功结果按 `SHA256(输入) + source + target` 缓存；相同文件+格式二次请求直接命中 → **0 credits**。
- 存储：用项目已有 **Cloudflare R2**（成本基线已含 ~$1/月，增量 $0）；或 Supabase Storage 免费 1GB；或 Vercel KV 免费额度。
- 为什么对低流量有效：SEO 站常见"同一本样本/热门书"被反复转换，且用户失败后会重试——缓存既省 credits 又消灭重试浪费。
- 收益：把"10 credits/天"的有效吞吐放大数倍，实现约 1 个模块 + 存储配置。

### A2. 每日额度预算（守门）
- 机制：按 UTC 天计数已用 credits（Upstash Redis 免费 / DB 行）；接近免费上限时**停止发往 CloudConvert**，改为优雅提示，而非把最后几分额度烧在重试 / 注定失败的请求上。
- 与现有逻辑互补：`cloudconvert.ts` 已有 5 分钟 402 缓存短路（避免 270s 空轮询，很好），但**没有对"成功调用"做预算**——补上这层才能避免"10 分额度被错误/重试吃光"。

### A3. 优雅降级 UX
- 额度耗尽时返回友好文案 + 推荐仍可用的本地格式（epub→txt / epub→zip），而非吓人报错。零成本提升"看起来可靠"的感知。

### A4. 扩大本地（免费）格式覆盖，腾出免费额度给 Kindle 格式
- epub→txt/zip 已本地；可再加 Node 原生 / pure-JS 转换（如 epub→html 抽取很轻量；epub→pdf 可客户端或免费库），减少其他格式对 CloudConvert 的占用，**把每日免费额度留给 azw3/mobi**。
- 注意：azw3/mobi 本身无法本地化（专有格式），此条只做"腾额度"。

---

## 2. 路线 B：搞一台 $0 机器跑 Calibre（零 $、需运维、彻底去依赖）

- **Oracle Cloud Always-Free**：ARM VM（4 OCPU / 24GB）永久 $0（需绑卡，偶有容量紧张）。装 Docker + Calibre，暴露 `/api/convert-internal`，Vercel 设 `CONVERSION_BACKEND_URL` 即完成接线——项目 `docker-compose.yml` 与 `route.ts` 转发逻辑**已就绪**，主要是部署 + 2 个环境变量。
- 备选：$0 档 Fly.io（3 共享 VM）、Render free（512MB，空闲回收）、Railway 免费额度——都要绑卡、有限额。
- 价值：彻底消除"按次 credit"依赖，等于把"重购 VPS"目标**提前以 $0 实现**。符合"不增加成本"，只是要花运维时间。
- 取舍：用户已把"重购 VPS"排到 monetization 后；Oracle 免费档是同一目标的 $0 版，是否现在做由你定（运维成本 vs 彻底去单点依赖）。

---

## 3. 路线 C：把 Calibre 塞进 Vercel 函数（零 $、脆弱）—— 不推荐作主方案
- 社区有人把 calibre 二进制打进 Vercel function；但 Calibre + 依赖超 250MB 函数体积上限且依赖众多共享库 / Qt，脆弱。仅作实验性备选。

## 4. 路线 D：换其他免费转换 API（Zamzar 5 文件/24h、ConvertAPI 微量）—— 不推荐
- 比 CloudConvert 免费档还小，可靠性更低。无收益。

---

## 5. 推荐排序（契合"零成本 + 流量优先"）
1. **现在做（零 $）**：路线 A（A1 缓存 + A2 预算 + A3 降级）。让免费档在当下低流量下够用，且是长期该有的卫生实践。
2. **可选现在做（零 $，需运维）**：路线 B（Oracle 免费 VPS + Calibre）——若想现在就彻底干掉额度依赖且不花钱。
3. **以后（monetization 后，按既定计划）**：充值 CloudConvert 付费包（$17/1000）或付费 VPS，永久解除约束，由广告 / 付费收入覆盖。

## 7. 残余风险 / 诚实披露
- 缓存对"每个用户各自的私有文件"命中率有限（文件不同则不复用）；但它仍消灭重试浪费、覆盖热门 / 样本文件，对低流量站点净收益明显。
- 免费档 10 credits/天是项目文档口径（DEPLOYMENT.md），非我实测 CloudConvert 当前档位；若实际档位更低，缓存的放大效应更重要。
- Oracle 免费档需绑卡 + 偶有容量问题，不是"零摩擦"；若介意运维，路线 A 已足够撑当前阶段。
