```
11-02: 2   11-03: 2   11-04: 10   11-05: 6
```
持续 4 天聚集 ⇒ 系统性、确定性问题。

### 5.3 F20 诊断前缀：线索与陷阱
11-05 的 6 次失败中 **3 次带 F20 诊断前缀**（F20 部署于 11-05 11:19）：
```
{ stage: PUT, kind: NETWORK, httpStatus: null, online: 1, msBucket: <1s, eventCount: 3 }
```
- `httpStatus=null` ⇒ R2 未返回任何 HTTP 状态 → **排除 R2 403/5xx 服务端拒绝**。
- `on=1` + `<1s` ⇒ 浏览器在线、瞬时失败。
- ⚠️ **v1 踩坑**：F20 设计文档明确写「CORS 预检拒绝与离线客户端都落到这里，`onLine` 是唯一判别量」。按此，`on=1`（在线）恰恰**更指向 CORS/浏览器侧确定性拦截**，而非「客户端网络瞬时中断」。v1 把这个方向读反了。更根本的是：`PUT:NETWORK` 是个**粗桶**，把「CSP 拦截 / CORS 拦截 / 真网络中断」三者混在一起，仅凭它无法定性——必须另做实验。

### 5.4 红队证伪链（v1 → v2，逐条实测）

| # | 实验 | 结果 | 推翻/确认 |
|---|---|---|---|

| E3 | R2 CORS 预检（外部 vantage，正/负对照） | `OPTIONS` + `Origin: https://www.bookconv.com` → **204** + ACAO + `Allow-Methods: PUT` + `Allow-Headers: content-type`；恶意 Origin → **403** 无 ACAO | ✅ 全局 CORS 健康（**由实验证明，而非 E1 的推断**）；白名单含 www 与 apex，正确拒绝 localhost/preview/大写/尾斜杠 |

| E6 | 线上响应头 CSP | `connect-src 'self' https://bookconv.com https://www.google-analytics.com https://stats.g.doubleclick.net https://*.sentry.io` — **无 R2 host** | 🎯 **定位真因** |
| E7 | 真实 Chromium A/B/C（`www.bookconv.com` origin，每例全新 presign） | A 线上原 CSP → `TypeError: Failed to fetch` **2ms**；B CSP 加 R2 host → **PUT 200**；C 同源负对照 → 200 | 🎯 **CSP_ROOT_CAUSE_CONFIRMED** |
| E8 | 用**真实 next.config 产出的 CSP**（通配源）复验 + 事故态反控 | 事故态 → 拦截 13ms；修复态 → **PUT 200** | ✅ **修复有效性 + 反向验证双通过** |

**真根因**：`next.config.ts` 的 CSP `connect-src` 由 `CORS_ORIGINS`（站点自身 origin）拼出，从未包含 R2 上传 host。浏览器 `fetch()` 受 `connect-src` 约束，对未列入的 host **在发网络请求之前**就拒绝 → `TypeError: Failed to fetch`、无 HTTP status、`<1s`、`navigator.onLine=1`，与 GA4 前缀 `PUT:NETWORK:on=1:<1s` 完全吻合。

**为什么此前所有排查都漏掉**：CORS（10-31 修好）与 CSP 是**两道独立门禁**；Node/curl 探针**不执行 CSP**，所以 E3/E4 全绿，而真实浏览器 100% 被拦。这正是 MEMORY §0「单机视角系统性误导 / 连通拦截类诊断必用外部 vantage 对照」的又一次实证——且这次连"外部 vantage"也必须是**真实浏览器**，不能是 Node。

**为何 10-31 修 CORS 后失败未消失**：10-31 修的是第二道门，第一道门（CSP）始终关着。`DIRECT_UPLOAD.md` 验证清单第 3 项虽写了"浏览器 Network 里看 PUT 200"，但显然从未真在浏览器里跑过，否则当场就能发现。已补第 8 项强制 CSP 检查（见 §6）。
