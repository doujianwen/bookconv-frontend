## 1. 两份实时告警的分析与根因

### 1.1 告警 1 — ℹ️ User Input（正确，无需动作）
- **Error: `Invalid zip file`** → `error-handler.ts:40` 映射 `CORRUPT_INPUT`。
- **§3.5 check: failed** → `convert-handler.ts:301-302` 由 `errorCode==='CORRUPT_INPUT'` 反推为 `failed`，与真实 `validateInputFile`（`conversion.ts:178` 抛 `Invalid zip file`，中央目录缺失）一致。
- **分类**：`classifyAlertSeverity` 经 `mapErrorCode`→`CORRUPT_INPUT`→命中 `USER_SIDE_ERROR_CODES` → 灰卡 ✅。
- **结论**：34,805 字节的小文件，中央目录缺失（下载截断/伪 epub）。处理链路正确，仅「频率突增才需关注」。

### 1.2 告警 2 — 🚨 System-side fault（**误分类 + 已知盲区复发**）⚠️
- **Error: `CloudConvert job failed after 2 attempt(s) | engine=calibre: ... Input task has failed || engine=auto: ... Input task has failed`**
- **§3.5 check: passed** → 因错误码是 `CLOUD_CONVERT_ERROR`（含 "cloudconvert" 命中 `error-handler.ts:61` 兜底），非 `CORRUPT_INPUT`，反推为 `passed`。
- **First engine: calibre** → 解析自错误串首个 `engine=XXX`（`convert-handler.ts:303`）。

**关键事实澄清（实测代码）**：
1. `engine=calibre` / `engine=auto` 是 **CloudConvert 自身的子引擎选择**（`cloudconvert.ts:402` `const label = useCalibre ? 'engine=calibre' : 'engine=auto'`），**不是**自建 VPS Calibre 后端。故告警 2 是**纯 CloudConvert 失败**，两个子引擎对同一 2.5MB 文件**都**在 import 阶段报 `Input task has failed`。
2. 同一输入哈希 `54cdb7688239`、两个 CC 子引擎失败签名**逐字相同** → **文件级（输入级）问题，不是引擎宕机**（宕机会表现为 402/超时/5xx，且不绑定单一 input hash）。
3. 这与 `docs/m8-10-失败签名监控小结-2026-10-27.md:13,16,53,169` 记载的 **POST-§3.5 复发**完全一致：
   - 10-26 Job `9dba318b`（epub→mobi）同样的「calibre+auto 双引擎 Input task has failed，2 attempts，Severity=System-side fault」。
   - 文档明言：**「§3.5 仅覆盖 jszip 级损坏，不等于 CloudConvert import 级损坏——后者（jszip 能解压、CC 导入失败）仍会进入 CC 并复现 Input task has failed」**；close-gate 当时已判 **FAILED**（修复后 7 天复发，证伪「签名消除」假设）。
4. 本次 10-31 告警 2 是 **复发 #2（10-26 + 10-31，均为深度校验放行后）**，已触发 `data/seo-geo-board.json:1336` 的重开诊断条件（「复发 ≥2 且均为深度校验放行后 ⇒ 重开诊断」），但未见新诊断落地。

**根因（结构性，非偶发）**：`validateInputFile` 的 §3.5 深度校验（`conversion.ts:200-252`）= jszip 解压每个成员 + container.xml 非空。**它不复制 CloudConvert 的 import 校验**（OPF/内容 XML 良构性、资源引用完整性、DRM 加密流、CC 不支持的压缩方式）。一个 jszip 能解压的「结构坏」EPUB，CC import 仍会拒收 → `Input task has failed`。该盲区在 10-27 已被文档定性为**结构性无法靠 §3.5 消除**。

**误分类危害**：`classifyAlertSeverity` 对 "Input task has failed" 找不到任何用户侧模式（不含 corrupt/drm/too large…）→ fail-closed → 红卡「System-side fault — investigate now」。但此签名在历史上是**最典型的坏输入类**（10-19/10-26/10-31 三证），红卡会：① 稀释 2026-10-01 建立的告警通道信噪比（M8-8 分级本就为防此）；② 把「已知的 §3.5 盲区复发」伪装成「系统紧急故障」，误导排查方向。

**附带浪费**：`cloudconvert.ts` 把 `Input task has failed` 当瞬态 `importTaskFailed` 重试（`m8-10:175`、 `seo-geo-board.json:1380`），对**永久损坏**输入白烧第 2 个 CC job + 额度 + ~270s 轮询。告警 2 的 `after 2 attempt(s)` 正是这次无效重试的实证。

## 3. 红队审计（本次新增 + 对内嵌红队的复核）

### 🔴 F1（P0）告警 2 误分类 + §3.5 结构性盲区复发（内嵌红队**完全未覆盖**）
- **证据**：`cloudconvert.ts:402`（engine=calibre/auto 是 CC 子引擎）、`m8-10:13,16,53,169`、`seo-geo-board.json:1362,1336`。
- **判据**：同一 input hash + 两子引擎失败签名逐字相同 ⇒ 输入级，非系统级；且属已文档化的 POST-§3.5 盲区类。
- **影响**：红卡误报 → 信噪比稀释 + 掩盖已知盲区；close-gate 阈值（≥2 复发）已触发但诊断未重开。
- **建议**：① 把 `Input task has failed` 从 fail-closed 红卡改路由到「输入被 CC 拒收」灰卡（或独立 ambiguous 桶），与 DRM/corrupt 同级降级；② 对 `Input task has failed` 加**永久损坏短路**（参照 DRM 的 `/DRM/i` 不重试逻辑，`cloudconvert.ts` 附近），禁止无效第 2 次重试；③ 触发 `seo-geo-board.json:1336` 的重开诊断，给出 §3.5 盲区的最终处置（接受为已知用户侧长尾 / 或加 OPF 良构性本地校验）。

### 🔴 F2（P0）GA4 计数自相矛盾：完成率 + 失败率 = 150%（内嵌红队**未覆盖**）
- **证据**：报告原文 上传 4、完成 3、失败 3。
- **判据（数学不变量）**：在干净的「终态」计数下，`完成 + 失败 ≤ 上传`。此处 `3+3=6 > 4`，**物理上不可能**。报告却同时给出「完成率 75%」与「失败率 75%」并列为真，二者之和 150%。
- **根因假设（需代码确认）**：`conversion_failed`/`conversion_complete` 是**每次尝试级**事件，非作业级终态。一次上传若「先失败（发 failed）后重试成功（发 complete）」会同时贡献两个事件 → 作业被重复计入。这恰与 `cloudconvert.ts` 的瞬态重试逻辑吻合。
- **影响**：① 「完成率/失败率」被包装成终态率，实则含双计；② 「真实成功率 50% = 3/(3+3)」**建立在 complete 与 failed 互斥的假假设上**——数据本身已证伪该假设，故 50% 也不可信；③ 无法从报告判断 4 次上传中究竟几次真正失败。
- **建议**：在 `ga4-redteam.mjs` 增加不变量检查 `completed + failed <= uploads`（违反即 P0 FAIL）；明确 `failed` 是「尝试失败」还是「作业失败」，消除双计；B3 当前只查字段**存在**（`ga4-redteam.mjs:100-108`），不查内部一致性，须升级。

### 🔴 F3（P0）叙述层假成功：「引擎侧无异常失败」 vs D2「不可验证」自相矛盾（内嵌红队**未覆盖**）
- **证据**：报告 Part A 写「转化失败率：正常（引擎侧无异常失败）」；同报告深度审计 D2 = UNKNOWN：「failed_by_date_error_code 无数据（维度未注册或查询失败）→ 无法验证 Part A 引擎结论」。
- **判据**：同一报告**不能**既声称「引擎侧无异常失败」（已验证结论），又声明支撑它的失败分流数据「缺失/不可验证」（D2）。这是叙述层的假成功——结论早于证据成立。
- **叠加风险**：`error-handler.ts:104-110` 注释载明 quota/CloudConvert 错误曾「 fell out and were reported as UNKNOWN in GA4」，故 UNKNOWN:1 正是已知盲区；以含 UNKNOWN 盲区的口径宣称「引擎侧无异常失败」不严谨。
- **建议**：D2=UNKNOWN 时，Part A 的引擎结论必须降级为「⚠️ 引擎结论不可验证」，禁止出现「正常/无异常」字样（与 B5 对 B1 的处置逻辑一致）。

### 🔴 F4（P0，复核实嵌红队 · 确认）数据陈旧下的「全绿」= 假成功
- 内嵌 B1 FAIL（`ga4-fetch-status.json.ok` 缺失 → F1 未真拉取）、B5 FAIL（应改发「⚠️ 数据未刷新，结论不可信」而非全绿）。**确认有效**：这正是 2026-10-01「100% 失败 T+1 才发现」的同质假成功。须作为硬门禁（非仅红队备注）——只要 B1≠PASS，飞书巡检结论**不允许**出现「全绿/正常」。
