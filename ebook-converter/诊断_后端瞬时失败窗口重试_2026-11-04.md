## 1 背景与本质
本次告警 f547b469（epub→azw3）复盘结论：用户文件真坏 → CORRUPT_INPUT 正确，无 bug。但排查暴露一个**真问题**——`delegateToBackend` 对后端**任何**非 200 / 非 429 失败都**直接回退 CloudConvert，零重试**。单次瞬时 5xx（后端活着、但进程抖动 / 重启 / GC）就把本可在后端成功的 job **白烧给 CC**（额度紧张 + ~270s 慢路径）。这才是任务 #1 的真正收益点（P2-C 放宽 EOCD 是 no-op，已否决）。

## 2 READ/TRIAGE 现状 FACT（代码实测）
- 熔断器 `src/lib/conversion-circuit-breaker.ts:23-24`：内存态、per-instance，`FAILURE_THRESHOLD=3`、`COOLDOWN_MS=60_000`；429 走 `recordBackendBusy` **不**计入熔断（2026-11-02 红队修正）。
- 后端客户端 `src/lib/conversion-backend-client.ts`：原 `delegateToBackend` 非 200 / 非 429 失败（5xx / 超时 / 网络）直接回退 CC，零重试（原行 173 / 192 `recordBackendFailure`）。
- 调用链 `src/app/api/convert/route.ts:100-124`：`canDelegate` 成立 → `delegateToBackend` → 返回 null（失败 / 跳过）即 `convertAndStream` 走 CC；**单次失败无重试**。
- 超时预算 `route.ts:33` `maxDuration=300s`；`delegateToBackend` 默认后端超时 `90s`（`CONVERSION_BACKEND_TIMEOUT_MS`）；CC 回退轮询 ~270s（`src/lib/cloudconvert.ts:16` MAX_POLL_ATTEMPTS=135×2s）。
- `recordBackendFailure` 调用点唯一：仅 `conversion-backend-client.ts`（原 173 / 192）。

## 3 方案 A（实施 · 已落地）
- 抽 `attemptOnce()`：单次调用自带 `AbortController` + 超时，返回 `{ res } | { err }`（超时 / 网络错误）。
- `delegateToBackend` 按状态码分支：
  - **200** → `recordBackendSuccess` + `streamBackendHit`（成功）。
  - **429** → `recordBackendBusy`，**不重试**（容量信号）。
  - **4xx（400–499）** → `failWith`（record 1 次 + 告警），**不重试**（确定性输入 / 体积错，重试必失败）。
  - **超时 / 网络错误（err）** → record 1 次 + 告警，**不重试**（慢失败，后端明显扛不住或挂了）。
  - **5xx（快速失败）** → **重试 1 次**（重试前再 `shouldUseBackend` 防御）→ 成功则 `recordBackendSuccess`；仍 5xx / err → `failWith`（record 1 次）。
- 失败计数语义：**重试失败只计 1 次**（避免「5xx + 重试失败 = 2 次」加速熔断）。
- 安全网：只对毫秒级 5xx 重试；超时 / 网络 / 429 / 4xx 一概不重试 → 后端真挂时与现状等价（多 1 次毫秒级请求），方案 **fail-safe**。
- 告警串（`onFallback`）保持现状格式（不带 `after 1 retry`），retry 信息仅进 `console.warn` → 既有 5xx 测试零破坏。
